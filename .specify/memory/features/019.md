# Feature Detail: MCP Native Capability Backend

**Feature ID**: 019
**Name**: MCP Native Capability Backend
**Description**: S-layer native-capability backend (compiler/git/browser/任意原生) exposed to agents as defined MCP tools — never a free VM login — mediated by the trusted ateom MCP client; cross-S shared pool with per-tenant strongly-isolated execution units. (xuanji custom feature)
**Status**: Draft
**Created**: 2026-09-20
**Last Updated**: 2026-09-20

## Overview

Xuanji-branch custom feature. The wasm sandbox gives an agent a minimal controlled
capability surface (ADR 0003 D1, deny-by-default), but a digital employee routinely
needs **native capabilities** wasm cannot/should not provide: compilers, git, native
binaries, browsers, heavy scientific compute, arbitrary CLI tools.

The naive answer — give the agent a channel to log into a VM and operate freely — is
**rejected**: it makes the native surface an *untrusted shell* whose only boundary is
"the VM is disposable", with no explicit capability boundary or enforcement point
(contradicts ADR 0003 D1/D3). This feature instead exposes the native backend as **a
set of defined MCP tools**; the agent **only calls these tools, never logs in freely**.
"MCP interface" is the contract; the backend implementation is pluggable (shared
disposable VM / container pool / remote API / per-tenant gvisor·microvm actor) — so
"VM + multi-user login" is one *special case*, and the existing
`python-exec-gvisor`/`microvm` escape hatch unifies into the same model.

Trust ordering: `ateom (S trusted mediator / MCP transport client) > execution unit
(S disposable untrusted / MCP server) > agent (wasm, Agent trust domain)`. Two sharing
scopes: **within-S** (one employee's agents; OS-account/container isolation suffices)
and **cross-S** (P-managed shared pool maximizing infrastructure benefit; per-tenant
execution unit **must** be microvm/gvisor — OS multi-user is not a tenant boundary).

Design authority: [ADR 0007](../../../docs/decisions/0007-mcp-native-capability-backend.md);
narrative in [trust-domain-panorama.md](../../../docs/concepts/trust-domain-panorama.md) §3;
decomposition in [two-tier-fork-sandbox-split.md](../../../docs/tasks/two-tier-fork-sandbox-split.md) §8.

Bootstrapped 2026-09-20 from the four-trust-domain panorama + ADR 0007 (Proposed) +

## Key Changes

1. **F10 MCP shared-pool orchestration/routing layer** — P-layer **trusted, hardened,
   self-audited** component (self-consistency condition C2; cross-tenant blast-radius
   concentration): schedules per-tenant execution units, routes ateom's MCP calls, holds
   pool-side allowlist + audit. Form: reuse WorkerPool/actor machinery (a microvm-class
   WorkerPool whose actors are MCP server instances) or a new controller/service.
2. **F11 per-tenant MCP execution units** — strongly-isolated **microvm** (reuse existing
   microvm SandboxClass, kata + cloud-hypervisor; condition C1 "shared pool, isolated
   execution unit"), disposable/wiped after use; + **MCP server runtime** (native tool
   executor). OS multi-user only for within-S; cross-S must be microvm/gvisor.
3. **Zero-trust, no standing secret (D5/I-1)** — SPIFFE/podcert workload identity + mTLS;
   tools labeled **(a) secret-free** / **(b) secret-bearing**; (b) → ateom mints a
   short-lived scoped token per call, injected, used-once, **never stored in the backend**
   (ADR 0003 D6 代取不返值, MCP version).
4. **MCP-backend audit + allowlist (S↔MCP crossing)** — per-call audit event
   (tool / args-truncated / target / allowed / status / bytes / latency + `src_domain`/
   `dst_domain`) into the ADR 0003 D7 unified model; MCP tool allowlist per capability.
5. **Backend egress controlled (D8/I-4)** — backend network egress allowlisted, or no
   direct egress (network ops routed back through ateom); must not bypass the wasm egress
   allowlist (ADR 0003 D5).

## Implementation Notes

- **Division of labor**: fork/substrate = F10/F11/F12 (pool orchestration, microvm
  execution units, cross-domain audit/allowlist) + zero-trust identity wiring (podcert);
  sandbox = S10 (ateom MCP client/mediator) + S11 (`mcp_call` host function + agent MCP
  semantic client + output sanitization) + S13 (MCP audit + tool contract). See sandbox
  `two-tier-sandbox-layer-design.md` §6.
- **Enforcement point is ateom (trusted side), never the backend** (ADR 0007 D2) — else
  the boundary is enforced by code an attacker can compromise (violates ADR 0003 D3).
- **cross-S sharing's tenant boundary** rides on C1 (microvm execution units) + C2
  (P-trusted orchestration) + C3 (zero-trust no-secret + cross-domain audit + output
  hostility). This is the central design bet — it raises the robustness bar on the pool.
- **Cross-repo seam**: the MCP tool contract/schema (tool names, arg schema, capability
  binding, (a)/(b) label) is the single source of truth — sandbox defines what the agent
  sees (S13/S5), fork's MCP server implements it (F11); analogous to the Ateom proto seam.
- Depends on **020 Multi-Actor Worker Pod** — without multiple concurrent agents per
  worker, "shared by these agents" has no referent.

## Future Evolution Suggestions

- MCP tool minimal-set + ABI/version management (converge with ADR 0003's host-function
  ABI open question; MCP schema vs wit component model).
- Backend form selection: shared VM multi-user vs per-tenant microvm pool vs container
  pool — cost / isolation / cold-start trade-off; whether within-S and cross-S differ.
- Unify `python-exec-gvisor`/`microvm` escape hatch fully as MCP-backend special cases.
