# Feature Detail: API Compatibility Policy

**Feature ID**: 018
**Name**: API Compatibility Policy
**Description**: Defined stability/versioning policy for the v1alpha1 CRDs and control-plane gRPC API, including deprecation rules and fork-compat guardrails.
**Status**: Draft
**Created**: 2026-08-06
**Last Updated**: 2026-08-06
**Type**: Non-functional (DFC)

## Overview

Upstream declares the project early-stage with no backward-compatibility
guarantees ("APIs are almost guaranteed to change"). For a long-lived fork that
rebases upstream continuously, an explicit compatibility policy is needed: how
xuanji consumes breaking upstream API changes, how custom API additions are
versioned (especially the E2B protocol plane), and how clients learn about
breaking changes.

## Latest Review

Bootstrapped from DFX gap analysis (DFC) during feature-registry
initialization (2026-08-06). No policy documented yet.

## Key Changes

1. Document the fork's API stability commitments (what xuanji guarantees).
2. Rules for adopting breaking upstream changes (CRDs, proto).
3. Versioning scheme for custom API additions (E2B plane, Wasm config).
4. Changelog/breaking-change note process per release boundary.

## Implementation Notes

- Must align with Constitution Principle I (upstream intent preserved) and
  Principle VIII (breaking changes documented).
- Proto changes follow substrate API guidelines (cf. UpdateActorSnapshotTag
  precedent).

## Future Evolution Suggestions

- Contract tests pinning the documented API guarantees in CI.
- Client SDK generation from the stabilized proto surface.
