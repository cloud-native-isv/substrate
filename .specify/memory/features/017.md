# Feature Detail: Snapshot Storage Extensibility

**Feature ID**: 017
**Name**: Snapshot Storage Extensibility
**Description**: Pluggable snapshot storage backend abstraction so deployments can add providers beyond GCS/S3 (e.g. self-hosted object stores).
**Status**: Draft
**Created**: 2026-08-06
**Last Updated**: 2026-08-06

## Overview

Snapshot persistence (feature 003) currently ships two backends — GCS and S3 —
implemented as sibling code paths in `cmd/atelet/internal/ategcs/`. Deploying
against other object stores (e.g. self-hosted MinIO-compatible storage in
private clouds, relevant to xuanji environments) today requires code changes.
This feature proposes a clean backend interface with configuration-driven
selection.

## Latest Review

Bootstrapped from DFX gap analysis (DFS/DFCfg) during feature-registry
initialization (2026-08-06). Design not started.

## Key Changes

1. Define a snapshot-backend interface (put/get/stream, sparse zstd aware).
2. Refactor ategcs GCS/S3 implementations behind the interface.
3. Configuration-driven backend selection in atelet.
4. Conformance tests runnable against any backend.

## Implementation Notes

- Keep the change upstream-friendly where possible: a clean abstraction could
  be contributed back, unlike xuanji-only features.
- Must preserve snapshot streaming latency characteristics.

## Future Evolution Suggestions

- Local/NFS backend for air-gapped deployments.
- Backend-level encryption-at-rest configuration.
