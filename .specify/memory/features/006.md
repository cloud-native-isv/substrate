# Feature Detail: Multi-Sandbox Runtimes

**Feature ID**: 006
**Name**: Multi-Sandbox Runtimes
**Description**: gVisor (runsc) and microVM (Kata/Cloud Hypervisor) sandbox herders with checkpoint/restore for workload isolation.
**Status**: Implemented
**Created**: 2026-08-06
**Last Updated**: 2026-08-06

## Overview

The ateom family provides pluggable sandbox runtimes inside worker Pods.
ateom-gvisor runs workloads under gVisor `runsc` with checkpoint/restore for
sub-second suspend/resume; ateom-microvm runs actors as Cloud Hypervisor VMs
(Kata) with userfaultfd demand-paged restore. Consistent lifecycle operations
across sandbox types are a core design goal.

## Key Changes

1. ateom-gvisor runsc checkpoint/restore (`cmd/ateom-gvisor/runsc.go`).
2. ateom-microvm Kata + Cloud Hypervisor support with demand-paged restore.
3. SandboxConfig CRD for per-template sandbox parameters.
4. Sandbox validation config (`manifests/ate-install/sandboxconfig-*`).
5. Internal ttrpc interface between atelet and ateom (`internal/proto/`).

## Implementation Notes

- gVisor is the primary isolation boundary (Constitution: Technology &
  Platform Constraints); a temporary gVisor patch may be required — see README.
- MicroVM assets staged to rustfs for kind dev
  (`hack/microvm-assets/stage-to-rustfs.sh`).
- New sandbox types (e.g. Wasm, feature 014) must plug into the same atelet /
  ateom lifecycle contract.
