# 通用绘图原则（所有图表通用）

> **适用范围**：本文件是**图表类型无关**的核心绘图原则，适用于类图/组件图/部署图/时序图/架构图等**所有** PlantUML 图表——不只大图。大图特有的美化技术栈见 [large-diagram-playbook.md](large-diagram-playbook.md)。
> **说明**：以下均为抽象原则；文中代码为**通用示意**（用占位名如「服务 A / 主机节点 / 子系统」），不针对任何具体系统——套用时按你的领域替换。

---

## 四步执行顺序（先「对」与「达意」，再「好看」）

任何一张图，按此顺序推进，前两步定「画什么、如何达意」，后两步定「画得好看」：

1. **UML 语义正确性** — 选对图类型、用对元素种类与关系类型、补齐构造型/接口（本文 §1）。
2. **视觉语义正确性** — 位置/数量/颜色/文字量本身即在传达信息，按人类第一眼理解规划（本文 §2）。
3. **基本布局与结构** — 分组、分层/分带、主次结构成形。
4. **文字修饰** — 单独的一步：元素上只留**简洁标题**，把详细清晰的说明**外置到 note**（布局安全则加、否则省）；详见 §3。
5. **对齐 · 着色 · 线条** — 收尾美化（大图见 playbook 五步技术栈）。

> **纯绘图技巧有天花板**：当反复调布局/连线仍无实质提升，瓶颈通常在**建模（步骤1）或达意（步骤2）**，而非美化。务必先把 1、2 做对。

---

## §1 UML 语义先行（步骤 1）

绘图前先做语义分析（见 [howto/00-semantic-analysis.md](../howto/00-semantic-analysis.md)），确保 UML 定义层面最优：

1. **选对图类型**（[howto/01-choose-diagram-type.md](../howto/01-choose-diagram-type.md)）：逻辑结构/依赖→类图/组件图；物理运行时拓扑→部署图；交互时序→时序图；等等。选错类型，后续全歪。
2. **用对元素种类**（最常见错误）：不要一律 `rectangle`/`component`。按类型用其原生元素——部署图用 `node`/`artifact`/`database`/`cloud`；组件图用 `component`/`interface`/`package`；类图用 `class`/`interface`/`enum`……**元素种类本身就是语义**，混用即丢失语义、也让引擎无法正确布局。
3. **区分关系类型**：不要所有边都用同一种线。按语义选——实线关联/通信路径、虚线依赖/控制信号、`«deploy»`/`«manifest»`/`«include»` 等构造型依赖、泛化/实现/聚合/组合各有记号。
4. **构造型与多重性**：用 `«stereotype»` 表达种类/角色/部署方式，用多重性（`1..*`、`«×N»`）表达数量关系，让模型自解释。
5. **补齐缺失构造**：为对外契约加 `interface` 棒棒糖 `()` 与端口——只加提升保真度且不增杂乱的部分。

## §2 视觉语义（人类视角，步骤 2）

UML 语义保证「正确」，读者的**第一眼理解**还依赖**视觉语义**——位置、数量、颜色、文字量本身在传达信息。UML 正确后、动手绘图前，先按人类视角规划：

1. **角色即位置**：按元素在系统中的角色决定空间位置，而非任由引擎摆放。中心/枢纽放**中心偏上**、从属/边缘沿**边/底部依次**；入口在一侧、汇聚在另一侧（Hub/Edge/Entry/Sink）。
2. **一对多（1:N）关系的表达**：当「一类 vs 另一类」的数量关系重要时（如 1 主控 : N 从属实例、1 网关 : N 后端），要让 1:N 被看见——但**表达法有讲究**：
   - **「一」**：详绘为**单个具体元素**（完整内部结构），作为该类的代表。
   - **「多」**：**不要画 N 份同级副本**。多个兄弟盒子会打乱对齐、撑乱结构、无谓增宽画布。改用**单一代表元素 + 多重性标注**表达「多」，手段按强弱：
     1. `collections`（原生**堆叠多框形**，UML 惯用"多实例"字形）——注意：在**部署图**中 `collections` **无法嵌套子元素**，只适合无内部结构的"多"。
     2. **堆叠阴影 motif**：给单个元素加 `Shadowing`（局部 `<style>` 类）制造"一叠 N 个"的观感，且能保留内部详绘——需要展示内部结构时的首选。
     3. **`«×N»` / "×N" 标签 + legend 一行**说明（"N 个同构对等，图示其一"）——最轻量。
   - **判据**：读者应看出"这是 N 个同构实例"，而画布上只有**一个**（堆叠/标注的）盒子——不因 N 而增加对齐负担。这与 [large-diagram-playbook.md](large-diagram-playbook.md) §1 的「×N 折叠」同源：折叠是呈现压缩、不是信息删除。
3. **关联即同色**：同一逻辑子系统用**同一色相族**（深浅随嵌套层级变化），让读者**前注意（pre-attentive）**地把相关元素归为一组。语义关键边用深色粗线，确保在色块上仍醒目。**色相承载语义，而非装饰。**
4. **分组即框选（容器分组）**：同类/同组元素除同色外，再用一个**共同的框架元素**框选，形成色彩之外的第二重分组信号（容器边界是比颜色更强的分组线索，尤其利于大图分区）。两档用法：
   - **宏观逻辑分区**用**可见命名框**——把一个逻辑子系统装进具名 `frame`（如 `frame "子系统 A"`），让分区一眼分明。
   - **同类细分组**用**不可见框**——透明边/背景的 frame（`<<invis>>` + `<style> .invis { LineColor transparent; BackGroundColor transparent; FontColor transparent; LineThickness 0 }`），把「多个对等副本」「一群同类外部元素」等无需标题的同类项**框选对齐但不增可见盒子/连线**。这是「同类共用一个副元素框选，副元素可不可见」的落地。
   - 注意：分组框是**容器**（与浮动 `note` 不同，不会被引擎甩到页边），但仍是嵌套层级——勿过度嵌套撑大画布；分区应服务于「角色即位置」（如枢纽框居上、从属框在下）。
5. **文字即负担**：密集文字既拥挤、又在渲染不佳时给读者压力。能用图元/形状/颜色/图标传达的，就不用文字——见 §3。

## §3 文字修饰步骤：简洁标题（在元素上）+ 外置 note 详解

**「文字修饰」是独立的一步**（执行顺序第 4 步）。目标：既**简洁**（画布不拥挤）又**表意清晰**（读者看得懂含义）。两个部分分工明确：

### 3.1 元素上：只放一个「很简洁的标题」
图元的文字标签只承载「最小可识别身份」——认出「这是什么」所需的最短名称（含必要区分词，如带限定的「订单查询服务」而非泛化的「服务」）。一切说明性/限定性信息（职责、协议、端口、部署方式、组成、约束）都**不进标签**。先做去重：
- **去重 → 直接删除**：若信息已由相邻图元表达——`interface` 棒棒糖（协议/端口）、`«stereotype»`（种类/部署）、嵌套容器（归属）——则从标签删除（零成本、除冗余）。
  - 例：`component "服务 A\n<协议·鉴权等描述>"` → `component "服务 A"`（协议由下方 `interface` 承载）。

### 3.2 元素外：用外置 `note` 做「足够详细而清晰」的说明
被剥离的说明不要塞回标签，也不要压缩成看不懂的碎片（这会「不简洁」又「表意不清」两头不讨好）。改为**外置 note 详解**：
- 对**确需解释、含义不能从标题+颜色+构造型一眼看出**的元素，挂一个 `note`（`note left/right/top/bottom of X` 或 `note as N`+`X .. N`），用**完整清晰的语言**写足含义（不是电报式碎片）。相邻 note 比远处 legend 更易读懂——读者在元素旁就看到解释。
- **布局安全是硬约束**：外置 note **不得扰乱整体布局**。渲染后必检：若 note 被引擎甩到远边、引出长交叉连线、或撑乱版面 → **删掉该 note**（必要时省略）。宁可省略，不可伤布局。
  - **嵌套簇经验**：note 只在**顶层/贴白空**的元素上可靠；挂在**深层嵌套成员**上常被甩到页边并拉长连线 → 对深层成员**省略 note**，把其说明**折叠进父级元素的 note** 或 **legend**。
- **选择性**：只修饰含义不明的元素，**不要每个盒子都挂 note**（note 泛滥同样是噪声）。note 数量宜少（如 ≤ 5）。
- **兜底顺序**：贴身 note（布局安全时·首选，最清晰）→ 折叠进父级 note / legend（note 不安全时）→ 都不合适则仅留简洁标题。

### 3.3 字号与字体一致（图内 + 跨图集）
文字「看起来不一致」多半不是内容问题，而是**字号/字体没统一**：
- **用 skinparam 的 per-kind 字号按「四级字号阶梯」集中设定**：定一个基准字号 `B`（正文可读下限，13–15），按语义层级套倍率——**T1 标题** `TitleFontSize`≈1.5×B(+`TitleFontStyle bold`)、**T2 容器** `node/frame/rectangle/packageFontSize`≈1.0×B、**T3 成员** `component/artifact/database/actorFontSize`≈0.9×B、**T4 附注** `note/legend/Arrow/StereotypeFontSize`≈0.8×B。**相邻阶梯至少差 1pt**（差 0 则层级消失、显得「字号无规律」），**T1↔T2 拉到 ≥1.4×** 让标题跳出；**只留四档**，其余元素种类归入语义最近一档、不新增第五档（档位越少越像「统一排版系统」）。一处定义、全图一致。
- **不要用零散的内联 `<size:N>` 或 `**bold**` 逐元素装饰**——那让同一张图字号忽大忽小、粗细不一，是「文字大小看起来不一致」的头号成因。加粗只留给标题（`TitleFontStyle bold`）与个别 callout，且全图集用法一致（含 note/legend 内的强调也要跨图统一）。
- **跨图集一致**：一组图共用**同一套 per-kind 字号**与同一字体族（承 §4.3 图集共享词汇）——同类元素在每张图字号相同，风格才统一。
- **工具注意**：有的渲染管线会强制 `defaultFontSize`/`defaultFontName`；但 per-kind 的 `*FontSize` 通常可在其上**覆盖生效**——层级就用这些设，不必与被强制的基准较劲。

- **判据**：读者用「简洁标题(图元) + 形状/颜色(种类) + 接口(契约) + stereotype(部署) + 外置 note/legend(详解)」应能**重建全部信息**，而画布上每个盒子只剩一个短标题、详解在旁而不挤。
- **可选增强**：用 OpenIconic `<&icon>` 给标题加一个种类图标（`<&cog>`服务、`<&hard-drive>`存储、`<&box>`制品、`<&person>`actor…），以符号强化——冗余编码，小尺寸收益有限，按需采用。

## §4 从上下文出发 · 减法 · 拆分为图集（面对海量信息时）

UML 是描述性语言，**脱离实际程序上下文则无意义**。当输入是一份大文档/一套代码/大量描述时，绘图不是「把信息塞进画布」，而是**从上下文提炼、做减法、必要时拆分为一组图**。

### 4.1 上下文驱动（绘图前）
- 画任何 UML **前先吃透上下文**——文档、代码、用户描述。先产出一份**紧凑上下文摘要**（组件、关系、核心流程、关键决策，附出处/节号），后续绘图与评审都对着它，保证**程序整体正确性**、不臆造。
- 上下文决定图类型与元素种类（见 §1）；同一系统，面向不同读者/问题，画的图不同。

### 4.2 减法优先（整洁美观 > 面面俱到）
- **每张图只表达一个核心点**。与该核心点无关的元素一律不画，用交叉引用移走（`▶ 见 图N`）。
- 面对海量信息，**在「面面俱到」与「整洁美观」之间，优先整洁美观**——一张让读者一眼抓住核心的图，胜过一张塞满全部细节、谁都读不动的图。
- 反例判据：当 legend 要写十几行替图说话、或一张图既当索引又当细节、或多族连线跨区交叉不可追踪时，说明**没做减法**，该拆。

### 4.3 严谨拆分为「图集」（单图表达不下时）
当一个核心点撑不下全部含义，**基于程序架构拆分为多张图**，而非硬塞一张：
- **按架构接缝拆**：如分层、控制面/数据面、静态结构/行为时序、请求流/制品流、系统边界/节点内部——沿系统本身的自然缝切，而非随意切。**若判断某图会因内容过多而结构散乱，即为拆分点**。
- **每图自足**：单看一张即可获取足够信息——带一句定位 caption（说明它在整体中的位置）、最小 legend、足够标注可独立读懂。
- **图间有层次与关联**：一张**概览/索引图**在顶（刻意稀疏，只给全景与入口），其余为其下钻的子图；父→子关系清晰。每图用统一**交叉引用**（`▶ 见 图N`）把被移走的细节指向对应子图，并用统一**页脚**（`第 N/M 图 · 全景见 图1 · <本图核心>`）标明其在图集中的位置。
- **共享稳定词汇**：编号通道（①②③…）、颜色族、构造型在**全图集含义一致**，读者的词汇表跨图稳定。
- **警惕记号冲突**：同一套编号/字母在一张图里**只指一类事物**。若通道用 ①②③，则隔离维度、时序阶段等**另用一套记号**（Ⓐ/Ⓑ… 或不同符号），避免同符异义。

> 判据：读者从**概览图**把握全局，再进**任一子图**获得一个自足的子故事；没有哪张图既是索引又是细节。「一张塞满的详图 = N 张图的平均，因而哪张都不是。」
