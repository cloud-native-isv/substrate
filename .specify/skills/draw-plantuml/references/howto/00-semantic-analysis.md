# 语义分析与意图理解

> 在选择图表类型（Step 2）之前，先分析和理解用户的绘制意图，确保绘图内容准确、完整。本指南是 [SKILL.md Step 1](../../SKILL.md) 的详细参考。

---

## 一、意图分类与识别

### 1.1 四种输入类型

| 类型 | 识别信号 | 典型示例 |
|------|---------|---------|
| **直接描述型** | 用户提供清晰文字描述，包含系统组件、流程或结构信息 | "画一个微服务架构图，包含 API 网关、用户服务、订单服务、支付服务" |
| **图片复刻型** | 用户引用图片文件，要求重绘或复刻 | "复刻 arch.jpg 的内容，用 plantuml 重新绘制" / "把这个架构图重画一下：diagram.png" |
| **模糊/不完整型** | 描述简短、模糊或缺少关键信息 | "画个系统图" / "帮我画个架构" / "画一下那个流程" |
| **代码可视化型** | 用户提供源代码，要求可视化其结构 | "根据这段代码画个类图" / "把这个微服务的调用关系画出来" |

### 1.2 识别决策流程

```
用户输入 →
  ├─ 包含图片文件路径/引用（.jpg/.png/.webp）？ → 图片复刻型
  ├─ 包含源代码块或代码文件引用？              → 代码可视化型
  ├─ 描述长度 < 20字 且 缺少具体组件/流程？     → 模糊/不完整型
  └─ 其他                                     → 直接描述型
```

> **注意**：一个请求可能同时属于多种类型（如"根据这段代码画个图"既是代码可视化型又可能是模糊型）。此时按优先级处理：图片复刻 > 代码可视化 > 模糊 > 直接描述，并综合提取信息。

## 二、内容提取策略

### 2.1 直接描述型

从用户文字描述中提取以下信息：

| 信息项 | 说明 | 提取方法 |
|--------|------|---------|
| **系统边界** | 哪些是系统内部，哪些是外部 | 识别"系统"、"外部"、"用户"等边界词 |
| **核心元素** | 组件、服务、模块、角色、类 | 识别名词性实体（服务名、模块名、角色名） |
| **关系类型** | 依赖、调用、包含、继承、消息 | 识别动词和关系词（"调用"、"依赖"、"继承"、"发送"） |
| **交互流程** | 请求链路、数据流向 | 识别顺序词（"先...然后..."、"请求到达后"） |
| **技术栈** | 框架、中间件、协议 | 识别技术名词（K8s、Redis、HTTP、gRPC） |

### 2.2 图片复刻型

当用户要求复刻/重绘图片时，按以下步骤处理：

#### 步骤 1：读取图片

使用 `Read` 工具读取图片文件路径（支持 jpg/jpeg、png、webp 格式）。读取后获取图片的视觉内容进行理解。

**如果图片路径不存在或无法访问**：
- 告知用户图片无法读取
- 请用户提供文字描述或更换图片
- 不要凭空猜测图片内容

#### 步骤 2：识别原图表类型

从图片视觉特征判断原图类型：

| 视觉特征 | 对应图表类型 |
|---------|------------|
| 方框 + 连线，展示静态结构 | 组件图 / 类图 / 包图 / 部署图 |
| 带生命线的方框 + 水平箭头 | 时序图 |
| 泳道 + 流程节点 + 菱形判断 | 活动图 |
| 圆角状态节点 + 转换箭头 | 状态机图 |
| 人形图标 + 椭圆用例 | 用例图 |
| 服务器/节点图标 + 网络连线 | 部署图 |

#### 步骤 3：提取视觉元素

按以下顺序从图片中提取信息：

1. **全局结构**：先看整体布局（层次结构？流程走向？网格布局？）
2. **分组容器**：识别框、区域、泳道、包等分组结构
3. **节点元素**：识别所有方框、圆圈、角色图标、数据库图标等
4. **连线关系**：识别箭头方向、线型（实线/虚线/粗线）、标签文字
5. **文本标签**：读取所有文字内容（元素名、关系标签、注释）
6. **视觉层级**：颜色/粗细/大小差异暗示的重要性和层次

#### 步骤 4：映射到 PlantUML 元素

| 图片中的视觉元素 | PlantUML 对应 | 适用图表 |
|----------------|--------------|---------|
| 方框 + 标签 | `component` / `rectangle` | 组件图 |
| 服务器/节点图标 | `node` | 部署图 |
| 人形图标 | `actor` | 用例图 / 时序图 |
| 带生命线的方框 | `participant` | 时序图 |
| 类框（含属性/方法） | `class` | 类图 |
| 数据库图标 | `database` / `storage` | 部署图 / 组件图 |
| 大框包含小框 | `package` / `frame` 嵌套 | 所有结构图 |
| 实线箭头 | `-->` | 所有图表 |
| 虚线箭头 | `..>` | 所有图表 |
| 粗线箭头 | `==>` | 所有关键路径 |
| 泳道 | `\|lane\|` | 活动图 |

### 2.3 模糊/不完整型

当用户描述过于简短或模糊时，**不要直接开始画图**。先进行差距分析（见第三节），然后通过交互式确认补充信息。

**必填信息清单**：

| 信息项 | 说明 | 缺失时的影响 |
|--------|------|------------|
| 系统名称/主题 | 要画的是什么系统 | 无法确定标题和范围 |
| 图表目的 | 架构总览？流程展示？类结构？ | 无法选择图表类型 |
| 核心元素 | 有哪些组件/参与者/类 | 图表内容为空 |
| 关系/交互 | 元素之间如何关联 | 图表缺乏意义 |
| 细节程度 | 草图模式？蓝图模式？ | 影响详细程度和元素数量 |

### 2.4 代码可视化型

分析代码提取结构信息：

| 代码特征 | 提取内容 | 推荐图表 |
|---------|---------|---------|
| 类/接口定义 | 属性、方法、继承关系 | 类图 |
| 模块/包导入 | 依赖关系、层级结构 | 包图 |
| 服务/组件注册 | 组件边界、接口定义 | 组件图 |
| 服务间调用 | 调用链路、消息类型 | 时序图 |
| 状态变更逻辑 | 状态节点、转换条件 | 状态机图 |
| 业务流程代码 | 活动步骤、分支条件 | 活动图 |
| 部署配置（Docker/K8s） | 节点、容器、网络 | 部署图 |

## 三、差距分析与交互式确认

### 3.1 何时需要交互式确认

在以下情况下**必须**使用 `AskUserQuestion` 工具向用户确认：

1. **模糊输入**：用户描述 < 20 字且缺少关键信息（系统名称、核心元素、图表目的）
2. **图片不清晰**：图片中的元素或关系无法明确识别
3. **多义性**：用户描述可对应多种图表类型，无法确定唯一选择
4. **范围不清**：无法确定系统边界或图表范围（画整个系统还是某个模块？）
5. **关系模糊**：元素之间存在但关系类型不明确（是调用还是依赖？是同步还是异步？）
6. **图片缺失关键信息**：图片模糊、文字不清、部分区域被遮挡

> **原则**：宁可多问一轮，也不要画错方向。但每轮提问不超过 4 个问题，避免反复追问导致用户疲惫。

### 3.2 交互式确认问题模板

#### 模板 A：模糊输入确认

```
问题1: 您想绘制什么类型的图表？
- 组件图（展示服务/模块组成与依赖）
- 时序图（展示交互流程与消息）
- 部署图（展示物理拓扑与节点）
- 类图（展示代码结构与继承关系）

问题2: 图表的核心主题/系统名称是什么？
（用户通过 Other 选项自由输入）

问题3: 需要展示哪些核心组件或服务？

问题4: 图表的详细程度？
- 草图模式（快速沟通，非正式，≤7 元素）
- 蓝图模式（详细设计文档，可接受 ≤12 元素）
```

#### 模板 B：图片复刻确认

```
问题1: 图片中的图表类型是什么？（如已从图片识别，用于确认）
- 组件图
- 部署图
- 时序图
- 活动图

问题2: 图片中有哪些核心元素需要保留？
（用户通过 Other 列出或确认提取的元素列表）

问题3: 是否需要调整或简化原图内容？
- 完全复刻（1:1 还原所有元素和关系）
- 简化（去除次要元素，聚焦核心结构）
- 增强（补充原图缺失的关系或注释）
```

#### 模板 C：多义性确认

```
问题1: 您更想表达系统的哪个方面？
- 静态结构（组件组成、模块划分）
- 动态行为（交互流程、状态变化）
- 物理部署（服务器、网络拓扑）

问题2: 图表的范围是什么？
- 系统全景（所有核心组件）
- 单个子系统（某个服务的内部结构）
- 特定流程（某个业务场景的交互）
```

### 3.3 确认后的意图总结

在开始 Step 2（选择图表类型）之前，向用户输出一份简短的意图总结进行最终确认：

```
📋 绘图意图确认
━━━━━━━━━━━━━━━━━━━━━━━━
• 系统主题: [确认的主题/系统名称]
• 图表目的: [架构总览 / 流程展示 / 类结构 / ...]
• 核心元素: [元素1, 元素2, 元素3, ...]
• 关系/交互: [关系1, 关系2, ...]
• 细节程度: [草图 / 蓝图]
• 特殊要求: [如有，如"复刻原图布局"、"标注技术栈"等]
━━━━━━━━━━━━━━━━━━━━━━━━
```

如果用户确认无误，继续进入 Step 2。如果用户有修改，更新意图后再继续。

> **当用户输入已经足够清晰和完整时**，可以跳过交互式确认，直接输出意图总结并进入 Step 2。不要对清晰的输入进行不必要的提问。

## 四、图片分析最佳实践

### 4.1 图片读取注意事项

- 使用 `Read` 工具直接传入图片文件的绝对路径
- 支持格式：jpg/jpeg、png、webp
- 读取后会获取图片的视觉内容进行理解
- 如果图片路径不存在，会返回错误 — 此时需要告知用户

### 4.2 元素识别策略

从图片中提取信息时，遵循"从宏观到微观"的顺序：

1. **全局结构**：先看整体布局
   - 层次结构？→ 可能有嵌套关系
   - 流程走向？→ 可能是时序图或活动图
   - 网格布局？→ 可能是部署图
2. **分组容器**：识别框、区域、泳道
   - 大框包含小框 → package/frame 嵌套
   - 水平分区 → 泳道或分层架构
3. **节点元素**：识别所有方框、圆圈、角色等
   - 记录每个元素的名称和类型
   - 注意图标样式（数据库图标、服务器图标等）
4. **连线关系**：识别箭头方向和线型
   - 实线 → 数据流/强依赖
   - 虚线 → 控制信号/弱依赖
   - 箭头方向 → 关系方向
5. **文本标签**：读取所有文字
   - 元素名 → PlantUML 元素 alias
   - 关系标签 → PlantUML 关系 label
   - 注释文字 → PlantUML note

### 4.3 图片复刻 vs 原创绘图

| 方面 | 图片复刻 | 原创绘图 |
|------|---------|---------|
| 元素来源 | 从图片提取 | 从用户描述提取 |
| 布局 | 尽量还原原图的空间关系 | 根据 Step 4 布局规划 |
| 图表类型 | 识别原图类型，除非用户指定改变 | 根据 Step 2 选择 |
| 关系 | 从图片连线提取 | 从用户描述提取 |
| 质量目标 | 准确还原原图信息 | 清晰表达用户意图 |

> **图片复刻不是像素级复制**：目标是理解原图的设计意图和结构信息，用标准 UML 语义重新表达，而非逐像素还原。关注的是信息准确性和可读性，不是视觉相似度。

## 五、注意事项

- **不要跳过语义分析直接画图**：即使用户描述看似清晰，也应快速验证关键信息是否完整
- **交互式确认要高效**：最多一轮提问（≤4 个问题），避免反复追问让用户疲惫
- **图片复刻要忠实**：理解原图的设计意图，用标准 UML 语义重新表达，不要遗漏关键元素
- **保留用户原始意图**：如果用户明确要求某种画法，不要自作主张更改
- **区分"模糊"和"简洁"**：用户可能只是想要一个简单的草图，这不等于"模糊" — 简洁的输入如果意图明确，可以直接执行
