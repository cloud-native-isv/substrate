# draw-plantuml 最佳实践（Best Practices）

> 从 viz-skill-arena 竞技 cycle（Substrate 架构图，2026-08-07）的 R1 评审建议与重绘改进中沉淀。draw-plantuml 两轮均为架构图类任务冠军（0.89 → 0.90），以下实践保持其优势并补足短板。配套陷阱见 [pitfalls.md](pitfalls.md)。

## 1. 需求清单逐项映射 UML 图型（防漏交付）

PlantUML 原生图型全，先列需求清单再逐项映射，不要只画「顺手」的图：

| 需求类型 | PlantUML 图型 |
|----------|---------------|
| 状态机 | 独立 `state` 图（不要只在序列图底部放文字 note——R1 点名） |
| 双层资源模型（声明层 ↔ 动态层） | 独立 `package` 分层图 |
| 组件/部署/序列 | `component` / `deployment` / `sequence` |

## 2. 多域结构用 package/rectangle 显式分组

组件嵌套表达分组语义偏弱（R1：*"worker Pod 用 component 嵌套表达分组语义偏弱，建议改用 package/rectangle 显式分组并加分组标签"*）。多命名空间/多节点/多层级时：

- 用 `package` 或 `rectangle` 显式分组，并给分组加标签（namespace 名、节点名）；
- 分组内组件按「入口 → 枢纽 → 出口」排列，减少长连线。

## 3. 部署图标注 namespace 与关键机制细节

部署图语义精度提升点（R1 实测有效）：

- 标注 namespace 名（如 substrate-system 控制面 / substrate-worker 工作节点）；
- 关键机制细节入 note（如 microVM 恢复的 userfaultfd OnDemand、隧道 mTLS 端口）；
- 网络/证书关系用显式虚线（如身份体系 → 各组件的证书签发）。

## 4. 信息密度控制：note 精简或拆子图

部署图每个组件都挂 note 会整体拥挤（R1：*"部署图信息密度极高，整体拥挤"*）。控制办法：

- 每个组件 note 精简为「端口 + 职责」两行；
- 仍拥挤 → 拆分为控制面/Worker 节点两张子图。

## 5. 序列图关键路径高亮

序列图 `group/alt/opt` 区块颜色与 `activate` 层次对比度一般时，给关键路径（如 Resume 工作流）加高亮色块，提升视觉引导（R1 建议）。

## 6. HTML 内嵌 puml 源码与渲染命令（可复现）

HTML 交付物内嵌：`.puml` 全文 + `render-plantuml.sh` 调用命令。评审要求 *"HTML 内附渲染命令与依赖说明"*——源文件自包含 + 渲染命令文档化是可复现性满分的核心。

## 7. 状态机人工介入态显式标注

状态机中不可自动恢复的状态（如 CRASHED）要显式标注「人工介入」语义，避免读者误解为自动迁移路径（Substrate 案例：物理失败不自动补偿）。

## 8. 图例与配色在 SVG 内自包含

组件图在 SVG 内嵌 legend（`legend right` + 色块说明），颜色是语义通道：同子系统同色相、跨子系统不同色相（R1 认可重绘版图例改进）。

## 9. 图文口径一致 + 旧架构显式标注时间点

图内组件/部署形态与配套 HTML 叙述必须**同一口径**（R1 实测：HTML 称「XX 以 DaemonSet 形态运行」而图内画成普通节点内组件，被判架构矛盾）。画旧架构/过渡期状态时在图内显式标注「旧架构」或时间点（如 `per-tenant Etcd（旧架构）`），不把新旧口径混在同一张图。

## 10. 省略即声明（完整性声明）

图有意省略部分组件（DNS、网络插件、证书控制器等集群面组件）时，用一句 `caption` 显式声明「仅绘制核心载体」或列明省略项，避免「没画」被读成「不存在」、部署形态被误读为完整。

## 11. 图内可承载的映射/状态不落 caption

演进/合并映射（旧组件→新组件）、生命周期阶段等**能用图内元素表达的信息画进图内**（`..>` 映射连线、`== 阶段 ==` 分隔线），caption 只留定位短句——R1 多次点名「仅出现在 caption 文字里」的表达方式不可靠。
