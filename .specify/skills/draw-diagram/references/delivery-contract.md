# Delivery Contract — 交付形态与文字规则（七技能统一）

本文件是**交付形态与面向用户的文字**的唯一权威（One Source Of Truth）。七个绘图技能（前门 `draw-diagram` + 六引擎）在交付时一律遵守；各引擎 SKILL.md 的「输出要求 / Output Requirements」只写**本引擎的机械细节**（模板、脚本、路径），MUST NOT 复写本文的规则，只给指针。

**为什么归语义层**：「交付成什么形态」「给用户的话该怎么写」是**面向用户的表达决策**，与用哪个引擎无关；引擎只负责兑现。故 owner 在前门，不在六家各写一份。

---

## D1 自足 HTML（每次交付必备）

每次绘图交付 **MUST** 含**一个可直接打开的 HTML 文件**：用户双击即可在浏览器里看到图，无需安装工具、无需联网、无需先打开源文件。

- 图在页面**主体**位置，尺寸以能读清正文文字为准（各引擎的有效字号量测规则见其自有 guide）。
- 图片以**同目录相对路径**引用；MUST NOT 只给一个在线渲染服务 URL 当作交付。
- 页面语言与用户一致（用户用中文提问 → 页面中文）。

**统一样式（owner：[`../assets/delivery.css`](../assets/delivery.css)）**

七技能交付的 HTML 共用一份样式，用户无论从哪个引擎拿到图，观感一致：

- 页面样式 MUST **逐字节内联**进 `<style>` 块 —— 从磁盘上的 `delivery.css` 复制，不凭记忆重写、不改写数值；MUST NOT 用 `<link>` 外链（外链会让 HTML 单独打开时失去样式，违反「自足」），也 MUST NOT 引用任何在线字体或 CDN 样式（违反「无需联网」）。
- 分工边界：该表只管**页面骨架**（背景、卡片、标题、正文、图框、复现性附录、暗色模式、打印）；**图表内部**的样式（d3 的 `.axis` / `.tooltip`、ECharts 的 option 配色等）归各引擎自己，写在该表之后即可，MUST NOT 反向覆盖骨架的排版变量。
- 该文件头部的注释即**期望的页面结构**：类名可省略，只写语义标签（`main` / `h1` / `figure` + `figcaption` / `section` / `details`）也有完整样式 —— 没有模板的引擎据此组装即可，不必自带 `template.html`。
- 交付的图片**默认保持原尺寸、溢出时横向滚动**，不等比缩小（把 760px 的图压到手机宽度，图上文字会小到不可读，与「尺寸以能读清正文文字为准」冲突）；确需缩小时（小图、缩略图）给 `figure` 加 `class="fit"`。

## D2 源文件与渲染图一并保留

HTML 是**入口**，不是唯一产物。同一次交付 MUST 在**同一目录**保留：

| 引擎 | 源文件（可再编辑） | 渲染图 | 说明 |
|------|-------------------|--------|------|
| `draw-plantuml` | `.puml` | `.svg` + `.png` | 二者都必须产出（PNG 供速览，SVG 供无损放大） |
| `draw-mermaid` | `.mmd` | `.svg` + `.png` | 同上 |
| `draw-excalidraw` | `.excalidraw` | `.svg` + `.png` | 场景 JSON 是可拖回继续编辑的白板源文件 |
| `draw-drawio` | `.drawio` | `.svg` / `.png` / `.pdf` | 未压缩 mxGraph XML；导出图与源文件同目录 |
| `draw-d3js` | `.html`（源即产物） | 图内联于 HTML | split 模式下另留 `data.js`/`data.json` 与本地 `vendor/d3.v7.min.js` |
| `draw-echarts` | `.html`（源即产物） | 图内联于 HTML | 另留 `config.json`/`config.js` 与本地 `vendor/echarts.min.js` |

**通用要求**：

- 源文件 MUST 保留「以供未来编辑」——不得只交图片而丢掉可再生成的源。
- HTML 内若附「复现性附录」（可折叠 `<details>`），其中的源码 MUST 与磁盘上**实际用于渲染的那份源文件逐字节一致**（含脚本注入的样式块），不得凭记忆重写。
- 图片与 HTML **同目录**、相对路径引用；嵌入 Markdown 文档时 PNG 与 SVG 的引用**须走同一机制**（各引擎「输出要求」已给出具体写法）。

## D3 文字规则：without jargon, with context

**适用范围：图内文字（标签、注释、图例）与 HTML 说明文字，二者同规。**

- **without jargon（不用行话）**：MUST NOT 使用只有作者或工具链才懂的缩写、内部代号、框架黑话、未展开的首字母缩略词。确实必须使用某个专有名词时，**在首次出现处用一句用户能懂的话说明它在这里指什么**。
  - 反例：`K8s CNI 侧挂 eBPF TC hook`
  - 正例：`容器网络插件在流量出入口处挂了一段自定义处理逻辑（eBPF），用于在不改应用的前提下改写转发规则`
- **with context（带上下文）**：每个名词都要让读者知道它**在这个系统里扮演什么角色**，而不是给一个孤立标签。标签写「网关」不如写「入口网关：外部请求的唯一进入点」。
- **判据**：把图与说明给一个**没参与过这次绘制、但了解用户业务**的人看，他能否不问人就说出「这是什么、谁调谁、为什么这样分」。不能 → 不合格。
- 图内标签的**长度与格式**约束（如 ≤10 字符、注释策略、标识符规范）owner 是各引擎的 `references/guide/content.md`（mermaid 与 plantuml 各有一份且**已分化**，不是同一文件），本文不复写。

## D4 文字 MUST NOT 描述图表本身

**图应当自说明。** HTML 说明文字与图内注释都 **MUST NOT** 解释图的画法或视觉编码：

- 禁止图例式解说：「椭圆代表用例」「方框代表对象」「箭头表示调用关系」「虚线框表示边界」。
- 禁止描述视觉编码：「红色表示关键路径」「线越粗表示越重要」「灰色的是外部系统」。
- 禁止把图里已画出的结构再罗列一遍当作说明（「本图包含 A、B、C 三个模块，A 连接 B……」）。

**理由**：这类文字与图**冗余**，读者要在图与文字之间来回对照，反而增加理解成本；且一旦图改动，这类描述立刻过期。

**例外与归位**：某种视觉编码确实不自明、不说明就会误读时 → 把说明做进**图内的 legend**（图例块），让解释与图同生共死；**不写进 HTML 正文**。legend 的画法 owner 是各引擎的 guide（如 `large-diagram-playbook.md` 的「legend 作单一细节仓」）。

## D5 正文说明 MUST 用用户原始上下文的术语描述架构或流程

HTML 说明文字讲的是**系统本身**，不是**这张图**：

- 用**用户自己文档/代码/提问里的名字**称呼组件与角色，不另造一套术语，也不把用户的叫法翻译成工具术语。
- 内容聚焦：这个系统**怎么工作**、**为什么这样分层**、**这条链路依次经过谁**、**哪个环节是瓶颈或单点**、**这次要解决的问题出在哪**。
- 用户给了上下文（文档、代码、目标图）→ 说明文字 MUST 与该上下文一致并**带出处**，不臆造未出现在上下文里的组件或关系。
- 一次交付若含多张图，正文按**图的顺序**组织，每张图配一段讲该视角下的架构/流程；跨图的编号与词汇保持一致。

## D6 交付前自检（可机械核对）

| # | 检查项 |
|---|--------|
| 1 | 存在一个可直接打开的 HTML，离线可看图（D1） |
| 2 | 源文件在盘、与 HTML 同目录，扩展名符合 D2 表 |
| 3 | 该引擎要求的图片格式**全部**产出（plantuml/mermaid/excalidraw 须 SVG **与** PNG 同时在） |
| 4 | HTML 相对路径引用图片，无绝对路径、无仅在线 URL 的交付 |
| 5 | 复现性附录内的源码与磁盘源文件**逐字节一致** |
| 6 | 全文（图内 + 说明）无未解释的行话/缩写/内部代号（D3） |
| 7 | 关键名词都带「在本系统中的角色」（D3） |
| 8 | 说明文字中**零**图例式解说、零视觉编码描述、零结构罗列（D4） |
| 9 | 说明文字讲的是架构/流程，用的是用户原始术语（D5） |
| 10 | 说明文字与用户给的上下文一致、无臆造成分（D5） |
| 11 | 页面 `<style>` 与磁盘上的 `assets/delivery.css` **逐字节一致**（内联，非 `<link>` 外链、无在线字体/CDN 样式）（D1） |
