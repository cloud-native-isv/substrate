# 绘图通用原则（diagram-principles）

> 图表类型无关的核心原则，适用于本技能的全部图表（UML 图与专项图）。这是「方法论总纲」四支柱的单一事实来源；工作流每一步都服从本节。

## 0. 执行顺序总纲

**先「对」与「达意」，再「好看」**，按固定顺序执行四步：

1. **UML 语义先行**（§1）——选对图类型、元素种类、关系类型、构造型、接口；
2. **视觉语义规划**（§2）——按人类视角规划角色位置、数量、色彩、分组；
3. **文字修饰**（§3）——元素上只留简洁标题，详细说明外置到注释；
4. **收尾美化**——对齐、着色、线条治理、大图专项（见 large-diagram-playbook）。

**任何一步都不允许跳到第 4 步**：先画「对」的图，再画「好看」的图。

---

## 1. UML 语义先行（选对类型与元素）

UML 脱离语义就是一堆方框。绘图前必须回答四个问题：

### 1.1 图类型对不对

| 想表达什么 | 正确的图类型 |
|-----------|-------------|
| 对象间的消息交互顺序 | `sequenceDiagram` |
| 类的静态结构/关系 | `classDiagram` |
| 对象生命周期/状态转换 | `stateDiagram-v2` |
| 业务流程/工作流 | `flowchart`（活动语义） |
| 实体与基数 | `erDiagram` |
| 进度/依赖/里程碑 | `gantt` |
| 层级分解/发散 | `mindmap` |
| 系统上下文/容器/组件/部署 | `C4Context` / `C4Container` / `C4Component` / `C4Deployment` |

错误示范：把「调用顺序」画成 flowchart 直线、把「状态机」画成 flowchart 菱形链——语义被抹平，读者无法区分「时序」「状态」「流程」。

### 1.2 元素种类对不对

- `classDiagram`：类、抽象类、接口、枚举、属性、方法——**元素种类本身即语义**；
- `stateDiagram-v2`：状态、初态 `[*]`、终态 `[*]`、复合状态、choice、fork/join；
- `flowchart`：圆角矩形（动作）、菱形（决策）、圆柱（数据/存储）、subgraph（边界/容器）——勿一律用矩形；
- `erDiagram`：实体、属性、主键 PK、外键 FK；
- `sequenceDiagram`：participant / actor、生命线、激活条。

### 1.3 关系类型对不对

- 类图：泛化 `<|--`、实现 `..|>`、组合 `*--`、聚合 `o--`、关联 `-->`、依赖 `..>`——**六种关系不可混用**；
- 状态图：`-->` 转换（可带 `: 事件[守卫]/动作`）；
- ER 图：乌鸦脚基数 `||--o{`、`}|--|{` 等，**数量语义必须显式**；
- 时序图：`->` 同步、`-->>` 异步、`--x` 失联/返回等箭头语义。

### 1.4 构造型与接口

- `classDiagram` 用 `<<interface>>` / `<<abstract>>` / `<<enumeration>>` 标注构造型；
- 对外契约（API、端口、队列）在类图/组件图中用接口节点 + `..|>` 表达「实现」，勿用普通依赖箭头。

## 2. 视觉语义（人类视角）

### 2.1 角色即位置

- 枢纽（Hub）居中偏上；边缘参与者沿边/底部；
- Entry（入口）在左上、Sink（终点）在右下；
- 位置传达角色，读者无需读标签即知谁是谁。

### 2.2 数量表拓扑：一对多用「单代表 + 多重性」

N 份兄弟盒是版面杀手。规则：

- 同一逻辑单元画**一个代表元素**，标注 `«×N»` 或 `×N`；
- 类图/ER 图用多重性标注（`1` / `*` / `0..*`）；
- 不画 N 份相同的盒、不画 N 条相同的线。

### 2.3 关联即同色

- 同一子系统/同一语义族用同一色相（`classDef` / `style` / themeVariables）；
- 不同层次（控制面 vs 数据面）用不同色相族；
- 颜色是语义通道，不是装饰——先定语义再上色。

### 2.4 分组即框选

- 宏观逻辑分区：可见的具名 `subgraph`（flowchart）或 `namespace`（classDiagram）；
- 同类细分组：同色系 + 无边框（flowchart 节点样式统一）；
- 分组层级 ≤2 层，超过则拆分图集。

## 3. 文字修饰

### 3.1 元素标签最小化（去重优先）

1. **先去重**：已被图类型/构造型/嵌套结构表达的语义，删掉重复文字；
2. **元素上只留简洁标题**：≤10 字符（CJK），英文 ≤12 字符；
3. 禁止在标题里塞一句话描述。

### 3.2 详细说明外置

- `flowchart`：边标签 `A -->|说明| B`、或独立注释节点 `A:::note` 连虚线；
- `sequenceDiagram`：`note right/left of 参与者: 说明`；
- `classDiagram`：`note for 类名 "说明"`；
- 通用：图例 `legend`（flowchart 支持 `legend`/`legendRight` 指令）；
- 布局安全优先：注释放不下就省，或并入图集文字说明。

### 3.3 字号层级统一

- `%%{init: {themeVariables: {fontSize: ...}}}%%` 统一基准字号；
- 层级：标题 > 容器(subgraph) > 元素 > 注释 > 图例 > 箭头标签；
- **禁用零散内联字号/加粗**——字号/粗细不一是头号杂乱成因；
- 跨图集保持一致（同一套 init 配置）。

## 4. 上下文驱动与拆分

### 4.1 上下文驱动（程序正确性优先）

- UML 脱离程序上下文无意义：先吃透文档/代码/用户描述；
- 产出**带出处的上下文摘要**：组件清单、关系清单、核心流程、关键决策；
- 后续绘图与自检都对着摘要，**保证程序整体正确、不臆造**；
- 摘要里标注不确定项，绘图时用最小假设并显式说明。

### 4.2 减法与拆分

- 信息量大时：**优先整洁美观而非面面俱到**；
- 每图突出**一个核心点**，其余砍掉或外置到图集；
- 单图表达不下 → 按架构接缝拆分（分层/控制面数据面/静态行为/请求制品流/系统节点边界）；
- 元素数量控制：核心 ≤7，硬上限 ≤15（超出先减法，再考虑拆分）。

### 4.3 图集组织

- 一张概览/索引图在顶 + 下钻子图；
- 图间层次与交叉引用：`▶ 见 图N`；
- 每图自足（不依赖他图才能看懂）；
- 图集共享稳定词汇：编号、颜色、构造型跨图同义。

## 5. 自检清单（每图交付前）

- [ ] 图类型选对了吗？（UML 语义先行）
- [ ] 元素种类/关系类型正确吗？（六种关系/箭头语义/基数）
- [ ] 构造型与接口标注了吗？
- [ ] 核心元素 ≤7、硬上限 ≤15 吗？
- [ ] 标签去重、≤10 字符、说明外置了吗？
- [ ] 字号层级统一、无零散内联字号吗？
- [ ] 色彩有语义吗（同色同族）？分组有边界吗？
- [ ] 布局方向/宽高比合理吗？（见 layout.md）
- [ ] 与上下文摘要一致吗？有没有臆造？
