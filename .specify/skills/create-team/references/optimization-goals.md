# 「优化」类目标的途径与策略（操作规范）

**Owner**: the team domain (`create-team`). 当 team 的 [goal](goal.md) 主题为**「优化」**时，用本文的分类与策略来选择团队形态。本文只讲**优化类目标的团队形态选择**;goal 概念本身(定义、作用对象、判据权威)见 `.specify/shared/definitions/goal-definitions.md`,经 [goal.md](goal.md) 转引,不在此另述。

## 1. 一次性 vs 持续优化（先分类）

| 类型 | goal 语义 | 停止条件 | 团队形态 |
|------|-----------|----------|----------|
| **一次性（one-time）** | 把某物从 A 提升到 B，**一次达标即止** | 达到目标质量（或有限轮次）即交付 | 一次 **iteration** 到阈值即停；或串行「评估 → 改进 → 复核」 |
| **持续（continuous）** | **不断提升 / 长期维持**某质量 | 达到高标准阈值，或收敛 / 资源上限 | **continuous** 运营循环（见 [`operating-loops.md`](operating-loops.md)）：按 cadence 长期运行，从 L1 起步，需可复现、可复盘、有护栏 |

**判定**：goal 含「持续 / 不断 / 长期维持 / keep improving」→ 持续；否则按一次性处理。

## 2. 持续优化的两种策略

两者都围绕**可度量 goal**（评分维度 + 阈值）组织，但选择压力与目标结构不同：

| 维度 | ① 淘汰（Elimination / Tournament） | ② 渐进（Progressive / Incremental） |
|------|-------------------------------------|--------------------------------------|
| **机制** | 同一目标上并行跑多个「变体优化器」，每代**淘汰最差、克隆最优** | 把总目标**分解为多个独立子目标**，每组各自「优化→绘制/执行→打分」迭代累积 |
| **选择压力** | 竞争择优（精英保留） | 质量阈值（各轨道达标即停，无竞争） |
| **目标结构** | 单一目标 + 多种改法竞争 | 可分解为 N 个子能力，分而治之 |
| **并行性** | 一代内多变体并行、跨代串行 | 多组（子目标）长期并行，组内小循环 |
| **停止条件** | 达标 / 连续多代无提升（收敛）/ 代数上限 | 每条轨道各自达阈值（如 > 90 分）即停 |
| **团队模式映射** | iteration（Supervisor 做锦标赛式选择）；若需长期持续择优则用 continuous | parallel dispatch（N 组互不相交）× 每组一个小 iteration |

> 两者可**组合**：先渐进补齐各子能力，再对整体做淘汰精修。

## 3. 淘汰策略 —— 配置要点

- **静态结构**：一个 Team Supervisor + 若干「变体优化器」Worker（每个用不同改进方法）。
- **花名册样例**（`variants: 3`，可直接实例化）：3 个 variant-optimizer（各持一个改进角度，如布局向/风格向/语义分解向）+ 1 个 renderer（Worker，用各变体的 target 副本重生成被评制品）+ 1 个 scorer（evaluator，统一按 `quality_dimensions` 打分并给出每变体「最大可改进点」）。完整可 re-run 的实例见 `.specify/teams/draw-plantuml-optimizer/team.md`。
- **动态结构（iteration）**：每代 → 各变体**改进目标(target)** → **由目标重生成被评制品** → 统一评分 → **保留最高分为下一代种子、淘汰最低分** → 重复。
- **config**：`quality_dimensions[]`（Σ=1.0）、`threshold`、`max_iterations`、`regression_limit`；若优化对象是可复用目标，设 `optimization_target`（技能/实现/配置的真实路径）；**收敛判据**（连续 N 代无提升）作为除达标外的停止条件。
- **多目标协同（`co_targets`）**：当优化对象是多个需协同演进的目标（如主技能 + 配套技能/命令），不要临时发明键——用 `config.co_targets` 列出各目标路径，并在 goal 或 config 中声明**分层原则**（哪类内容归哪个目标）；评分仍是单一加权总分，但每轮改动必须按分层原则路由到正确目标。单目标场景继续用 `optimization_target`。
- **目标引用用路径语义，不用技能名语义**：当 target 是会被复制到工作副本或 standalone 部署的技能时，目标解析与其内部自指引用一律按**「当前加载目录」的路径语义**（如 `${SKILL_HOME}/...`）而非按技能名解析——按名解析在多副本环境（工作副本 vs 真实路径 vs standalone 安装）下有歧义。跨技能机制委托（A 技能的 feedback 交 B 技能处理）同理：落点写路径，不写名字。
- **关键设计**：把上一代评分器的「最大可改进点」反馈注入下一代变异，使进化有方向。
- **种子嫁接**：下一代的种子不只是「克隆最优」——以最高分变体为种子主体，**嫁接亚军变体评分最高的单一改动**（如亚军在某一维度上反超冠军的具体改法）。纯精英保留容易陷入冠军变体的局部最优；嫁接保留了亚军的差异化探索（实测 gen-1 0.763 → gen-2 0.859 的跃升来自此组合）。
- **`score = f(target)` 不变式（淘汰策略同样适用）**：当 `optimization_target` 是可复用目标（技能/实现/配置）时，变体**只改 target（工作副本），不得直接手改被评制品**；再由 executor **加载最新 target、从源输入重生成**被评制品（即与 §4 相同的「重载最新实现」），对**重生成物**评分。「固定被评对象、只变呈现/方法」中的「方法」= **改 target**，被评制品每代由 target 重生成，**不是**手工微调制品本身。采纳的最优 target 落其真实路径为标准输出，重生成物为运行中间件。
  - **反模式**：直接优化被评制品（手改输出的图/文件）、只在末尾把改动批量蒸馏回 target——这度量的是**制品**而非 **target**，target 的优化闭环从未真正闭合。

## 4. 渐进策略 —— 配置要点

- **目标分解**：把总目标拆成 N 个**独立子目标**，每个子目标一组 agent（互不相交的并行轨道）。
- **组内 subagent 分工**：**优化 agent**（改进技能/实现）、**执行/绘制 agent**（用最新实现产出制品）、**打分 agent**（按评分维度打分）。
- **单轨流程**：
  1. **查资料**：先查本地是否已有所需说明文档；**没有则从权威来源获取**（记录来源 URL）。
  2. **优化**：优化 agent 改进该子目标的实现。
  3. **重载最新实现**：优化完成后，其余 agent **重新加载最新实现**（保证渐进累积，不基于旧版本）。
  4. **执行 + 评分**：产出制品并评分（如 正确性 60% + 美观 40%，满分 100；低于下限则调整重做）。
  5. **循环**：重复 2–4，**直到该轨道达到质量阈值**（如 > 90 分）即停。
- **关键差异**：无淘汰、无竞争；靠「重载最新实现 + per-track 阈值停」实现稳定累积；评分标准按子目标各自清晰。

## 5. 如何选择

- 目标单一、改法未定、有明确评分 → **淘汰**（多方案竞争择优）。
- 目标可分解为多个独立子能力、想稳定累积、每子目标有清晰阈值 → **渐进**（分而治之 + 阈值停）。
- 二者可组合：先渐进补齐，再淘汰精修。

## 6. 文档 / recipe 类 backlog：先采证后写（两阶段标准套路）

当 backlog 项是「补 recipe / 写操作文档」类内容时，iteration 团队固化为两阶段执行：

1. **采证**：executor 先**真实跑通**完整业务场景，捕获成功的命令序列、参数与输出（失败也如实记录）。
2. **誊写**：optimizer **只依据采到的证据**写文档；无证据的域不写——与 improve-skills 的「无证据不编造」纪律天然一致。

配套要求：backlog 项登记时必须显式标注**「需哪种执行证据可解锁」**（哪个场景跑通、哪类输出在手即可写），让后续 run 能定向采证，而不是留下泛泛的"待补"。

> 淘汰式优化的可复用范例（draw-plantuml 复杂图表优化）以团队花名册形式持久化在 `.specify/teams/draw-plantuml-optimizer/team.md`——其中完整给出了评分规则（加权维度）、淘汰/精英保留策略与成员映射，可直接 re-run。完整的逐轮评分结果需实际执行该 iteration 后累积，届时每轮报告落在同目录 `runs/` 下。
