# 项目总结操作手册 (Reporting Playbook)

`summarize-project` 技能的**跨层公共约定**：跨层图表呈现公约（四态色板 / yyyy-mm-dd 日期 / 图题图说 / 渲染契约）、**进度呈现公约（进度贯穿五章节）**、报告结构、刷新规则、图集拆分、三图一致性清单、范围与粒度控制、落盘检查单、外部文档取材。各呈现层面的细则已分解到独立层参考文档（见下方索引）；工作流主框架见 [../SKILL.md](../SKILL.md)。

**边界（两条）**：① **日期与进度的计算**（状态判定、延期、天数差、百分比、聚合、today 偏移、出图判据）由 `scripts/progress-engine.py` 独家承担，本手册与各层文档只写"取哪个字段、怎么呈现"（见 [consistency-rules.md](consistency-rules.md) §0.1）。② 本手册只写**本报告的信息语义约定**（哪张图承载什么、报告结构与门禁）；通用绘图规则——PlantUML 语法、字形与冗余编码、图例契约、版面/刻度/zoom 量测、渲染踩坑——权威出处在 draw-plantuml：`<draw-plantuml>/references/guide/style.md`、`<draw-plantuml>/references/guide/large-diagram-playbook.md`、`<draw-plantuml>/references/howto/13-wbs-diagram.md`、`<draw-plantuml>/references/howto/14-gantt-diagram.md`、`<draw-plantuml>/references/howto/15-mindmap-diagram.md`、`<draw-plantuml>/references/howto/12-rendering-and-output.md`。同一条规则只有一个权威出处，本手册不重述通用规则。

## 1. 跨层图表呈现公约（所有图表统一遵守）

### 1.1 统一四态色板（工作项四态 + 里程碑三态）

全报告所有图（WBS、里程碑视图、进展甘特、特性概览）共用一套状态色板；同一状态在任何图中同色，图内声明与图例色块**引用完全相同的 6 位十六进制字面量**（不得色名/十六进制混写）：

| 语义 | 填充色 | 描边色 | 冗余符号 | 用在哪 |
|------|--------|--------|----------|--------|
| completed / 已完成 | `#C6E9CB` | `#3E9256` | `✓` | WBS `.done` 类、脑图 `.done` 类、甘特已完成条（`is 100% complete`） |
| in-progress / 进行中 | `#BBD8EE` | `#2E6E9E` | `●` + 条内填充比例 | WBS/脑图 `.doing` 类、甘特进行中条（配 `is N% complete`） |
| **delayed / 延期** | `#EF9A9A` | `#C62828` | `⚠` + 条内填充比例 | WBS/脑图 `.late` 类、甘特延期条（配 `is N% complete`，延期天数取引擎字段） |
| not-started / 未开始 | `#ECEFF1` | `#90A4AE` | `○` | WBS/脑图 `.todo` 类、甘特未开始条（不写 complete 子句） |
| 里程碑 achieved | `#43A047` | — | `✓` | 里程碑视图与进展甘特的已达成菱形 |
| 里程碑 pending | `#FFD54F` | `#F57F17` | `◇` | 未达成菱形（`<style>` milestone 默认色） |
| 里程碑 at-risk（含逾期） | `#E53935` | — | `⚠` | 逾期菱形（锚定日已过且未达成）或有材料依据的风险菱形 |
| 里程碑锚点（WBS 节点） | — | — | `◆Mn` | WBS 节点标题行末尾 |
| 分组节点（非状态） | `#CFD8DC` | `#78909C` | — | 脑图分组节点、甘特全程背景带 |
| today 参照线 | `#1565C0` | — | — | 饱和深蓝，保证白底可见 |
| 依赖箭头 | `#607D8B` | — | `-[dotted]->` | 低调虚线 |

- **四态取自引擎，呈现层不做判定**：每个工作项的 `status`（`completed / in-progress / delayed / not-started`）、`progress_pct`、`delay_days` 一律**取进度引擎脚本的输出字段**；本手册、层参考文档与报告正文**都不写**日期先后比较、天数差或百分比算式（字段清单与红线见 [people-encoding.md](people-encoding.md) 第 1.0 节）。
- **浅色给工作项、饱和色给里程碑**：工作项图元（WBS 节点、甘特条、脑图节点）内部要放深色文字，故一律浅填充；里程碑菱形是小图元、须高饱和才辨识。延期态沿用同一分工——工作项浅红 `#EF9A9A` ↔ 里程碑 at-risk 饱和红 `#E53935`，与已有的 completed `#C6E9CB` ↔ achieved `#43A047` 完全同构，不引入新的配色逻辑。
- **延期态为何取略深的浅红**（实测取舍）：`#EF9A9A` 比另三态略深、略饱和，两个理由——① 甘特"条内填充比例"是一条几何通道，填充色必须与白色余量可辨；实测 `#FFCDD2`（Material Red 100）红通道与白同值，30% 填充在成图上目检不出来，换 `#EF9A9A` 后填充边界清晰；② 延期是需要读者优先注意的异常态，略强的视觉权重是有意为之。
- **两套符号并存且不冲突**：工作项四态符号 `✓ ● ○ ⚠`，里程碑三态符号 `✓ ◇ ⚠`。`✓` 与 `⚠` 两套共用且**同义**（已完成/已达成、落后于计划）；`◇` 专属里程碑（菱形形状本身即里程碑语义），工作项"未开始"改用 `○`，二者不混用；`●`/`○` 的实心↔空心对比表达"已动工↔未动工"。字面量与放置位见 [people-encoding.md](people-encoding.md) 第 1 节。
- 在此色板之外不为状态另造颜色；非状态语义（如阶段分组带、脑图分组节点）用中性灰系，不与四态色冲突。
- **零实例退化优先于"色板完整"**：项目没有延期条目时，`<style>` 不定义 `.late`、图例不列延期行；同理适用于其余三态（图例契约见 §1.6）。
- **四张图一律着色，不允许灰白单色**：WBS、特性概览脑图、里程碑视图、进展甘特全部按本色板编码状态；只有"材料完全没有状态信息"才整图不着色，且必须显式声明（见 [people-encoding.md](people-encoding.md) 第 6 节）。
- **里程碑三态必须同时带 `✓ / ◇ / ⚠` 符号**（本报告的冗余编码约定；字面量见 [people-encoding.md](people-encoding.md) 第 1 节）。为什么颜色要与符号冗余、以及字形选择规则（可用字形白名单 `✓◆◇●○▲■★☆⚠`、`✔`/`✗` 与 emoji 一律禁用）见 `<draw-plantuml>/references/guide/style.md`「状态编码：颜色 + 符号冗余」。

### 1.2 日期格式公约（yyyy-mm-dd）

- 报告中**一切日期**统一 `yyyy-mm-dd`：PlantUML 语句（`Project starts 2026-03-02`、`happens 2026-03-13`、`starts 2026-03-02 and ends 2026-05-27`）、跟踪表、图说、进度叙述、`title` 中的基准日、`## 元信息` 生成日期。
- **禁止**任何变体：`2026/5/1`、`2026.5.1`、`5月1日`、`Mar 2`、`the 2nd of march` 等；材料中的其他写法在采集阶段（Step 2）即换算为 `yyyy-mm-dd` 记录。
- 材料只给到月精度时，引擎会补当月首日并标 `inferred`（`precision=month`）；呈现时写 `yyyy-mm-dd（推断）` 或保持 `yyyy-mm` 区间叙述并在假设区标注精度限制，**不虚构具体日**。
- **日期的转写与校验由引擎完成**（`progress-engine.py`：可归一化的写法自动转写、歧义/非法日期直接报错），报告里出现的每个日期都应能在引擎输出中找到。

### 1.3 图题与图说（标题简洁、内容详实）

- **标题简洁**：图 `title` 与章节内图名 ≤15 个汉字（可含括注的基准日）；图内节点/条目标题同样从简（WBS 节点 ≤12 汉字、里程碑名 ≤10 汉字、甘特任务名同 WBS），细节一律沉入图说与配套表格，不塞进图形元素。
- **图说详实**：每张渲染图之后紧跟一段"图说"，固定三要素——
  1. **是什么**：一句话讲本图呈现什么、数据截至哪一天（yyyy-mm-dd）；
  2. **怎么读**：颜色/符号/线条的编码含义（工作项四态色与 `✓●○⚠` 符号、条内填充比例/`NN%` 完成度、◆Mn 对照、菱形状态色与 `✓◇⚠`、today 蓝线、虚线依赖、锚定换算说明等）；
  3. **结论**：一句当前状态判断（如"整体完成约 45%，today 线左侧无未完成条，进度贴合计划"）。
- 禁止"只贴图不解释"；图说与图互为印证，图说中的数字须能从图或表中复核。

### 1.4 渲染契约（委托 draw-plantuml，失败必须可见）

- **逐图渲染**：每张图的源码单独成一个 `assets/<图名>.puml` 文件（**源码只以文件形态存在，不进 `summary.md` 正文**），经 draw-plantuml 的 `render-plantuml.sh` 渲染为 SVG 与 PNG（命令见第 5 节）。**正文一律引用 `.svg`**（`.png` 作为 `assets/` 内的同名配对产物交付，正文不另写「png 备选」字样——否则同一报告两次运行的图位文字会不同）。**成功标准**三条同时满足：命令零退出、产物为含 `<svg` 根元素的非空文件、渲染结果中无 `Syntax Error` / 错误红字。
- **失败修正 ≤2 轮**：按报错行修正源码后重渲。常见语法诱因（前向引用、`<style>` 的 `arrow { }` 内写 `LineStyle`、`happens at` 引用未声明的任务、`<style>` 多属性挤在一行、`legend` 未闭合、日期格式非法等）见 `<draw-plantuml>/references/howto/14-gantt-diagram.md`、`<draw-plantuml>/references/howto/13-wbs-diagram.md` 与 `<draw-plantuml>/references/guide/style.md`，本手册不重述。修正若触及门禁冻结内容，回对应门禁重新确认。
- **失败不可静默**：2 轮修正仍失败时，**不得**删图、不得以旧渲染结果冒充——`.puml` 源文件保留在 `assets/` 内，在报告该图位置写图题 + 显式告示行 `> ⚠ 本图渲染失败：<一句原因>`（并注明图源文件名，读者可自行渲染），并计入元信息渲染状态清单。
- **渲染状态清单**：`## 元信息` 逐图记录「图名 | ok / failed（原因） 」；存在 failed 时报告仍可落盘，但自包含检查按"带失败告示"通过，不算静默缺图。
- **渲染后量测自检**：成功产物还须按 `<draw-plantuml>/references/howto/14-gantt-diagram.md`「量测自检：三条几何判据」执行（有效字号 / 长宽比 / 标签不越界），可用其 `scripts/measure-svg-layout.py` 量测；另目检本报告特有项——图例完整可见、today 线可辨、WBS 左右阶段顺序正确、无文字截断重叠。**版面不合格按"调参重渲"处理**（刻度/zoom、MaximumWidth、Margin/Padding、legend 位置），不占用 2 轮语法修正额度、也不出失败告示。
- **两支量测各司其职（渲染后，判据不重叠）**：**通用版面几何**（长宽比 / 有效字号 / 标签溢出 / A–B 排期比对）以 `<draw-plantuml>/scripts/measure-svg-layout.py` 为权威引擎；**数据侧几何**（甘特条形起止 ⇄ 记录层日期、里程碑菱形 ⇄ 锚定日、进行中条结束边界 ⇄ 基准日——需项目日期做真值）由本技能 `scripts/verify-chart-data.py --svg <图.svg> --kind gantt --expect <记录层.json>` 承担——其 `--expect` 真值**直接由引擎输出转出**（`bars` 取各条目的 `planned_start`/`planned_end`/`progress_pct`，`milestones` 取 `anchor_date`，`project_start`/`today` 取 `gantt.project_start` 与 `baseline`），因此"图画在哪一天"与"报告写哪一天"共用同一份计算结果。两支输入不同、量测对象不同，不重复实现同一量测（通用几何不在本技能重造）。

### 1.5 人员承载公约（人员是一等呈现维度）

采集阶段登记的「负责人」必须在呈现层有落点，**不得静默丢弃**。三层承载位（细则、字面量与实测示例见 [people-encoding.md](people-encoding.md)）：

1. **记录层**：结构 B/C 的负责人列必填（规范名 / `规范名（推断）` / `未记录`），结构 D 与之互为镜像。
2. **图内**：WBS 任务级节点第二行 `【姓名】`、甘特条形显示名后缀 ` ▪ 姓名`、里程碑标签末尾 ` ▪姓名`（脑图：叶子特性**有**负责人材料时必标 ` ▪姓名`、**无**则不标，见 requirements-features「图形编码规范」）。部分缺失写 `未记录`，**不得整段省略**；全量缺失时全图不标注并用 `caption`（或图说首句）显式声明"材料未记录任何负责人信息"。
3. **报告正文**：`## 功能分解` 节内固定小节 `### 人员与分工`，首句为**人员维度覆盖率声明**（`已记录负责人的条目 X / 全部条目 Y（Z%）`）。全量缺失时小节仍保留，写明已检索过哪些来源。
- **甘特不使用 `on {资源}`**：资源语法不会把人名画在条形上，且底部资源盒吃掉大量图高——人员一律进条形显示名（理由与实测见 [people-encoding.md](people-encoding.md) 第 3 节）；仅当用户明确要求人员负载分布时按其例外条件启用。
- **名称跨图逐字一致**：结构 D 规范名 = WBS `【…】` = 甘特 ` ▪ 姓名` = 里程碑 ` ▪姓名`；`（推断）` 后缀只出现在表格与元信息，不进图内。
- **隐私收敛**：对外报告的人员表默认不呈现邮箱（结构 D 的「别名/邮箱」列折叠为 `-`）。

### 1.6 图例契约（遵循 draw-plantuml）

- 图例的通用契约——**零实例退化 / 双向完备 / 单编码退化 / 色块与声明同字面量**，以及落盘前必跑的确定性自检脚本——见 `<draw-plantuml>/references/guide/style.md`「图例契约」，本手册不重述。
- **本报告特有的一条**：人员图例行仅在图内确有人员标注时出现；全图无人员标注时不列该行，改由 `caption`（或图说首句）承担声明。

### 1.7 读者用语纪律（内部标识不得渗入正文）

规则、门禁、分级体系的**内部标识**是生成期可判定性的工具，不是给读者看的语言。以下内部标识——信息源分级代号（`T1`–`T5` tier）、构建/CI 证据分级（`E1`–`E5`）、诚实处理编号（`RC-1`~`RC-5`）、覆盖/自洽门禁名（`CG-COVERAGE`、`CG-1`~`CG-11`）、[consistency-rules.md](consistency-rules.md) 的 `§编号`、统计口径 ID（`M-FEAT-1`、`M-TASK-*`、`M-SPEC-*` 等）、**引擎字段名与枚举值**（`progress_pct`、`delay_days`、`schedule_status`、`schedule_state`、`unknown-schedule`、`progress_basis`、`counts.*`、`gantt.today_offset_days` 等）、**数据层内部标识**（数据库/表/列/视图名与 SQL 本身：`project.db`、`schema/project.sql`、`work_items`、`work_item_deps`、`status_norm`、`entity_ids`、`v_*` 视图、`PRAGMA foreign_keys`、任何 SQL 片段）、以及脚本名（`project-db.py` / `progress-engine.py` / `verify-chart-data.py` / `check-coherence.py` / `detect-project-sources.py` / `validate-project-input.py`）——**只允许出现在 `## 元信息` 或技能内部文档（本 `references/` 下各文件）中**。读者面写业务语言：`unknown-schedule` → 「无计划日期，无法判定延期」，`delayed` → 「逾期 N 天」，`progress_pct=null` → 「进度未量化」。

五个面向读者的报告章节——`## 项目概览` / `## 需求与特性` / `## 功能分解` / `## 项目里程碑` / `## 任务进展`，连同其**图题、图说、正文表格**——**必须使用纯业务语言**：写"该阶段部分完成""里程碑锚点缺失，本维度暂缺""进度未量化，仅报状态计数""下单结算已交付、优惠券开发中"，而**不得**出现 tier 代号、规则编号、门禁名、脚本名、引擎字段名、表名/列名/SQL 等内部黑话。**进度数字同理**——读者看到的是数值本身（`12/20 = 60%`），字段名与取值来源对照只写在 `## 元信息 · 进度数据来源`。这是 §1.3「标题简洁、业务语言、无内部黑话」与"读者兼顾"原则的强化——内部标识服务于判定，业务语言服务于阅读，两者分置。落盘检查单（§7）设一条对应门禁。

### 1.8 进度呈现公约（进度贯穿五章节）

**进度是一等呈现维度，不是《任务进展》一节的专属话题**。外部读者最先想知道"这个项目做到哪了"，因此五个章节**各有固定的进度呈现位**，缺一即骨架不完整：

| 章节 | 进度呈现位（固定） | 形态 |
|------|--------------------|------|
| `## 项目概览` | 章节末 `### 整体进度摘要` | 整体完成度句 + 一句进度判断 + 进度概览表（4 行）+ 进度条（引擎给 `progress_bar` 则必出、未给则不出） |
| `## 需求与特性` | 开篇量化句 + 特性清单表「进度%」列 | 一句 + 表格列 |
| `## 功能分解` | `### 工作项进度`（阶段聚合段 + 工作项段）+ WBS 图说结论句带进度 | 两段表格 + 一句 |
| `## 项目里程碑` | 里程碑进度汇总表（达成率/已达成/逾期/待达成/最大逾期天数）+ 跟踪表「达成进度」「延期天数」列 + 达成叙述带百分比 | 汇总表 + 表格列 + 一句 |
| `## 任务进展` | 甘特 + `### 进度叙述`（整体完成度 / 分阶段进度表 / 完成度分布 / 逾期条目数） | 三段叙述 + 分阶段表 |

**两条硬约定**：

1. **计算在引擎，呈现只引用**：一切进度百分比、达成率、天数差、逾期判定、阶段聚合、完成度分布由进度引擎 `${SKILL_HOME}/scripts/progress-engine.py` 计算并输出结构化进度数据；报告正文与本 `references/` 各文档**不写算式、不判日期先后、不算天数差**——需要一个数字就"取引擎输出的 `<字段>`"。
2. **跨章节同值同源**：同一实体的进度在任何章节都引用引擎**同一字段**，落笔字面量（含精度、分子分母）完全相同；不一致时回引擎重取，**禁止人工调平**。

进度呈现位总表、逐章节呈现模板、进度叙述规范（百分比写法、枚举→读者用语映射、禁用写法清单）、跨章节一致门禁、`null` 时的降级形态与 `## 元信息 · 进度数据来源`，全部以 [progress-presentation.md](progress-presentation.md) 为**唯一权威出处**，本手册不重述。落盘检查单（§7）设「每章节进度呈现位齐全」与「进度数字均引用引擎输出、跨章节口径一致」两条门禁。

## 3. 刷新规则（重复运行）

- **整体重生成，刷新整个目录**：每次运行重新读取信息源并重生成**整个交付目录**——`summary.md` 正文（概览、特性清单、图表、表格）、`assets/` 全部图源与渲染产物、`data/` 全部中间产物一并重建，保证呈现与事实源同步；不存在"增量维护事实"的概念。
- **附注保留**：既有报告中的 `## 附注` 节逐字节保留并放回固定位置；用户写在其他章节的手工内容不保留（可在刷新前提示一次）。
- **变更留痕**：每次运行刷新 `## 元信息`（生成日期 + 信息源清单 + 四道门禁确认状态）；里程碑状态以事实源为准重新判定。
- **确认沿用（刷新运行的批量确认）**：刷新运行仍走四道门禁；与既有报告逐字一致的门禁章节可合并为一次「全部沿用」确认，有变化的章节逐层确认。

- **进度呈现位的降级**：五章节的进度呈现位在进度数据缺失（引擎给出空值）时**保留位、退化内容**——写 `-（无可计数依据）`、判断句改"无排期依据"式，**不写 `0%`**、不用状态计数反推百分比；逐章节降级形态见 [progress-presentation.md](progress-presentation.md) 第 6 节（与本节「五类禁造物」的进度百分比终态完全一致，不新增终态、不放宽门禁）。
- **无里程碑材料**：`## 项目里程碑` 保留标题，章节体仅「材料声明 + 已检索来源」，不出跟踪表与视图；**普通提交、版本号、`Implemented` 特性不得升格为里程碑**（第 4 节）。
- **无排期材料**：甘特**不出图**，`## 任务进展` 退化为「声明 + WBS + 状态表 + 叙述」；git 提交日期不得当作任务 `starts/ends`（第 5 节判据，含 git-only 极弱材料阈值）。
- **最小可交付形态**：五章标题必留、缺料章节体退化为声明；报告随材料量伸缩、宁短勿虚，不为"显得完整"堆占位行或虚构图（第 7 节）。
