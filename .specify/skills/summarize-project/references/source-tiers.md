# 跨层规范：opt-in repo 补充源 —— 定向查询规程（可选补充源，非主路径）

`summarize-project` 的**可选补充源规程**。本技能的**输入主路径是必要信息表 + 上下文摄取 + 表单补填**（唯一权威见 [required-info.md](required-info.md)）：项目管理信息本来就不在代码仓库里——一个项目常横跨多个 repo，排期、负责人、里程碑、验收节点活在项目管理程序里。**默认不扫任何 repo。**

**本文档只在下面这个门打开时才适用**（启用门，两条同时满足）：

1. 表单 `project.repos[]` **已声明**至少一个仓库（含 `repo_id` 与 `repo_path`）；
2. 目标字段出现在该仓的 `derive_fields[]` 里，即用户**明确标注该字段「从 repo 推导」**。

门未打开 ⇒ 本文档整份不执行；门打开 ⇒ 只对**被授权的那些字段**做**定向小范围查询**。

**硬禁止（相对旧版的行为变更）**：

- ❌ 不再「默认检测 `.specify/` 管理结构、据此深挖 `specs/*/requirements.md`、`tasks.md`」——那是旧主路径，已废止；
- ❌ 不做全仓扫描、目录遍历、批量 `wc -l src/*`、通读模块树；
- ❌ 不把 repo 当作 R 档（必填项）的来源：R 档缺失一律阻断出表单，**不能靠扫 repo 凑齐**；
- ✅ 允许的形态：**单条只读命令 + 限定路径 + 只取被授权字段**（例：只为 `people.owner_name` 跑一次 `git shortlog -sne --no-merges`；只为 `milestones[].actual_date` 跑一次 `git tag` + `git for-each-ref … refs/tags`）。

**边界（两条）**：
1. 本文档只写**信息语义**（材料在哪、用什么命令定向取、怎么写溯源、取不到就退回合法终态）。它**不写**任何绘图规则（PlantUML 语法、字形、图例、版面量测），那些的唯一权威出处是 draw-plantuml。
2. **一切日期与进度计算**在 `scripts/progress-engine.py`；本文档不含算式（见 [consistency-rules.md](consistency-rules.md) §0.1）。

**推导结果的标注纪律（每条都要）**：从 repo 推导出的值一律带 `inferred: true` + `inferred_from: repo:<repo_id> <命令要点>`，进入引擎输出的 `inferred_fields`，并在报告 `## 元信息 · 推断字段清单` 逐条呈现。**repo 推导只影响 I / O 档字段**。

**多 repo 归集与冲突处置**：

| 情形 | 处置 |
|------|------|
| 多个仓库都声明了同一字段的 `derive_fields` | 逐仓定向查询，结果按 `repo_id` 分别记录 |
| 同一 `item_id` 在多个 repo 中"看起来都有" | **工作项身份由表单唯一确立**：同一 `item_id` **不得**在多 repo 重复定义；repo 只补字段值，不新增工作项 |
| 多仓对同一字段给出**冲突值** | **不合并、不取平均、不选最新**：保留表单/管理系统导出的值，把冲突逐条写进 `## 元信息`（形如「`T-07.actual_end`：repo:gateway 给 2026-04-02、repo:sdk 给 2026-04-05，采用表单值 2026-04-03，冲突留痕」） |
| repo 与表单冲突 | **表单/管理系统导出优先**（它才是项目管理事实源）；repo 值只作佐证并注明冲突 |

**取不到就退回合法终态**：定向查询无结果时**不换更大范围重试**，直接按 [degradation.md](degradation.md) 第 3 节走该字段的合法终态（`未记录` / `未排期` / `-（无可计数依据）` / `未知`）并显式声明。

工作流主框架见 [../SKILL.md](../SKILL.md)；记录层与呈现映射见 [data-model.md](data-model.md)；跨层图表公约见 [reporting-playbook.md](reporting-playbook.md)。

## 1. 可选补充源阶梯（佐证强弱排序，**只在门打开时**逐级取用）

同一个仓库里可能有若干种材料，**佐证强度**从高到低如下。它们**都只是补充源**：主源永远是表单字段；只有当某字段被 `derive_fields` 授权、且表单里该字段为空时，才按本阶梯从强到弱找**一处**佐证，找到即止。

可选地，用 `python3 ${SKILL_HOME}/scripts/detect-project-sources.py --target <repo_path>` 对**已声明的某个仓库**做一次探测，看它有哪些补充源可用（输出 `source_tiers` / `primary_tier` / `build` / `git`）——这只是 opt-in 情形下的便利工具，**不是主路径的检测步骤**。

| 级别 | 名称 | 存在性判据（命令/位置） | 权威承载的呈现内容 |
|------|------|--------------------------|--------------------|
| **T1 规格级** | Spec artifacts | 存在规格目录，且至少一个子目录含需求/任务/计划文档（**示例布局**：`.specify/specs/*/requirements.md`、`tasks.md`、`plan.md`） | 需求、功能分解（计划/任务层级）、任务状态与进度（勾选标记）、里程碑（验收节点） |
| **T2 记忆级** | Memory | 存在有数据行的特性索引与项目原则文档（**示例布局**：`.specify/memory/features.md`、`constitution.md`） | 项目概览（使命/原则）、特性清单与状态（索引状态列）、特性→代码映射与子项（特性详情文档） |
| **T3 代码与构建级** | Code & Build | 存在包/工程清单或构建定义（**示例**：`Cargo.toml`/`pyproject.toml`/`package.json`/`go.mod`/`Makefile`/CI 定义——判据见 §3.1 的 C1–C4，不限于这些文件名） | 项目概览（清单元数据）、特性（CLI 子命令 / 公共 API / 模块）、功能分解的**叶子佐证**、状态证据（可构建/有测试/有 CI，见 §6） |
| **T4 版本历史级** | Git history | `.git/` 存在 | 时间锚点（首末提交日期、活跃区间）、作者名册、每次提交的变更范围；**不承载**工期、里程碑、进度百分比（见 §5 红线） |
| **T5 外部文档级** | External docs | `README*`、文档目录、用户提供的 Word/PDF/Markdown/看板导出 | 项目概览与特性叙述的补充、路线图/发布记录中的里程碑、外部需求/任务清单 |

> **README/docs 的跨级地位**：README 与文档目录属于 T5，但对**项目概览与特性叙述**而言它们往往是最贴近产品语言的材料，**任何级别都可引用**作为补充与佐证；只是当它与 T2/T3 事实冲突时，按"代码是唯一事实源"以代码为准，并在叙述中注明冲突（见 §4 的红线）。

### 1.1 字段级授权与佐证降级链（**仅对被 `derive_fields` 授权的字段**）

这**不是**"报告内容的主源优先级"（报告内容的主源永远是表单字段），而是"**某个已被授权的字段**在仓内找佐证时按什么顺序找、找不到怎么办"。一个字段只找**一处**佐证，找到即止：

| 被授权字段（示例） | 仓内佐证顺序（强→弱） | 找不到时的终态 |
|--------------------|------------------------|----------------|
| `project.project_desc` | C1 包/工程清单的描述字段（§3.1；**文件名随生态而变**）→ README 引言 | 概览写「材料未记录项目定位」 |
| `features[].status` | 规格工件的任务勾选 → 记忆级特性索引状态列 → 构建/CI 证据分级（§6） | 状态记 `未知`（**不等于** `not-started`） |
| `work_items[].status` | 规格工件的任务勾选标记（`[x]`/`[ ]`，口径见 [consistency-rules.md](consistency-rules.md) §1.2）→ 记忆级状态列 → 构建/CI 证据（§6） | 状态记 `未知` |
| `milestones[].planned_date` / `actual_date` | git 标签日期（`git for-each-ref … refs/tags`）→ 发布记录/变更日志 → 验收记录 | `未排期` + 「无计划日期，无法判定延期」（**不上红**） |
| `people[].owner_name` | 工件内 owner 字段 → `git shortlog -sne --no-merges`（项目级）/ `git log --format='%an' -- <限定路径>`（条目级）；**回填规则见 [people-encoding.md](people-encoding.md) 2.4** | `未记录` |
| `work_items[].actual_start` / `actual_end` | 工件内明写的完成日期 → **不得**用提交日期冒充（§5.2 红线） | `-`（无实际日期） |

**三条纪律**：

1. **不跳级臆造**：只能用仓内**实际存在**的材料，且每条溯源到具体位置（文件#章节 / `git:<命令要点>`）；找不到就退合法终态，**不许"推理"出一个值**。
2. **每条推导都留痕**：值后加 `（推断）`，记录 `inferred_from: repo:<repo_id> <命令要点>`，进入引擎 `inferred_fields` 与报告 `## 元信息 · 推断字段清单`。
3. **只读红线不变、范围不得扩大**：对仓库只读取、不写入、不"整理修复"；一次授权只允许**该字段**的定向查询，**不得**顺手扫描其它内容或扩大到未授权字段。

## 2. 记忆级（T2）定向取材规程

**仅在字段被 `derive_fields` 授权、且表单里该字段为空时**才定向读取下列材料，并且**只读该字段需要的那一处**（例如只为 `features[].status` 读 features.md 的状态列），**不通读整套记忆工件**：

> 下表的「位置」列写的是**材料类别 + 一种常见布局的示例路径**。`.specify/…` 这套布局只在采用该框架的仓里成立；**其它仓的等价材料在别处**（如 `docs/` 下的原则说明、独立的特性台账、词汇表）。按类别找材料，**不要**因为示例路径不存在就断言"该仓没有这类材料"。

| 材料类别 | 位置（示例布局） | 取材命令/方法 | 派生到 | 溯源写法 |
|------|------|---------------|--------|----------|
| 项目使命/原则 | 项目原则文档（示例：`.specify/memory/constitution.md`） | 读抬头段 + 原则标题 | 结构 A 项目概览（背景、范围边界） | `<原则文档>#<原则名>` |
| 特性清单 + 状态 | 特性索引（示例：`.specify/memory/features.md`） | 读表格数据行（列序以该文件表头为准） | 特性清单表格、结构 B 顶层分支 | `<特性索引>#<行标识>` |
| 特性详情 | 单特性详情文档（示例：`.specify/memory/features/<ID>.md`） | 读概述 / 关键变更 / 实现说明 / 相关文件 / 状态跟踪等小节 | 结构 B 任务层佐证、功能分解叶子佐证 | `<特性详情>#<小节>/<条目序号>` |
| 领域词汇 | 术语表（示例：`.specify/memory/glossary.md`） | 读规范词与释义列 | 概览与特性叙述的术语校准（避免把内部代号当特性名） | `<术语表>#<术语>` |

**状态列 → 三态映射：唯一权威是 [consistency-rules.md](consistency-rules.md) §1.1，本节不另写一份映射表。** 把索引里的**状态原文字面量**如实落进表单 `features[].status`，映射由引擎按 §1.1（及表单 `status_map` 覆盖）执行；延期态**不来自**状态字面量，由引擎结合排期字段判定后作为第四态 `delayed` 输出。

- **不要凭直觉理解状态词**：同一个词在不同项目里含义可能相反（典型如"已实现"到底算 completed 还是 in-progress，取决于该项目生命周期是否把"评审/上线"算在内）。特性详情里的**状态跟踪小节**通常写着该项目对每档状态的**本地定义**，判定前先读它；本地定义与 §1.1 默认表冲突时，**以本地定义为准**并写进表单 `status_map`、同时把实际映射表落进 `## 元信息 · 状态映射`。
- **特性详情只作佐证，不新增条目**：特性详情里的关键变更与相关文件小节可为**表单中已声明**的工作项补上一句佐证（如实现落点、评审记录），但**不得**据此新增工作项或替代表单的分解树——分解树的条目集合由表单唯一确立（覆盖闭合等式的候选全集也以表单为准）。

## 3. 代码与构建级（T3）定向取材规程

**仅当**某字段（如 `project.project_desc`、`features[].feature_name`/`status`）被 `derive_fields` 授权、且更强的仓内佐证都不存在时，才用语言清单与入口定义做**定向补语**：从语言清单取一行 `description`、从入口/子命令定义取用户可见能力名。**禁止**为了"补全功能分解"而通读模块树——**工作项与阶段来自表单**，不由代码结构生成。

### 3.1 语言无关的取材点判据（先用判据定位，再查 3.2 的生态对照表）

**规程本身与语言无关**：无论目标仓是什么语言，被授权字段的取材点都落在下列四类之一。**先按判据定位，再到 3.2 查该生态的具体文件/语法**；3.2 未列出的生态**同样按本表判据处理**（不得因为"表里没写"就跳过或改用全仓扫描）。

| 取材点类别 | 语言无关判据（怎么认出它） | 可派生的字段 | 溯源写法 |
|------------|----------------------------|--------------|----------|
| **C1 包/工程清单** | 仓根（或工作区根）下声明包名、版本、一句话描述、依赖的那个元数据文件 | `project.project_desc`（描述字段）、技术栈叙述 | `<清单文件>#<段名>` |
| **C2 入口定义** | 清单里声明的可执行入口，或约定入口文件；决定项目形态（有入口 = CLI/服务类，无入口 = 库类） | 项目形态判断、特性派生路线（§4） | `<入口文件>#<符号>` |
| **C3 模块/包结构** | 源码根之下的一层目录或模块声明列表（**只取一层，不递归遍历**） | 功能分解的**叶子佐证**（不新增工作项，见 §5.3） | `<源码根>/<模块>` |
| **C4 构建与 CI 定义** | 构建入口（任务化构建文件或清单里的脚本段）与 CI 流水线定义目录 | 状态证据分级（§6 的 E2/E3/E4） | `<构建文件>#<目标>` |

**三条语言无关的纪律**：

1. **只取被授权字段需要的那一类**：授权了 `project.project_desc` 就只读 C1 的描述字段，**不**顺手读 C3 模块树；
2. **C3 只取一层、只作佐证**：模块名要用业务语言重述后才能进图，且必须在图说注明"分解依据 = 代码模块结构（推断）"；**代码结构不产出工作项**；
3. **清单缺字段就按 §1.1 的降级链退到下一级佐证**（如清单无描述字段 → 退 T5 的 README 引言），**不推理、不编造**。

### 3.2 各生态的等价取材点（**示例对照表，非穷举**；未列出的生态按 3.1 判据处理）

| 语言/生态 | 概览元数据 | 入口 | 模块树 | 子命令定义（CLI 特性） | 构建/依赖 |
|-----------|-----------|------|--------|------------------------|-----------|
| **Rust** | `Cargo.toml` `[package]` name/version/description/edition | `src/main.rs`、`src/bin/*.rs`、`[[bin]]` | `src/` + `mod` 声明 | `#[derive(Subcommand)] enum` 变体、`#[command(name)]`（clap） | `[dependencies]`、`Makefile`、`build.rs` |
| **Python** | `pyproject.toml` `[project]` name/version/description（或 `setup.cfg`/`setup.py`） | `__main__.py`、`[project.scripts]` 控制台入口 | 含 `__init__.py` 的包目录树 | argparse `add_subparsers()`+`add_parser("名")`、click `@cli.command()`、typer `@app.command()` | `[project.dependencies]`/`requirements*.txt`、`tox.ini`、`noxfile.py` |
| **Node** | `package.json` name/version/description | `main`/`bin`/`exports` 字段指向的文件 | `src/`/`lib/` 目录树、`exports` 子路径 | commander `.command("名")`、yargs `.command()`、oclif `commands/` 目录 | `dependencies`/`scripts` 字段、lockfile |
| **Go** | `go.mod` module 路径 + `go` 版本 | `package main` + `cmd/<名>/main.go` | 目录=包，`cmd/`/`internal/`/`pkg/` | cobra `&cobra.Command{Use:"名"}`+`AddCommand`、urfave/cli `cli.Command{Name}` | `go.mod` require 块、`Makefile` |

- **入口决定项目形态**：有 `[[bin]]`/`cmd/`/`bin`/`console_scripts` → CLI/工具类项目，特性优先从子命令派生（§4）；只有 `lib.rs`/包无入口 → 库项目，特性从公共 API（`pub fn`/`__all__`/`exports`）派生。
- **模块结构只作叶子佐证，不产出阶段/工作项**：阶段与工作项的集合由**表单**唯一确立（§5.3、[work-breakdown.md](work-breakdown.md)）。被授权时，代码模块可以为**表单中已声明**的工作项补一句实现落点佐证；命名一律用业务语言重述（**不直接拿文件名当节点名**），并在图说注明"分解依据 = 代码模块结构（推断）"。**不得**据模块目录"自然分组"生成阶段或主题分支——那会长出表单里没有的条目，使覆盖闭合等式与"无孤儿条目"纪律双双失效。

## 4. CLI 项目的特性派生规则（子命令 = 用户可见能力）

CLI 的**子命令**是最贴近"用户可见能力"的特性来源，比模块树更接近产品语言。规则：**一个子命令映射为一条特性行**，描述取自子命令的文档字符串/help 文本，状态按 §6 证据分级判定。

| 框架 | 子命令定义位置 | 提取规则 | 溯源写法 |
|------|----------------|----------|----------|
| Rust · clap(derive) | `#[derive(Subcommand)] enum X { 变体 {...} }` | 每个 enum 变体 = 一个子命令；`#[command(name = "x")]` 覆盖显示名（否则变体名转 kebab-case）；变体上方 `/// 文档` = 描述；`#[arg(...)]` = 参数 | `src/main.rs#enum Command::Console` |
| Rust · clap(builder) | `Command::new("x").subcommand(...)` | 每个 `.subcommand(Command::new("名"))` = 子命令 | `src/cli.rs#subcommand("console")` |
| Python · argparse | `sub = p.add_subparsers(); sub.add_parser("名")` | 每个 `add_parser("名")` = 子命令；`help=`/`description=` = 描述 | `cli.py#add_parser("console")` |
| Python · click/typer | `@cli.command()` / `@app.command()` | 每个装饰的函数 = 子命令；函数名或 `name=` = 显示名；docstring = 描述 | `cli.py#cmd_console` |
| Node · commander | `program.command("名")` | 每个 `.command("名")` = 子命令；`.description()` = 描述 | `index.js#command("console")` |
| Go · cobra | `&cobra.Command{Use: "名", Short: "..."}` | 每个 Command 且被 `AddCommand` = 子命令；`Use` 首词=名、`Short`=描述 | `cmd/console.go#cobra.Command` |

**提取结果的落笔形态（示例，字面量随项目而变）**——每个子命令一行，逐条带溯源：

| 子命令 | 定义位置的符号 | 描述（取自文档注释 / help 文本） | 溯源 |
|--------|----------------|----------------------------------|------|
| `<子命令名>` | `<入口文件>` 里的 `<变体/函数/Command 对象>` | `<该子命令的一句话描述原文>` | `<入口文件>#<符号>` |

> 上表是**形态模板**：子命令的数量、名称与描述**完全由目标仓的代码决定**，必须逐条实测得出，**不得**沿用任何项目的清单。

**红线 · 代码是子命令的唯一权威**（与"代码是唯一事实源"一致）：
- **help 文本/README 与代码不一致时以代码为准**：文档里的命令列表常滞后于代码（少列、错列、名字变了都很常见）。派生特性时**以代码里实际注册的子命令集合为准**，README/help 视为可能过时的 T5 材料；差异要在叙述中注明冲突（形如"`<子命令>` 存在于 `<入口文件>` 但未列入 README 的 help 示例（README 待更新）"）。
- 反向亦然：README/help 里描述、**代码里不存在**的子命令**不得**作为特性（那是路线图愿望，归 not-started 并溯源到文档而非代码）。

**子命令特性与 T2 特性索引的对账**：两者都在时以**特性索引的划分为主线**（它是人工聚合的产品视角，常把若干相关子命令归并为一条特性），CLI 子命令作为该特性下的能力点/佐证；**仅 T3 有、T2 无**时才让"一子命令 = 一特性"。

## 5. 版本历史级（T4）取材规程与红线

git 能提供**时间锚点与作者**，但**不能**提供工期、里程碑与进度。**提交极少、零标签的项目尤其要守住红线**——材料越稀疏，把提交数/提交日期当成进度和排期的诱惑越大。

### 5.1 git 能得到什么

| 材料 | 命令（只读，日期即取 `yyyy-mm-dd`） | 派生到 |
|------|--------------------------------------|--------|
| 项目起止锚点 | `git log --reverse --date=short --format='%ad %s' \| head -1`（首提交）；`git log -1 --date=short --format='%ad %s'`（末提交） | 项目活跃区间（推断） |
| 每次提交的范围 | `git log --date=short --format='%h %ad %s'`；`git show --stat <hash>` | 提交→工作项映射（§5.3） |
| 作者/负责人推断 | `git shortlog -sne --no-merges`（全局）；`git log --format='%an <%ae>' --no-merges -- <路径>`（路径主要作者） | 结构 D 人员（值后加 `（推断）`，见 data-model.md 第 4 节） |
| 标签（发布锚点） | `git tag`；`git for-each-ref --format='%(refname:short) %(creatordate:short)' refs/tags` | 里程碑锚点（**仅当存在**） |

> **四条命令的输出全部因项目而异**：提交数可能是个位数也可能是四位数、标签可能为空、作者可能只有一个也可能几十个。这些值**只能实测**，且**只能**派生到上表右列写明的那几项——**不得**据此推出工期、进度或里程碑（§5.2、§5.4）。单一作者情形的处置有确定性裁决规则，见 [people-encoding.md](people-encoding.md) 2.4。

### 5.2 git **不能**得到什么（红线）

- **工期**：提交间隔 ≠ 任务工期（一次提交可能攒了几周的活，也可能是一分钟的 typo 修正）。不得把某个提交区间（形如 `<首提交日>..<末提交日>`）当作某任务的"耗时 N 天"。
- **进度百分比**：提交数、代码行数**都不是**完成度。3 次提交不代表"完成 3/N"。
- **里程碑**：见 §5.4。

### 5.3 提交**不产出**工作项（只作已声明工作项的佐证）

- **红线**：工作项集合由**表单 `work_items[]`** 唯一确立。**禁止**用 git 提交生成工作项条目——否则分解树会长出表单里没有的条目，覆盖闭合等式与"无孤儿条目"纪律双双失效。
- **允许的用法**：为**表单中已声明**的工作项补一条实现佐证（形如"该项的实现落在 `git:<hash> <提交主题>`"），溯源写 `git:<hash> <主题>`，并标 `inferred_from: repo:<repo_id> git:log`。
- **连佐证都不作的提交**：`.gitignore`、格式化、typo、合并提交等非实质提交。
- **仍不可得的**：工期、进度百分比、里程碑（见 §5.2、§5.4）。

### 5.4 「提交 ≠ 里程碑」红线

- **里程碑必须有锚点**（[milestones.md](milestones.md)「锚定与状态规则」）：绝对日期、git 标签、发布记录、验收/verification 节点、或用户明述。**一次普通提交不构成里程碑锚点。**
- **零标签 + 无发布/验收记录 ⇒ 里程碑可能不可派生**：无 git 标签、无发布记录、无验收节点、特性索引也无"状态跃迁事件"记录 → **没有可信里程碑锚点**。此时按 [milestones.md](milestones.md) 的退化路径处理：`## 项目里程碑` 节**不出独立视图**，写明"本项目材料未提供里程碑锚点（无 git 标签、无发布记录、无验收节点、无用户明述里程碑）；里程碑维度暂缺"，并记入 `## 元信息`。
- **禁止用提交数/特性数硬造里程碑**：不得把"第 N 次提交""有 k 个特性已实现"包装成 M1/M2。
- **允许的弱替代（须标推断且有防御性日期）**：若确需一个时间参照，可用"当前代码基线（截至末提交 `yyyy-mm-dd`）"作为**叙述性时间点**写进概览/进展叙述，但它**不是**里程碑菱形，不进里程碑跟踪表。

## 6. 构建 / CI 作为状态证据（证据强度分级）

缺 T1（无 tasks.md `[x]`）时，"某能力是否已实现"要靠证据推断。**证据有强弱之分，必须分级标注**——把"代码存在"当成"已完成"是本回退向最容易犯的错。

> **分级判据与语言无关**；下表「取材位置」列写的是**类别**（按 3.1 的 C1–C4 判据定位），具体文件名随生态而变，套用前按 3.2 查该生态的等价物。

| 证据等级 | 信号 | 取材位置（类别） | 支持的状态结论 | 标注写法（`<>` 按实际填） |
|----------|------|------------------|----------------|----------|
| **E1 最弱·存在性** | 源文件/模块/子命令存在 | C3 模块结构、C2 入口 | 「已编码，未验证」——**不足以**判 completed | `状态=in-progress? 证据=E1 代码存在(<模块文件>)` |
| **E2 弱·可构建** | 构建入口存在且能干净构建 | C4 构建定义、C1 清单 | 能构建，仍不足以判功能正确 | `证据=E2 可构建(<构建文件>#<目标>)` |
| **E3 中·有测试** | 测试/夹具存在且有可跑的测试入口 | C4 的测试目标、测试目录/夹具文件 | 行为有回归覆盖 | `证据=E3 单测(<构建文件>#<测试目标> + <夹具文件>)` |
| **E4 中强·CI 门禁** | CI 流水线定义存在且跑构建+测试 | C4 的 CI 定义目录 | 持续验证 | `证据=E4 CI(<流水线文件>)` |
| **E5 强·显式完成态** | 任务清单已勾选 + 验收记录（T1），或特性索引标"已实现"档 + 特性详情里的评审记录（T2） | T1 / T2 工件 | 可判 completed | `证据=E5 特性索引<状态> + 评审(<特性详情>#<评审节>)` |

**规则**：
- **判 completed 至少要 E3，且优先引用能拿到的最高等级**；只有 E1（光有代码）时状态最多写 in-progress 或标注"仅代码存在、无测试/评审佐证"。
- **"代码存在" vs "任务已勾选"是两码事**：E1 是"写了"，E5 是"验收了"。回退取材时若只有 E1/E2，**不得**因为"文件在那儿"就判 completed。
- **CI 缺席也是证据**：找不到 CI 流水线定义（目录不存在、或存在但不含流水线文件）→ E4 不可用，须在元信息注明"无 CI 门禁佐证"。
- **证据链要逐条写出等级 + 取材位置**，缺哪一级就明写缺（形如 `E5(<出处>) + E3(<出处>)，无 CI 门禁（E4 缺失）`）。**能拿到哪几级完全取决于目标仓**，不存在"通常有 E3/E5"这种默认假设。

## 7. 端到端示例：一个被授权三个字段的仓

> **本节是流程示例，不是任何具体项目的事实**：仓名、路径、字段值都是占位符（`<…>`），**换个项目全部会变**。可移植的只有"授权 → 定向取一处佐证 → 留痕 → 未授权维度诚实缺席"这条流程。

**前提（门已打开）**：表单里 R 档已齐备（`project_name`、`baseline_date`、`work_items[]` 非空），并声明了

```yaml
project:
  repos:
    - repo_id: <repo-id>              # 示例：主仓的短标识
      repo_path: <仓库路径>
      repo_role: "<该仓在项目中的角色>"
      derive_fields: ["project.project_desc", "features[].status", "people.owner_name"]
```

即**只有这三个字段**允许从该仓定向推导；其余字段一律以表单为准或走合法终态。本示例演示这三个字段怎么取到佐证：

1. **`project.project_desc`（已授权）**：按 §1.1 的降级链先读 C1 包清单的描述字段；该字段缺失 → 退到 T5 的 README 引言，取其中一句定位原文。记 `inferred_from: repo:<repo-id> <实际出处>`。
2. **`features[].status`（已授权）**：读 T2 特性索引的状态列（**行数与各状态的分布实测得出**），按 [consistency-rules.md](consistency-rules.md) §1.1 由引擎映射；证据强度按 §6 逐条标注（能拿到哪几级由该仓实际情况决定，缺的级别明写缺）。记 `inferred_from: repo:<repo-id> <索引文件>#<行标识>`。
3. **`people.owner_name`（已授权）**：工件内无 owner 字段 → 跑一次 `git shortlog -sne --no-merges` 取作者名册，**回填规则按 [people-encoding.md](people-encoding.md) 2.4 的确定性裁决**（单作者/多作者、项目级/条目级各自怎么落，不由执行器临场决定）；覆盖率仍取引擎 `people.coverage_formula`。
4. **里程碑日期（**未授权**）**：不查 `git tag`、不查 CHANGELOG。表单 `milestones[]` 为空 ⇒ `## 项目里程碑` 按 [degradation.md](degradation.md) 第 4 节走完全缺失形态（保留章节 + 材料声明），**不得**把提交/版本号/"某特性已实现"升格为里程碑。
5. **细粒度进度与工期（**未授权**）**：不读任务清单勾选、不用提交日期当排期。表单未提供 `checks`/`planned_end` ⇒ 引擎给 `progress_pct=null` 与 `unknown-schedule`，报告写 `-（无可计数依据）` 与「无计划日期，无法判定延期」，甘特按判据不出图。

> 这份示例说明 opt-in 模型的价值：**表单 R 档齐备就能出报告，repo 只为被授权的那几个字段补了佐证**；未授权的维度诚实地"缺席可见"，既不扫全仓、也不拿提交数硬造进度与里程碑。

- [ ] **门的检查**：表单未声明 `project.repos[]` 时，本次运行**对任何仓库零查询**（无 `git`、无文件读取、未跑 `detect-project-sources.py`）
- [ ] 声明了 `repos[]` 时，每次查询都能指名到「哪个 `repo_id` + 哪个被 `derive_fields` 授权的字段」；**未对未授权字段做任何查询**
- [ ] 查询形态合规：单条只读命令 + 限定路径，**无全仓扫描、无目录遍历、无批量统计**（未出现"通读模块树/遍历 specs"这类动作）
- [ ] 每条 repo 推导值都带 `（推断）` 与 `inferred_from: repo:<repo_id> <命令要点>`，且已进入引擎 `inferred_fields` 与 `## 元信息 · 推断字段清单`
- [ ] 一个字段只取**一处**佐证（按 §1.1 顺序，找到即止），未叠加多处佐证凑说法
- [ ] **多 repo**：同一 `item_id` 未在多个 repo 中重复定义；跨仓冲突**未合并/未取平均**，已保留表单值并把冲突写入 `## 元信息`
- [ ] **repo 未被用来凑 R 档**：必填项缺失走的是阻断出表单，不是"去仓里找一个值填上"
- [ ] 里程碑红线：只有材料明确标注的发布/评审/验收/阶段完成节点才成为里程碑；普通提交、版本号、"某特性已实现"**未**被升格（§5.4）

- [ ] `## 元信息` 登记了：本次授权了哪些 `repo_id` × 哪些 `derive_fields`、实际取到了什么、哪些字段仍缺
