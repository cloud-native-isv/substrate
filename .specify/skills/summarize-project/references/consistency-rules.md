# 判定规则全集与自洽性门禁 (Consistency Rules)

本文档是 `summarize-project` 的**判定规则单一权威**与**落盘前自洽性门禁**。其他层参考文档只描述"呈现什么"，一切**"如何判定"**（状态映射、聚合、计数、纳图、逾期、消歧）与**"如何保证数字自洽"**的规则集中在此，避免同一规则在多处出现分叉版本。

工作流主框架见 [../SKILL.md](../SKILL.md)；记录层 Schema 见 [data-model.md](data-model.md)；跨层图表公约见 [reporting-playbook.md](reporting-playbook.md)。

**适用纪律**：本文档的规则是**判定的唯一依据**。层参考文档与规则冲突时以本文档为准；本文档未覆盖的判定视为规则缺口 → 按第 9 节「规则缺口处理」办，**不得**由执行者临场自造判定并静默落笔。

**计算下沉纪律（本轮新增，见 §0.1）**：本文档定义**语义与呈现契约**，而**日期与进度的计算由 `scripts/progress-engine.py` 独家执行**——Markdown（本文档、其他层参考文档、报告正文）里出现"比较两个日期""算天数差""算百分比""求平均"这类**可执行算式或判定步骤**本身即缺陷，应改写为"取引擎 `<字段>`"。

## 0. 基准日唯一化与"计算下沉"总则

### 0.1 计算下沉：日期与进度的唯一计算者是 `progress-engine.py`

**本文档（以及全部 `references/`、报告正文）不承载任何日期/进度计算逻辑**：不比较两个日期的先后、不算天数差、不判延期、不算百分比、不做聚合平均。这些一律由技能自带引擎完成——引擎**从 SQLite 关系模型读取，用 SQL 完成查询与聚合**（天数差 `julianday`、分组 `GROUP BY`、排序 `ORDER BY`）：

```bash
python3 ${SKILL_HOME}/scripts/project-db.py --db <交付目录>/data/project.db \
  --load <交付目录>/data/project-input.yaml          # 表单 → 数据库（约束即校验）
python3 ${SKILL_HOME}/scripts/progress-engine.py \
  --db <交付目录>/data/project.db --baseline <D0> --out <交付目录>/data/engine-out.json --summary
python3 ${SKILL_HOME}/scripts/progress-engine.py --print-schema   # 字段契约与最小示例
```

- **输入**：**关系模型 `<交付目录>/data/project.db`**——七个实体各一张表（`project` / `phases` / `work_items` / `milestones` / `people` / `features` / `sources`，另有依赖联结表 `work_item_deps` 等），字段名即列名、也是实体间外键。**字段类型、取值域与关联完整性由数据库约束保证**（权威 = `schema/project.sql`，业务含义见 [required-info.md](required-info.md)）；装载即校验，约束违规进不了模型。
- **中间产物纪律**：数据库与引擎输出都是**派生中间产物**，落在**交付目录的 `data/` 子目录**（`project.db` / `engine-out.json`），默认每次生成报告时**从事实源重建**并随交付目录整体刷新（用户要求基于历史库演进时用 `project-db.py --update`，UPSERT + 变更摘要，元信息注明）；**绝不写入被总结的目标项目的管理工件**（只读红线 §10 的写入白名单见 W-3「计算与校验中间产物」，其范围仅限交付目录）。
- **引用纪律**：报告与各层参考文档只能**引用引擎输出字段**（`status` / `schedule_status` / `delay_days` / `progress_pct` / `progress_formula` / `gantt.today_offset_days` / `milestones.*` / `coverage.*` / `diagnostics.declarations`），**不得**在文档或报告里重述算法、重算一遍或手工改判。
- **可复现**：同一输入 + 同一 `--baseline` 必得同一输出（引擎不读系统时钟）；`## 元信息` 记一行引擎运行记录（命令、输入文件、基准日）。
- **字段名是内部标识**：`unknown-schedule` 等字段值只出现在 `## 元信息` 与技能内部文档；面向读者的五个章节写业务语言（见 reporting-playbook §1.7）。

### 0.2 基准日 D0

全报告**只有一个基准日** `D0`：

- `D0` = 本次运行的报告生成日期（写入 `## 元信息 · 生成日期`），并**逐字**作为 `--baseline` 传给引擎（引擎要求零填充 `yyyy-mm-dd`，格式不符直接报错）。
- `D0` 是**唯一**的 "today"：甘特 `today` 线、里程碑达成/逾期判定、"数据截至哪一天"的图说表述、进度叙述中的"当前"，全部来自同一次引擎运行。
- 各图**不得**各自取日期；`today is N days after start` 的 `N` **取引擎 `gantt.today_offset_days`**（不在文档/报告里做减法），不依赖渲染环境时钟。
- 若用户指定"截至某日"的汇报口径，则 `D0` 取该日期、同样传给 `--baseline`，并在元信息注明「基准日由用户指定」；此时不得再混用生成日期。

核对（第 8 节 CG-8）：报告中出现的所有"基准日 / today = yyyy-mm-dd"字面量必须完全相同，且等于引擎输出的 `baseline`（其来源见引擎输出 `baseline_source`：`--baseline` 或表单 `project.baseline_date`）。

### 0.3 输入契约：判定的对象是**关系模型的列**，不是仓库工件

本文档定义的一切判定都作用在**已装载进数据库的关系模型**（`data/project.db`）的列上：状态映射的输入是 `work_items.status` / `features.status` 的原文字面量，勾选计数是 `checks_*` 四列，日期是 `planned_*`/`actual_*`/`planned_date`，层级是 `phase_id`，依赖是 `work_item_deps` 联结表。

- **字段类型、取值域、关联完整性的唯一权威是 `schema/project.sql`（DDL，由数据库约束强制）**；字段的业务含义与三档必填性 R/I/O 见 [required-info.md](required-info.md)。本文档不重复定义字段。
- **输入侧门禁分两段**：① **机械约束**（外键断裂 / ID 重号 / 日期非法 / 枚举越界 / 无出处数字）由**数据库在装载时拒绝**（`project-db.py --load`，退出码 3，报可读原因）；② **R 档业务必填组合**（`project_name` / `baseline_date` / `work_items` 与 `milestones` 至少一组非空）由 `scripts/validate-project-input.py` 检查（同为退出码 3 阻断）。任一段不过，都不进入本文档的任何判定。
- **§4、§7、§11 中出现的 `specs/*/tasks.md`、`features.md` 等仓库工件命令，只适用于 repo opt-in 且相应字段被 `derive_fields` 授权的情形**（规程见 [source-tiers.md](source-tiers.md)）——它们**不是**默认路径。未 opt-in 时，工作项单元恒为 `work_items` 表（必要时叠加 `features` 表），候选全集 `C` 亦以库中数据为准。

## 1. 状态映射全集（源状态字面量 → 基础三档）

> **第四态 `delayed`（延期）不在本节映射范围内**：源状态字面量只能给出 `completed / in-progress / not-started` 三档；
> "是否延期、延期几天"由**进度引擎脚本**结合排期字段判定并输出（`status = delayed` + `delay_days`），
> 呈现层只把该字段编码成颜色与符号（浅红 `#EF9A9A` + `⚠`，见 [reporting-playbook.md](reporting-playbook.md) §1.1 与
> [people-encoding.md](people-encoding.md) 第 1.0 节）。**本技能文档与报告正文一律不做日期先后比较、不算天数差。**

> **本节是语义契约，不是执行步骤**：下列各表定义"哪个字面量算哪一态"，供报告 `## 元信息 · 状态映射` 原样呈现给读者复核。**映射的执行在引擎内**（`progress-engine.py` 内置同一张映射表）；目标项目自身定义不同时，把差异写进表单的 `status_map` 键（入库为 `status_map` 表）覆盖，**不要**在文档或报告里另判一遍。未映射字面量由引擎收集到 `diagnostics.unmapped_statuses`（`--strict` 下直接报错），条目状态记 `unknown`。

### 1.1 引擎内置的默认生命周期映射（示例口径；目标项目自身定义优先）

下表是**引擎内置的默认映射表**，取自一种常见的 SDD 框架口径（5 态有序生命周期 `Draft → Planned → Implemented → Ready for Review → Completed`，其权威在该项目自己的宪章/流程定义里）。**它是默认值，不是对所有项目成立的事实**：目标项目定义了不同的状态集或不同的语义时，**以目标项目的定义为准**，用表单 `status_map` 覆盖（见本节末的两条纪律）。默认映射的关键语义——**`Planned` 表示"规格已批准、实现已排期"，代码尚未动工，映射为 `not-started`**（把 `Planned` 映为 `in-progress` 与生命周期语义矛盾）：

| 源状态字面量 | 生命周期含义（该框架的原文口径） | 三态 | 进度% 默认 | 备注 |
|--------------|------------------------------|------|-----------|------|
| `Draft` | Feature defined, spec in progress | `not-started` | 0 | 规格在写，实现未启动 |
| `Planned` | Spec approved, implementation scheduled | `not-started` | 0 | **已排期 ≠ 已开工** |
| `Implemented` | Code changes merged to feature branch | `in-progress` | 见 §1.4 | 已交付代码，生命周期未闭合 |
| `Ready for Review` | PR open, tests passing | `in-progress` | 见 §1.4 | 进度高于 Implemented，仍未闭合 |
| `Completed` | Merged to main, deployed | `completed` | 100 | 终态 |
| `Deferred` / 任务标记 `[~]` | 本轮不做（延后项是一等状态，不是"未开始"） | 见 §1.3 | — | **不得**当作 `[ ]` 或 `[x]` |

- 若目标项目的流程定义与上表不同，**以目标项目的定义为准**，并把实际映射表原样写入 `## 元信息 · 状态映射` —— 映射表是报告的一部分，读者可复核。
- `Implemented` / `Ready for Review` 映射为 `in-progress` 时，**必须**同时按 §5「已交付但记录未闭合」检查记录侧闭合度。

### 1.2 任务勾选标记映射（`tasks.md`）

| 标记 | 三态 | 说明 |
|------|------|------|
| `[x]` `[X]` | `completed` | **大小写两种写法都必须计入同一桶**。两者的实际比例**因项目而异**，必须由统计命令/数据库**实测得出**，**不得假定哪一种占多数**——只匹配小写（或只匹配大写）在某些项目会漏掉绝大部分已完成项 |
| `[ ]` | `not-started` | 未开始 |
| `[~]` | `deferred` | 独立桶，见 §1.3 |
| 其他单字符（如 `[P]`） | **非状态标记** | 并行/分组等元标记，**必须从状态统计中排除**并在口径中声明。哪些字符在本项目属于非状态标记、各出现多少次，一律由 §7.2 的统计命令实测，不得凭记忆列举 |

> **可移植性纪律（见 [portability.md](portability.md)）**：本节只固定"哪个字面量算哪一态"这条**项目无关的规则**。任何具体计数（某个标记出现几次、大小写各占多少）都是**某个项目某次运行的实测值**，随项目而变，只能来自脚本/数据库输出，**不得**写进规则、也不得作为下一个项目的默认假设。

### 1.3 `deferred` 的处理（第四桶，不并入三态）

- 记录层单独成桶 `deferred`，**不得**静默归入 `not-started`（会虚增待办）或 `completed`（会虚增完成）。
- 呈现层：`deferred` 条目在 WBS/甘特中沿用 `not-started` 灰色，但名称行尾追加 ` ~`（波浪标记），图例增一行 `~ = 本轮延后（deferred）`。
- **所有完成度算式必须明写分母是否含 deferred**（见 §7.3）。

### 1.4 未映射状态的兜底（fail-loud，禁止静默归类）

源材料出现上表之外的状态字面量时：

1. 记录层状态列填 `unknown`，并在同行来源列后追加 `（原文：<字面量>）`；
2. 呈现层：沿用 `not-started` 灰色，名称行尾追加 ` ※`，图例增一行 `※ = 状态未映射（原文见记录表）`；
3. `## 元信息 · 状态映射` 中列出全部未映射字面量及出现次数；
4. 未映射条目**单独计数**，绝不折算进三态的任何一个百分比（分母中单独列出）。

> **禁止**把不认识的状态"猜"成三态之一。`unknown` 是合法且诚实的终态。

### 1.5 外部材料（看板 / issue 导出 / 路线图）状态映射

外部材料（看板、issue 导出、路线图）须先落一张 `原文状态 → 三态` 的**显式映射表**并写入元信息；表未建立不得开始映射。常见对照（仅作起点，须按项目确认）：

| 常见原文 | 三态 |
|----------|------|
| Done / Closed / Resolved / 已上线 | `completed` |
| In Progress / Doing / In Review / 开发中 | `in-progress` |
| To Do / Backlog / Open / Todo / 待开始 | `not-started` |
| Blocked / On Hold / 挂起 | `in-progress` + 在叙述中标注阻塞（不新增状态色） |
| Won't Do / Cancelled / 已取消 | **移出统计**（不入三态、不入分母），在元信息声明剔除数量 |

## 2. 阶段（父项）状态与进度聚合：**取引擎聚合结果**

**语义契约（一句话三条，执行在引擎内）**：

```
完成   ⇔ 子项全部 completed
未开始 ⇔ 子项全部 not-started
其余（任何混合、任何 in-progress） ⇒ in-progress     ← 含"部分完成 + 部分未开始"，绝不画成未开始灰色
```

`deferred` / `unknown` 子项不参与上述判定（旁路），但父项须继承标记：存在 deferred 子项 → 父项图说注明数量；存在 unknown 子项 → 父项名称追加 ` ※`。

**呈现取值（不在文档里算）**：

| 呈现需要 | 引擎字段 | 呈现要求 |
|----------|----------|----------|
| 阶段状态（WBS 颜色、表格状态列） | `items[].status`（父项已聚合，`status_source=aggregated`） | 与子项呈现互不矛盾；引擎标出的"记录冲突"须写进呈现物（RC-4） |
| 阶段进度% | `items[].progress_pct` + `progress_formula` | **算式串照抄** `progress_formula`（等权平均，分子分母齐备）；`null` → 写 `-（无可计数依据）`，不给任何数字 |
| 阶段进度的分母与排除项 | `items[].aggregation.denominator` / `excluded_unquantified` / `excluded_ids` | 图说注明「N 项进度未量化，未计入阶段进度」（N 取 `excluded_unquantified`） |
| 阶段起止日期（甘特阶段条/分隔带） | 父项自身无日期时引擎按子项包络给出 `planned_start`/`planned_end`，并置 `dates_derived=true` | 呈现时注明该阶段日期为子项包络推出 |

- 非等权口径只能通过在表单里给出权重（入库为 `weight` / `weight_source` 列）来表达，**不得**在报告里手写加权算式（§7.4 的登记要求不变）。
- 若引擎给出 `progress_pct = null`（排除后分母为 0），报告一律走诚实空值，**不得**回退成"手工估个数"。

## 3. WBS 节点计数口径与规模处理

### 3.1 计数口径（消除「≤15」的解释歧义）

「单图节点 ≤15」的**计数对象定义**：

- **计入**：`@startwbs` 中所有**深度 ≥2** 的节点，即以 `**`、`***`、`****`… 开头的节点行（阶段节点 + 任务节点 + 子任务节点全部计入）。
- **不计入**：① 根节点（单个 `*` 行）；② `<style>`/`legend`/`endlegend` 及其内容；③ 节点内的 `\n【负责人】` 第二行（属同一节点）；④ 节点标题上的 ` ◆Mn` / ` ~` / ` ※` 标记；⑤ 注释行（`'` 开头）。

可执行核对命令：

```bash
# N = 本图计入节点数（根节点不计）
N=$(grep -cE '^\*{2,}' wbs.puml); echo "WBS 节点数 N=$N（阈值 15）"
# 各层级分布（便于判断拆分切口）
grep -oE '^\*+' wbs.puml | awk '{print length($0)" 星级"}' | sort | uniq -c
```

阈值：`N ≤ 15` 一图呈现；`N > 15` 必须走图集拆分（§3.3）。软建议：`N ≤ 12` 阅读体验最佳。

### 3.2 禁止用"合并"来降节点数（硬红线）

> **节点上限约束的是"每张图"的容量，不是"项目"的规模。**

- **禁止**为了让节点数落到 15 以内而把多个真实工作项揉成一个（例如把 31 个 spec 压成 10 个"工作项"）——这是**信息丢失**，属违规呈现，而不是合法简化。
- 规模超限的唯一合法出路是**图集拆分**（§3.3）或**用户显式指定的粒度限定**（此时按 §4.4 保证信息不丢）。
- 落盘前核对：报告中呈现的工作项数量必须能与记录层（结构 B）行数对上；结构 B 行数必须能与事实源条目数对上（§8 CG-7）。

### 3.3 图集拆分的确定性切分规则

`N > 15` 时按固定算法拆分，不凭感觉：

1. **概览图**：根 + 全部阶段节点（只到深度 2）。若阶段数本身 > 15，先按 §4.2 的映射向上再聚一层（如 spec → 特性 → 主题），并在图说说明聚合层级。
2. **下钻子图**：每个阶段一张，图内 = 该阶段节点 + 其全部后代。单个阶段的后代数仍 > 15 时，按该阶段的下一层再拆一次（子图的子图），编号 `图 2.1`、`图 2.2`。
3. **交叉引用**：概览图的每个阶段节点标题后追加 ` ▶图N`；每张子图 title 含所属阶段名。
4. **图集完整性**：Σ(各子图深度 ≥2 节点数 − 该子图重复出现的阶段节点 1 个) = 结构 B 中的全部条目数。此式必须在落盘前算一遍（§8 CG-7）。

## 4. 工作项单元与可复现聚合规则

> **默认口径（新输入模型）**：工作项单元恒为**表单 `work_items[]` 的一行**（ID = `item_id`、名称 = `item_name`、层级 = `phase_id`、状态 = `status`、勾选 = `checks`）；`features[]` 各行在需要时作为特性维度的独立单元。本节 §4.1–§4.3 关于「以 spec 为工作项单元」的规则**仅适用于 repo opt-in 且相应字段被授权**的情形（见 §0.3 与 [source-tiers.md](source-tiers.md)）——未 opt-in 时整节按表单口径执行，下列 spec 取材命令不运行。
>
> **opt-in 情形下 specs 缺席时**，按下列固定顺序取补充佐证，并在报告口径中写明"工作项来自表单，佐证来自 <来源>"：
> 1. 该仓的**特性索引**（若存在）每一行特性 = 一个工作项（ID 用 `F-<NNN>`，名称取名称列，状态取状态列按 §1.1 映射）；
> 2. 特性详情文档里的实现说明 / 源文件引用建立**特性 → 代码模块**归属，供 §11 覆盖门禁穷尽代码侧候选；
> 3. 仍需更细的任务层时，退回代码模块的目录结构（一个源码模块 = 一个子任务节点）或版本历史，**不虚构 spec**。**代码侧的目录形态、文件后缀与模块声明方式随语言而变**，取材点判据见 [source-tiers.md](source-tiers.md) §3——本节不写任何语言专属路径。
>
> 稀疏分支下：进度百分比无勾选计数可算 → 一律走 §5.2 RC-3 诚实空值 `-（无可计数依据）`，状态只由特性索引的生命周期字面量经 §1.1 得出；§11 覆盖门禁的"候选工作来源"集合＝特性索引行 ∪ 代码模块（而非 spec 目录）。

### 4.1 默认口径：一个 spec = 一个任务节点

- 默认**不做主题合并**：`specs/<key>/` 每个目录生成结构 B 中**恰好一行**任务记录（ID `T-<n>`，名称取 spec 的业务化标题）。
- spec 数量清点必须区分两个不同的数（**二者不等，报告中必须写清用的是哪个**）：

```bash
cd <目标项目>
# (a) spec 目录数（含尚未产出 tasks.md 的）
ls -d .specify/specs/*/ 2>/dev/null | grep -v '/\.archive/' | wc -l
# (b) 含 tasks.md 的 spec 数（可参与任务勾选统计的）
ls .specify/specs/*/tasks.md 2>/dev/null | wc -l
# (c) 差集：有目录无 tasks.md 的 spec（必须在报告中显式列出，不得静默丢弃）
for d in .specify/specs/*/; do [ -f "$d/tasks.md" ] || echo "无 tasks.md: $d"; done
```

> **规则**：(a) 与 (b) 通常**不等**（差集即"有目录、尚无任务清单"的 spec），把 (a) 的数量配 (b) 的口径叙述即为不自洽。两个数各是多少、差集包含哪些 spec，**一律由上面三条命令在目标项目上实测得出**，不得沿用任何项目的历史值。

- `.archive/`（或该项目等价的归档目录）下的 spec **默认不计入**在建工作项；如需呈现历史，单独成一个「已归档」阶段并在口径中声明。归档目录里同样可能有已勾选任务，**混入会直接改变完成度**，因此其条目数与勾选数必须单独实测、单独列出。

### 4.2 阶段层（父项）由 spec→特性映射决定（三级回退，可复现）

| 优先级 | 来源 | 提取方法 |
|--------|------|----------|
| 1 | 任务清单头部的「所属特性」声明（**示例字面量**：`**Related Feature**: <FID> <名称>`，实际键名以目标项目的模板为准） | 直接采信；**有此头的 spec 占比因项目而异，须实测**（下方命令逐个打印，未声明者显式列为 `未声明`） |
| 2 | 特性索引里的「规格路径」列反查 | 该列指向某个 spec 的需求文档时建立反向链接；**已填行数须实测**，不得假定该列已填满 |
| 3 | 都没有 | 父项填 `P-99 未归属`，**不得**按目录名前缀数字猜特性 |

```bash
# 一次性导出 spec → 特性 的映射候选（优先级 1）
for f in .specify/specs/*/tasks.md; do
  k=$(basename "$(dirname "$f")")
  r=$(grep -m1 '^\*\*Related Feature\*\*:' "$f" | sed 's/.*: *//; s/ *(from.*//')
  printf '%-34s -> %s\n' "$k" "${r:-未声明}"
done
# 反向链接（优先级 2）
awk -F'|' '/^\| [0-9]{3} \|/{gsub(/^ +| +$/,"",$2); gsub(/^ +| +$/,"",$7); if($7!="-") print $2" -> "$7}' .specify/memory/features.md
```

阶段节点名称取特性名（业务语言）；阶段状态由 §2 真值表从其 spec 子项聚合得出——**不直接抄特性索引的状态列**。两者不一致时按 §5 记为记录冲突。

### 4.3 spec 内部再分解（可选第三层）

需要子任务层时，切分依据固定为任务清单内的**分组标题**（`^##` 级标题，**示例**：`## Phase N` / `## User Story N`，实际标题体系以目标项目模板为准），一个分组 = 一个子任务节点；**不按单条任务展开**——单个 spec 的任务条数常远超单图节点上限（§3.1），逐条展开必然爆图。

```bash
grep -nE '^## (Phase|User Story|阶段)' .specify/specs/<key>/tasks.md
```

### 4.4 粒度限定下的信息保全

用户要求只看阶段层（高管粒度）时：

- 图中只画到阶段层；
- 但**该阶段包含的全部 spec 必须在配套表格中逐条列出**（含状态与来源），且图说给出「本阶段含 N 个规格，清单见任务记录表」；
- 结构 B 仍保留完整行数——粒度限定只影响"入图"，不影响"入记录"。

## 5. 「已交付但记录未闭合」的诚实处理（禁止臆造百分比）

### 5.1 触发条件（任一成立）

> **稀疏材料分支**：U-1/U-2/U-3 全部依赖勾选统计或验收字段。当项目没有这类工件时这三条**无法经勾选触发**——但"已交付但记录未闭合"的实质仍可能成立：特性索引标了"已实现"档的状态，却没有任何规格/任务清单能佐证收口度。此时按 §1.1 映射把该状态归入 `in-progress`，进度 % 走 RC-3 诚实空值 `-（无可计数依据）`，并在 RC-5 的"记录未闭合项"表用触发条件列写 `U-SPARSE（无规格佐证收口）`；**不得**因"代码存在"就把它记 `completed`（RC-2 禁止代码反推同样适用）。

| 代号 | 条件 | 检测方法 |
|------|------|----------|
| U-1 | 特性索引状态 ≥ `Implemented`，但其 spec 下仍有 `[ ]` 未勾选任务 | 勾选统计 vs 索引状态列 |
| U-2 | spec 的 `verification.md` 存在但 SC 字段全为空 / `TBD` / `pending` | 见下方命令 |
| U-3 | spec 任务全为 `[ ]`（0 条勾选），但对应能力在代码/文档中已存在 | 勾选统计 + 代码取样 |
| U-4 | 特性索引与 spec 状态互相矛盾（一方称完成、一方称未开始） | 交叉比对 |

```bash
# U-1 / U-3：逐 spec 勾选分布
for f in .specify/specs/*/tasks.md; do
  k=$(basename "$(dirname "$f")")
  d=$(grep -cE '^[[:space:]]*[-*] \[[xX]\]' "$f"); o=$(grep -cE '^[[:space:]]*[-*] \[ \]' "$f"); z=$(grep -cE '^[[:space:]]*[-*] \[~\]' "$f")
  printf '%-34s done=%-4s open=%-4s deferred=%s\n' "$k" "$d" "$o" "$z"
done
# U-2：verification.md 的 SC 字段是否留空
grep -HnE '^SC-[0-9]+_status=[[:space:]]*$' .specify/specs/*/verification.md
```

> **典型现场（示例，数值随项目而变）**：某个 spec 有数十条任务但**0 条勾选**、验收文档的成功标准状态列全空；而代码与文档里该能力**明显已经交付**。这就是"能力已交付、记录未闭合"，也正是执行器最容易被迫臆造一个"50%"的地方——按下节 RC-1~RC-5 处理，进度走诚实空值。

### 5.2 处理规则（RC-1 ~ RC-5，强制）

- **RC-1（进度%来源封闭 —— 只约束"喂给引擎什么"）**：进度百分比**只能**由引擎从下列三类可计数事实算出，别无他途；采集阶段只负责把它们如实落进表单并装载进数据库，**不在文档或报告里做除法**：
  1. 勾选计数 → `checks: {done, open, deferred, excluded}`（引擎输出的 `progress_formula` 自带分子分母）；
  2. `verification.md` 的 SC 通过数 → 同样落成 `checks`（`done` = 通过 SC 数、`open` = 未通过/留空 SC 数）；
  3. 材料中明写的百分比 → `progress_pct` + **必填** `progress_source`（无出处时引擎直接报错拒收）。
- **RC-2（禁止代码反推）**：**禁止**以"代码看起来做完了 / 目录里有文件 / 功能能跑"为由给出任何百分比。观察到代码存在只能支撑状态判为 `in-progress`，**不能**支撑任何具体数字。
- **RC-3（诚实空值 —— 引擎给 null，报告照落）**：三类依据皆无时引擎输出 `progress_pct = null` / `progress_basis = null`；报告进度% 列写 `-（无可计数依据）`，甘特条**不写** `is N% complete` 子句（保持 in-progress 蓝色、无填充比例），图说注明「N 项进度未量化」（N 取引擎 `project.counts.unquantified_progress`，声明句可直接引 `diagnostics.declarations`）。任何形如 `50%`（"大概一半"）的手写数字视为编造，属缺陷。
- **RC-4（冲突显式化，不隐藏）**：特性/任务状态表的状态列在冲突时写成
  `in-progress（索引:Implemented / 任务勾选 0/48，记录冲突）`
  —— 冲突写进呈现物本体，而不是只写在脚注里。
- **RC-5（元信息记录未闭合项清单）**：`## 元信息` 必须含「记录未闭合项」表，列固定为
  `条目 | 索引状态 | 记录侧缺口 | 触发条件(U-n) | 受影响的呈现字段`。
  无此类项时写「无」。

### 5.3 只读红线下的定位（不代为修复）

当目标项目自身设有"状态跃迁前置门禁"（典型形态：把某个状态推进到"已实现"档之前，要求零未勾选任务 + 每条成功标准都有验收状态行）时，U-1/U-2/U-3 命中意味着**事实源侧的门禁违规**，不是呈现层的计算问题。目标项目没有这类门禁时，U-1/U-2/U-3 仍按记录冲突如实呈现。

本技能的处置**止于如实报告**：在报告中标出冲突与缺口，**不修改**任何事实源工件（任务清单、特性索引、验收文档等）中的任何一个字符，也不"顺手补勾选"。修复由 `/speckit.*` 流程或用户完成。提示句的写法是确定性的：`## 元信息` 的「记录未闭合项」表**非空时必须**在表末追加一句中立提示「以上记录未闭合项建议回到事实源侧处理（本技能只读）」；表为空（写「无」）时**不写**该句。不由执行器决定加不加。

## 6. 逾期与 at-risk：**判定在引擎内，文档只定义语义与呈现**

本节不含任何日期比较或天数差算式。全部判定由 `progress-engine.py` 一次算出（基准日即 `--baseline`），报告按下表**引用字段**。

### 6.1 里程碑

引擎为每个 `type=milestone` 条目输出 `status` / `anchor_date` / `delay_days` / `schedule_status` / `evidence`。语义：

| 引擎 `status` | 语义 | 「依据」列写法 | 图元 |
|---------------|------|----------------|------|
| `achieved` | 有达成材料（标签已打 / 版本已发布 / 验收记录存在） | 照引 `evidence`（含达成出处，晚于锚定日时引擎已给出晚了几天） | 绿 `✓` |
| `at-risk`（逾期子类） | 有锚定日、未达成、锚定日已过 | 照引 `evidence`（含 `delay_days` 天数） | 红 `⚠` |
| `at-risk`（风险子类） | 有锚定日、未到期，但材料明写风险/延期（库列 `risk_note`） | 照引 `evidence`（引风险原文出处） | 红 `⚠` |
| `pending` | 有锚定日、未到期、无风险信号 | `-` | 琥珀 `◇` |
| `unknown-schedule` | **无计划日期**（无绝对锚定日、也无可换算的锚定工作项） | 固定写「无计划日期，无法判定延期」 | 琥珀 `◇` + 标签写 `未排期`，**绝不上红** |

- **逾期不需要额外风险材料**：锚定日与基准日都是已记录事实，引擎据此直接给 `at-risk`——逾期里程碑不会被留成 pending。
- **无计划日期不等于逾期**：`unknown-schedule` 是诚实终态，**不得**用 git 日期、提交活跃区间等推断基线补一个"计划日"再判延期；报告在跟踪表依据列 + 图说 + `### 材料缺口` 三处声明（可直接引 `diagnostics.declarations`）。
- 锚定日由推断日期得来时，引擎已在 `date_meta`/`evidence` 标注，「依据」列须带 `（锚定日为推断）`。
- 「锚定工作项工期不足」「前置依赖逾期」这类风险，通过在表单里给 `risk_note`（入库为同名列）表达（附出处），由引擎归入 `at-risk` 风险子类；**不在报告里现算工期差**。

### 6.2 任务

- **逾期任务 = 引擎 `schedule_status == "delayed"` 的条目**（引擎已同时给出 `delay_days`）；数量取 `project.counts.delayed`，明细取 `project.delayed_items`。
- **图上不新增标记**（避免符号膨胀）：甘特的 `today` 蓝线已使其自证——蓝线左侧结束的非绿色条即逾期。
- **图说必须点明数量**：「基准日左侧仍有 N 条未完成条目（逾期）」，`N` 取 `project.counts.delayed`；`N = 0` 时写「today 线左侧无未完成条目，进度贴合计划」。
- **无计划完成日的条目**：引擎给 `schedule_status = "unknown-schedule"`、`delay_days = null`——这些条目**不计入逾期数**，且必须在图说/元信息显式声明「无计划日期，无法判定延期」（数量取 `project.counts.unknown_schedule`）。
- **已完成条目的按期性**：引擎区分 `completed-on-time` / `completed-late`（含晚了几天）/ `completed-schedule-unknown`（无实际完成日）；叙述如需提"按期完成/逾期完成"，照引该字段与 `evidence`。
- **表格必须可查**：任务记录表标注逾期条目（可复用状态列括注），逾期任务数进入 `## 任务进展` 叙述。结束日期为推断值时，引擎的 `date_meta` 已标出，图说注明「基于推断工期」。

### 6.3 反向自洽（渲染后目检，不是重新判定）

- `today` 线**右侧**不应出现 `completed` 条目；出现即数据矛盾 → **回查库中的日期或状态并重跑引擎**，不得手工改判、也不得两者并存落盘。
- 里程碑视图中基准日左侧的菱形应全为 `achieved` 或 `at-risk`（不应有 `pending`）；右侧不应有 `achieved`（若真有提前达成，须在图说显式解释）。`unknown-schedule` 菱形无日期、不入时间轴，只出现在跟踪表与声明句中。

## 7. 聚合数字的口径固定与可复现（统计口径契约）

### 7.1 五要素登记（无口径不得进报告）

**报告中出现的每一个聚合数字**（计数、比例、百分比、总量）都必须在 `## 元信息 · 统计口径` 表中有一行登记，列固定为：

| 口径 ID | 指标定义（分子 / 分母） | 采集命令（逐字可复跑） | 范围（glob / git 窗口） | 采集日 |
|---------|------------------------|------------------------|-------------------------|--------|

- 报告正文的数字**只能引用口径 ID**（如「任务完成度 89.1%〔口径 M-TASK-1〕」）。
- 同一指标全报告**只有一个口径**；需要第二种口径时必须另起 ID 并在叙述中并列说明差异原因。
- **跨口径的数字禁止相加、相减、相除或并列比较**（这是"1073+13+122≠1223"类错误的根因）。
- **采集与计算分工**：§7.2 的命令**只负责采集原始计数与日期**（勾选分布、特性状态分布、标签数、提交数、首末提交日），它们的结果落进**表单并装载进数据库**；一切**比例、百分比、天数差、平均**由 `progress-engine.py` 产出，报告**照抄**引擎的算式串（`progress_formula` / `project.progress.formula` / `coverage.*`）。文档与报告都不做除法。
- **引擎产出的数字同样要登记口径**：该行「指标定义」写清引擎字段与口径（如 `project.progress.formula`、口径 `checks（不含 deferred）`），「采集命令」写引擎调用命令（含 `--baseline`），这样读者可原地复跑复核。

### 7.2 采集命令集（**仅 opt-in repo 情形**；命令是规则，输出值一律实测）

> **本节给的是命令，不是数值。** 下列每条命令的输出**因项目而异**，必须在目标项目上现跑现取，并连同口径一起登记进 §7.1 的统计口径表。**任何示例数值都不构成默认假设**（可移植性纪律见 [portability.md](portability.md)）。命令形态本身也依赖目标项目的工件布局（目录名、索引文件名、表格列序），套用前先确认路径存在，不存在就整组略去。
>
> **稀疏材料分支**：`M-TASK-*`（勾选分布）与 `M-SPEC-*`（spec 计数）依赖任务清单工件。项目没有这类工件时它们**返回空/零**，须**整组略去而非记 0**（记 0 会伪装成"0 项完成"）。此时可算的口径通常只剩特性状态分布、标签数与提交窗口。完成度**不得**用勾选比给出——无勾选可算时按 §7.3 与 RC-3 只报状态计数（形如"N 个特性：a 已实现 / b 未启动"），不写百分比。

```bash
cd <目标项目>

# M-TASK-*：任务勾选分布（全部标记一次算清，含大小写与非状态标记）
grep -hoE '^[[:space:]]*[-*] \[.\]' <任务清单 glob> | grep -oE '\[.\]' | sort | uniq -c | sort -rn
#   → 输出形如「<n1> [X] / <n2> [x] / <n3> [ ] / <n4> [P] / <n5> [~]」；各值**实测**
#   done=[X]+[x]  open=[ ]  deferred=[~]  非状态标记（如 [P]）单列并从分母排除（§1.2）

# M-FEAT-1：特性状态分布（列序以目标项目的索引表格为准，下例取第 5 列）
awk -F'|' '/^\| [0-9]{3} \|/{gsub(/^ +| +$/,"",$5); print $5}' <特性索引文件> | sort | uniq -c | sort -rn
# 与索引表头/摘要声明的总数交叉核对（**不一致 → 记为记录冲突，不擅自取其一**）
grep -m1 -iE 'total .*features?' <特性索引文件>

# M-SPEC-1 / M-SPEC-2：spec 计数（见 §4.1，两个数不同，须写清用哪个）

# M-TAG-1：标签数
git tag | wc -l

# M-COMMIT-*：提交数——**窗口必须声明**，下面三个数互不相等，禁止混用（§12）
git rev-list --count HEAD                                # 含 merge，仅 HEAD 可达
git rev-list --count --no-merges HEAD                    # 不含 merge，仅 HEAD 可达
git rev-list --count --all                               # 全部 ref（含远端分支/标签）
# 作者贡献：其分量之和 = `--no-merges HEAD` 的那个数，**与另两个数不可混用**
git --no-pager shortlog -sne --no-merges HEAD

# M-DATE-1：项目起止日期 —— 必须加 --reverse
git log --date=short --format='%ad' --no-merges --reverse | sed -n '1p'   # 最早提交
git log --date=short --format='%ad' --no-merges | sed -n '1p'             # 最新提交
```

> **`--reverse` 陷阱（实测已复现）**：`git log` 默认**逆时序**输出，`sed -n '1p;$p'` 得到的是「最新, 最早」而非「最早, 最新」。直接当作 `起,止` 使用会得到起点晚于终点的负工期。取最早提交**必须** `--reverse`。

### 7.3 百分比一律**照抄引擎算式串**（禁止裸百分比、禁止手算）

- 报告中的一切百分比都必须是引擎输出的算式串**逐字复制**——引擎输出天然是 `分子/分母 = xx.x%` 形态（条目级 `progress_formula`、项目级 `project.progress.formula`、覆盖率 `coverage.coverage_formula`）。**禁止**只写 `89.1%` 或 `约九成`，也**禁止**在报告里另做一次除法。
- **分母口径必须点名**：写在算式旁的口径名取引擎 `project.progress.basis`（如 `checks（不含 deferred）`）。引擎同时给出另一口径于 `project.progress.alternatives`。**并列呈现与否有确定性裁决规则，不由执行器随意决定**：
  - `deferred` 桶计数为 0（或引擎未给 `alternatives`）⇒ **只呈现 `basis` 一个口径**，正文与元信息都不并列；
  - `deferred` 桶计数 > 0 ⇒ **正文仍只用 `basis` 口径**，另一口径**只**写在 `## 元信息 · 统计口径`（另起口径 ID）并注明差异只来自 deferred 桶。
  - 两个口径的数字**在任何位置都不得混用或相互运算**。
  引擎输出的算式串形如 `<分子>/<分母> = <百分比>%`（**示例**：`1106/1228 = 90.1%` 不含 deferred、`1106/1241 = 89.1%` 含 deferred——**这两个数值只是形态示例，随项目而变**）。
- **分桶加法闭合由引擎给出**：`project.progress.buckets`（done / open / deferred / excluded_marks）与 `bucket_closure` 算式串直接落进元信息；报告不自行相加。非状态标记（如 `[P]`）走 `checks.excluded`，单列且不入分母。
- 引擎给 `progress_pct = null` 时（无可计数依据），该处写 `-（无可计数依据）`，**不得**为了"有个数字"而手写百分比（RC-3）。

### 7.4 加权口径的额外要求（默认不加权）

- **默认口径是引擎的等权平均**（父项 `progress_formula` 已写明分子分母）。**无权重依据时不做加权**，也不在报告里手写任何加权算式。
- 确有材料依据的权重（如材料明写各阶段占比）时：把权重连同出处一并落进表单（入库为 `weight` / `weight_source` 列）（并在 `## 元信息` 逐项列出**每一项权重与权重和**），由引擎给出对应算式串；报告照抄。
- 权重和必须与算式分母一致——这一致性在**元信息的权重清单**上核对（CG-4），而不是靠在报告里重算一遍。

## 9. ID 命名空间消歧与规则缺口处理

### 9.1 三个独立命名空间（禁止裸号）

| 前缀 | 命名空间 | 取值来源 | 形态示例（值随项目而变） |
|------|----------|----------|------|
| `F-` | 特性索引 ID | 特性索引的 ID 列（**示例布局**：`memory/features.md`） | `F-019 <特性名>` |
| `S-` | 规格键（spec key） | spec 目录名（含其前缀数字；**示例布局**：`specs/<key>/`） | `S-019-<slug>` |
| `P-` / `T-` | 报告自编工作项 ID | 本报告结构 B 自编 | `P-02` / `T-13` |

- **报告中一律带前缀引用，裸 `019` 禁止出现**（表格列、图节点、图说、叙述均适用）。
- **spec 目录前缀数字与特性 ID 不同源、不可互推**（**示例**：`S-019-<slug>` 的所属特性完全可能是 `F-022`——两套编号各自独立递增，按数字对齐会把两件不同的事混为一件）。两者的实际对应关系**只能**按 §4.2 的三级回退在目标项目上查出。
- 唯一权威映射是 §4.2 的三级回退；映射结果作为一列写入任务记录表（或独立的 `S-<key> | F-<NNN> | 映射来源` 小表），读者可复核。
- 命名空间内出现重号（同一空间两个同号条目）时，全称区分并在元信息记为记录冲突，不合并。

### 9.2 差值必须有名有数（无静默丢弃）

任何"事实源有 X 条、报告呈现 Y 条"的差值都必须逐项交代，格式：`X − a(未排期) − b(已剔除:原因) − c(粒度限定未入图) = Y`。差值项无名无数即视为静默丢弃条目，属缺陷。

### 9.3 规则缺口处理

遇到本文档未覆盖的判定情形时，按序处理，**禁止**临场自造判定后静默落笔：

1. 优先按最接近的既有规则**类推**，并在 `## 元信息 · 估计假设` 登记「按 §<节号> 类推判定：<情形> → <结论>」；
2. 类推会实质性影响范围/时间/状态结论时，转为一轮澄清提问（≤4 问，见 SKILL.md「信息不足与澄清」）；
3. 两者都不可行时，该条目状态记 `unknown`（§1.4），**不猜**。

## 10. 只读红线的精确边界与写入白名单（Feedback 冲突裁决）

### 10.1 冲突陈述

- 核心原则说「**绝不修改** `.specify/`、需求文档、任务清单等任何源工件」；
- 而 `## Feedback` 步骤要求把技能自省记录写入 `.specify/memory/feedback/`。

字面读来二者互斥，执行器面对矛盾指令只能跳过其中之一（实测三个执行器全部跳过了 Feedback 步骤）。本节给出**明文裁决**。

### 10.2 裁决：红线的作用域是"被总结的事实源"，不是"字面上的 `.specify/` 路径"

只读红线保护的是**信息源的真实性**——即本技能读取并据以下结论的那些工件。它**不是**对某个目录前缀的字符串级禁写。判定标准只有一条：

> **一个路径是否是本次的输入来源（项目输入表单、用户提供的外部材料，或 opt-in 授权后的仓库路径）、是否会成为任何呈现层的取材来源。是 → 绝对只读（含表单本身：技能读它、不改它）；否 → 根本不该被访问。**

`.specify/memory/feedback/` **不是**任何呈现层的取材来源（不在信息源映射表的任何一格里），写入它不会改变项目概览、特性、工作项、里程碑、进度中的任何一个结论。因此：

**`## Feedback` 步骤照常执行；只读红线不覆盖 feedback 目录。二者不构成真实冲突。**

### 10.3 写入白名单（穷举，仅此三项）

| # | 允许写入的路径 | 写入方式 | 说明 |
|---|----------------|----------|------|
| W-1 | 交付目录本身（`.specify/project/summary/` / `docs/project-summary/` / 用户指定）：`summary.md` + `assets/` + `data/` | 本技能落盘 | 技能的唯一交付物（**整个目录**），重复运行整体刷新 |
| W-2 | `${SKILL_WORKDIR}/.specify/memory/feedback/` | **只经** `feedback-utils.py` 引擎（不手写文件） | 技能自省通道，宿主框架资产 |
| W-3 | 图源与渲染产物、计算/校验中间产物（图源 `*.puml` 与渲染出的 `*.svg` / `*.png` 同名落 `assets/`；**项目数据库 `project.db`、引擎输出 `engine-out.json`**、可选导出 `progress-data.json`、`expect.json`、门禁结果落 `data/`） | draw-plantuml 渲染流程 / `project-db.py` / `progress-engine.py` / 校验脚本 | 一律落**交付目录内**（`assets/` 或 `data/`，默认每次运行从事实源重建、随目录整体刷新，作为交付物一部分保留）；**绝不写入目标项目管理工件区**（目标项目 ≠ 宿主时交付目录外零写入） |

**白名单之外一律只读**，明确包括：`.specify/specs/**`（requirements / plan / tasks / verification / checklists）、`.specify/memory/features.md` 与 `features/**`、`.specify/memory/constitution.md`、`.specify/instructions.md`、`.specify/skills/**`、`.specify/agents/**`、`.specify/templates/**`、`.specify/history/**`、`.specify/memory/session|knowledge/**`、README/docs、源代码、git 仓库（不 commit、不 tag、不改 ref）。

### 10.4 优先级与目标≠宿主的处理

1. **优先级**：白名单（W-1~W-3）> 只读红线 > 其他。红线不得被用来跳过 `## Feedback`；反之 Feedback 也不得被用来写红线内的任何路径。
2. **写入方向固定为宿主**：feedback 一律写**运行本技能的宿主工作区** `${SKILL_WORKDIR}/.specify/memory/feedback/`。当 `--target` 指向的目标项目 ≠ 宿主工作区时，**绝不**向目标项目写任何字节（含 feedback）。
3. **standalone 模式**：`${SKILL_WORKDIR}/.specify/` 不存在（非 Spec Kit 部署）→ 整个 Feedback 步骤跳过，不调引擎、不建目录。
4. **自总结场景的透明化**：目标项目 == 宿主工作区（即用本技能总结承载本技能的那个项目自身）时仍照常记录，但必须在 `## 元信息` 加一行声明：
   「本次运行向宿主 `.specify/memory/feedback/` 追加了 1 条技能自省记录（框架自省通道，非目标项目事实源，不影响本报告任何结论）。」
5. **落盘检查项**：「未对任何信息源工件产生写入」的核对口径 = 白名单之外零写入。可用下式自证（在目标项目根执行，`<D0>` 为基准日）：

```bash
# 白名单之外是否有改动（应只列出交付目录内的文件）
# <交付目录> = .specify/project/summary | docs/project-summary | 用户指定路径
git status --porcelain | grep -vE '<交付目录>/' || echo "白名单之外零写入 ✓"
```

## 11. 分解树覆盖完整性门禁（CG-COVERAGE）

> **解决的缺口**：最典型的失分形态是"事实源里有大量细粒度工作（如上百条未勾选任务）没有归属到任何工作项，报告却只字未提"。分解树只画聚合后的工作项本身不算错（§3.2 允许聚合呈现），**错在差值静默丢弃、且进度百分比的分母与分解树呈现的范围对不上**。本门禁把"覆盖是否完整"从人工目检升级为**可执行 + 强制声明**。

### 11.1 穷尽候选工作来源（分母的全集 C）

覆盖率的分母不是拍脑袋定的，必须**穷尽**项目里一切"算一份工作"的来源，形成候选全集 `C`。**默认（表单）口径下 `C` 直接来自库表，见 11.5**；下面的命令只适用于 **repo opt-in 且相应字段被授权**的富材料仓，且**每条命令的路径都随目标项目而变**（下列写法是示例，套用前先确认路径存在）：

```bash
cd <目标项目>
# c1 = spec 目录数（在建工作项候选，排除归档目录）
ls -d <specs 根>/*/ 2>/dev/null | grep -v '/<归档目录>/' | wc -l
# c2 = 细粒度任务候选（全部勾选行，按 §1.2 口径，含大小写/deferred；非状态标记排除）
grep -hcE '^[[:space:]]*[-*] \[[ xX~]\]' <任务清单 glob> 2>/dev/null | paste -sd+ | bc
# c3 = 特性索引行（特性侧候选）
awk -F'|' '/^\| [0-9]{3} \|/{n++} END{print n}' <特性索引文件>
# c4 = 代码顶层模块（代码侧候选）——**取材点随语言而变**：源码根目录、模块声明方式与
#      文件后缀都不通用，判据见 source-tiers.md §3；下面只是"数一层模块"的形态示例
ls <源码根>/<模块文件 glob> 2>/dev/null | wc -l
```

- **分解粒度不由执行器临场挑选，按下列顺序唯一确定**（保证同一输入两次运行得到同一个 `C`）：
  1. 用户**显式指定**了受众粒度（如"只看阶段级"）⇒ 取该层，细项按 `R-粒度截断` 记入残差（§4.4）；
  2. 否则 ⇒ **固定取表单工作项层**，即 `C` = 表单 `work_items[]` ∪ `features[]`（11.5 的默认口径）；
  3. opt-in 富材料仓下的 `c1`/`c2`/`c4` **只作残差清点的佐证**，**不改变** `C` 的层级、也不新增工作项（[source-tiers.md](source-tiers.md) §5.3）。
  `C` 用哪一层，报告口径必须写明，且它就是进度百分比的分母集合（11.3）。
- **一个粒度只对一个 `C`**：不得"分解树按一套口径画、完成度按另一套算"——那是分母集合 ≠ 覆盖范围，属本门禁要抓的核心不自洽（11.3）。

### 11.2 逐项归属与残差清单（R）

把 `C` 的每一个候选**逐一**判定：归属到分解树的某个工作项（attributed），还是无处安放（residual）。residual 全体构成**残差清单 `R`**，必须**有名有数**落进 `## 元信息`：

| 残差桶 | 含义 | 处置 |
|--------|------|------|
| `R-未排期` | 有该工作但无时间信息，未入甘特 | 入 WBS 与记录表，图说列明数量（§9.2、task-progress） |
| `R-未归属` | 找不到对应特性/阶段（§4.2 优先级 3 落空） | 挂到 `P-99 未归属` 阶段，**不得**丢弃 |
| `R-已剔除` | Cancelled / Won't Do / `.archive/`（§1.5、§4.1） | 单列并写明剔除原因与数量，不入分母 |
| `R-粒度截断` | 用户限定只看阶段层，细项未入图（§4.4） | 图未画但记录表保留，图说声明"含 N 项，清单见表" |

> **残差清单为空也要显式写**：`分解树覆盖：候选全集 C=<数>，残差清单为空，覆盖率 <数>/<数> = 100%`。空残差同样是一次声明，不是省略。

### 11.3 进度百分比的分母集合＝分解树覆盖范围（强制声明）

- 报告里出现的整体完成度，其**分母集合**必须**逐字等于**分解树覆盖的那个 `C`（减去 `R-已剔除`）。即：进度是在"图上画出来的这批工作"上算的，不是在另一个更大/更小的 population 上算的。
- **闭合等式与覆盖率由引擎产出**：把候选清点结果写进表单的 `coverage` 块（入库为 `coverage` 表）（`candidate_total` / `excluded` / `granularity_truncated` / `unattributed` / `source_label`），引擎输出 `coverage.closure_equation`（形如 `<候选全集> − <已剔除> − <粒度截断> = <分解树工作项数>`，**示例**：`31 − 2 − 23 = 6`）、`coverage.closure_ok`、`coverage.coverage_formula`、`coverage.progress_denominator_set`——报告**照抄这些字符串**，不在文档或报告里做减法/除法。引擎发现闭合不成立会给出 `closure_note` 并计入 `diagnostics.warnings`。
- 落盘声明格式（写入 `## 元信息 · 分解树覆盖`，各值取自引擎字段）：

  ```text
  分解树覆盖：候选全集 C = <coverage.source_label>（<coverage.candidate_total>）
  残差清单 R：R-未排期 a、R-未归属 <coverage.unattributed>、R-已剔除 <coverage.excluded>（原因）、R-粒度截断 <coverage.granularity_truncated>
  覆盖闭合：<coverage.closure_equation>（= 分解树工作项数 = 进度分母集合大小）
  覆盖率：<coverage.coverage_formula>
  进度分母集合：<coverage.progress_denominator_set>
  ```

- **双保险**：`check-coherence.py` 的 CG-COVERAGE 会在报告文本上**再验算一次**闭合等式（去括注后 `first − Σsub == last`），写错即 FAIL——引擎负责算对，检查器负责堵住"抄错/漏声明"。

### 11.4 机械兜底（check-coherence.py · CG-COVERAGE）

```bash
python3 ${SKILL_HOME}/scripts/check-coherence.py <报告路径>
```

- 报告含 `@startwbs` 却**全文无**"分解树覆盖 / 覆盖完整性 / 残差清单 / 未归属工作项 / 归属残差 / 覆盖残差"任一显式声明 → **FAIL CG-COVERAGE**（这一条直接堵住"大批候选工作未披露"这一最易静默的缺口）。刻意不认"人员维度覆盖率""该工作项覆盖的各 spec"这类无关"覆盖"字样，避免假通过。
- 报告写了覆盖闭合等式但**算错** → **FAIL CG-COVERAGE**，打印 `first − subs 实为 X，报告写 Y`。
- 脚本是**下限**：`C` 是否真的穷尽、每项归属是否正确，仍须人工按 11.1/11.2 过检——脚本只保证"你声明了，且算式没写错"。

### 11.5 默认（表单）口径下的覆盖门禁

未 opt-in 时不存在 spec/模块候选：候选全集 `C` = **表单 `work_items[]` ∪ `features[]`**（去重后按 `phase_id` 归属到阶段）。opt-in 且被授权时，可把仓内条目作为**佐证**并入残差清点，但**不得**新增工作项（见 [source-tiers.md](source-tiers.md) §5.3）：

- 分解树画到工作项层：`C` = 表单工作项数（+ 未被工作项覆盖的特性行，记 `R-未归属` 并显式列出）。
- 无 `checks`/`progress_pct` 可算 → **不出整体完成度百分比**（RC-3），覆盖率仍要给（如 `12/12 = 100%`，若全部条目进树）。
- 覆盖声明照写：`分解树覆盖：候选全集 C = 表单 work_items(12) ∪ features(5)；残差清单 R：<按上表>；覆盖率 …`。CG-COVERAGE 的显式声明要求**同样生效**（有 WBS 就要声明）。
