# 跨层规范：表单字段缺失时的诚实降级 —— 缺失即可见信息，绝不臆造

`summarize-project` 的**跨层强制规范**：当**项目输入表单**里某些字段没填、或摄取不到时，报告如何**诚实降级**——把"缺什么"变成读者看得见的信息，而不是用占位数字、虚构日期、想象的负责人把报告撑得"看起来很丰满"。工作流主框架见 [../SKILL.md](../SKILL.md)；**字段的业务含义与三档必填性见 [required-info.md](required-info.md)、字段约束的权威是 [`../schema/project.sql`](../schema/project.sql)（由数据库强制）**；记录层与呈现映射见 [data-model.md](data-model.md)；跨层公约见 [reporting-playbook.md](reporting-playbook.md)；人员维度的缺失声明见 [people-encoding.md](people-encoding.md)。

**边界（三条）**：
1. **档位定义不在此**：哪些字段是 R（必填-阻断）/ I（可推断）/ O（可选）、字段名与关联规则，唯一权威是 [required-info.md](required-info.md)。本文档只写**缺失命中后**章节与图怎么退化、怎么声明。
2. 通用 PlantUML 绘图规则（语法、字形、图例、版面量测、caption 渲染位置等）的权威出处在 draw-plantuml，本文档不重述。
3. **判据的计算不在此**："进度算不算得出来""有没有计划日期""排期材料是否过弱"这类判定由 `scripts/progress-engine.py` 给出（字段 `progress_pct=null`、`schedule_status=unknown-schedule`、`gantt.schedule_material.gantt_recommended` / `weak_git_material` / `reason`）；本文档只按结果退化（见 [consistency-rules.md](consistency-rules.md) §0.1）。

**本文档存在的原因**：真实项目的表单常常填不满——没有细粒度任务、没有计划日期、没有负责人、没有里程碑节点。此时若沿用"信息充足"路径，执行器会被迫**编造**进度百分比、里程碑日期、任务工期。本文档给出一条硬底线：**表单里没有的，一律走"合法终态 + 显式声明"，绝不臆造；报告宁可短而诚实，不可长而虚假。**

## 1. 降级总则（按三档分流 + 三条硬规矩）

**先分流**（档位见 [required-info.md](required-info.md) 第 2 节）：

| 档位 | 缺失时的处置 | 是否降级 |
|------|--------------|----------|
| **R 必填-阻断** | 走 [../SKILL.md](../SKILL.md) Step 1 的 Step C：**阻断**，向用户呈现只列缺失必填项的待填表单，补填后重新校验 | **不降级**（不许用降级或猜测糊过去） |
| **I 可推断** | 依据项目背景/阶段/里程碑等上下文或确定性规则**推断并标注** `inferred: true` + `inferred_from`，汇总进 `## 元信息 · 推断字段清单` | 推断，不算缺口 |
| **O 可选** | 取本文档第 3 节的**合法终态**并在三个声明位之一**显式声明** | 降级，缺口可见 |

**三条硬规矩**（对 I / O 档缺失一律适用）：

1. **缺失即可见信息**：字段缺口**不得静默省略**、**不得用占位数字/日期/人名填充**。每一处缺失都要在三个声明位之一（或多处）显式出现——见第 2 节声明位定义。读者读完报告必须能一眼看出"哪些内容因表单未提供而不存在或被降级"。
2. **禁止臆造**：进度百分比、里程碑日期、工期、负责人、任务状态五类信息**表单没给就绝不凭空产生**——各自的合法终态见第 3 节。**推断**（有可指认依据，如按工作项分组推断阶段、按 `sources[]` 推断条目来源）允许，但必须带 `inferred_from` 并登记；**臆造**（无依据编数字/日期/人名）禁止。
3. **短而诚实优先**：报告篇幅随表单填充度伸缩。填得少 → 报告短。**不允许**为了"显得完整"而虚构图表、堆砌占位行、把普通事件升格。最小可交付形态见第 7 节。

## 2. 五层缺失分级与声明位

### 2.1 三档缺失分级（以**表单字段**为对象）

| 档位 | 判定（对表单字段） | 通用处置 |
|------|--------------------|----------|
| **可推断（I 档）** | 字段未填，但有可指认依据（工作项分组可推断阶段、`sources[]` 可推断条目来源、日期次序可推断依赖、状态字面量可归一化等） | 推断并呈现，值后加 `（推断）`、记录 `inferred: true` + `inferred_from`，汇总进 `## 元信息 · 推断字段清单` |
| **部分缺失（O 档，部分行）** | 同一字段部分行有值、部分行为空（如 3/8 个工作项有 `planned_end`） | 有值的照常呈现；空的用**合法终态**（`未记录` / `-` / `未排期` / `未知`）逐条占位，**不得整段省略**——省略会让读者把"没提供"误读为"确实没有" |
| **完全缺失（O 档，整组/全字段）** | 该实体组整组为空（如 `milestones[]` 为空、`people[]` 为空），或该字段在全组皆空 | 保留章节骨架 + 段首**材料声明句** + 列出已检索来源；能省的图（里程碑视图 / 甘特）按第 4、5 节省掉；元信息记一条缺口 |

> **R 档缺失不进本表**：`project_name` / `baseline_date` / `work_items[]`+`milestones[]` 皆空、以及关联断裂，一律**阻断出表单**（第 1 节分流），不走降级。

### 2.2 三个声明位（缺失必须落到其中）

- **① 章节内声明句**：在退化章节段首写一行 blockquote，统一前缀 `> 材料声明：…`（醒目、可扫读）。模板见第 8 节。
- **② 图内声明**：WBS/脑图用 `caption`（`caption` 在 WBS 渲染于图例下方，实测见 [people-encoding.md](people-encoding.md) 2.2）、甘特用 `legend` 内一行或图说首句承担。字形/渲染位置规则见 `<draw-plantuml>/references/guide/style.md`。
- **③ 元信息缺口清单**：`## 元信息` 内固定的 `### 材料缺口` 小节（结构见第 6 节）——全局汇总，与各章节声明句一一呼应（声明句是局部提示，缺口清单是全局边界地图）。

### 2.3 五层缺失矩阵（每层三档处置 + 声明位）

| 呈现层面 | 完全缺失（整组/全字段空） | 部分缺失（部分行空） | 可推断（I 档） |
|----------|----------|----------|--------|
| **1 项目概览** | `project_desc` 空且无可推断依据 → 章节写「背景：材料未记录」并列已检索来源（声明位①③）| 缺某一要素（如无 out-of-scope 说明）→ 该要素写「材料未界定」，其余照常（①）| 目标可由 `project_desc` + 工作项主题推断 →「推断自 <出处>」（①）|
| **2 需求与特性** | `features[]` 整组为空 → 表格退化为「（表单未提供特性清单）」+ 已检索来源（①③）；不画脑图 | 部分行 `status` 空 → 状态列写 `未知`（非臆测四态）（①）| `status` 字面量可归一化、`feature_id` 可生成 → 标 `inferred`（①③）|
| **3 功能分解 WBS** | `work_items[]` 与 `features[]` 皆空 → 不出 WBS（此时已属 R 档阻断，见第 1 节）| `phases[]` 为空或部分工作项无 `phase_id` → WBS 退化到**单层/特性层**（不强求 phase→task→subtask），深度受限声明写图说（①②）；`owner_id` 空→`【未记录】`；`status` 空→节点默认色 + caption | 阶段可由工作项分组推断、`phase_order` 可由出现顺序推断 → 标 `inferred`（②③）|
| **4 项目里程碑** | `milestones[]` 整组为空 → **不出里程碑视图**，跟踪表省略，章节仅保留材料声明 + 已检索来源（①③）；**不得**把普通提交/版本号/状态跃迁升格为里程碑（见第 4 节）| 部分里程碑 `planned_date` 与 `anchor_item_id` 皆空 → 锚定列写 `未排期`，不进带日期菱形（①）| 有 `anchor_item_id` 且该工作项有 `planned_end` → 引擎换算绝对日期并注明锚定关系（②）|
| **5 任务进展** | 全部工作项都没有 `planned_start`/`planned_end`（也无工期依据）→ **甘特不出图**，退化为 WBS + 特性/任务状态表 + 状态叙述（①③，见第 5 节）| 部分行缺日期 → 用相对依赖排期或标 `未排期`，不虚构工期（①）| 仅 opt-in repo 的 git 活跃区间 → 只作项目整体区间推断，**不得**当任务排期（见第 5 节判据）|

- `project_name` 与 `baseline_date` 是 **R 档**，缺失走阻断、**不会**出现在本矩阵里；`work_items[]`/`milestones[]` 至少一组非空同理。
- `features[]`、`work_items[]` 通常有值（它们是用户最先能给的信息）；**`milestones[]` 与排期字段（`planned_start`/`planned_end`）是最常整组为空、也最容易诱发臆造的两处**——第 4、5 节专门处置。

## 3. 禁止臆造的硬门禁（五类禁造物 + 合法终态）

以下五类信息**无材料依据时绝不允许凭空产生**。每一类给出"无依据时的合法终态"，并规定该终态在**表格 / 图 / 叙述**三处一致呈现（同一字面量，不得一处写 `未记录`、另一处却编个值）。

| 禁造物 | 无依据时的合法终态 | 表格呈现（记录表/跟踪表）| 图内呈现 | 叙述呈现 |
|--------|--------------------|------------------------|----------|----------|
| **进度百分比** | 引擎 `progress_pct = null` → `-（无可计数依据）`（引擎只在有勾选计数/材料明写百分比时给数字）| 进度% 列写 `-`；completed 记 100、not-started 记 0（按定义，非臆测，同样由引擎给出）| 甘特条形不写 `is N% complete`（保留纯着色）| 不出现"整体完成约 X%"等编造数字；项目级也走引擎的诚实空值（`project.progress.progress_pct=null` + `reason`），只说"X 项已完成 / Y 项未开始（按特性状态）" |
| **里程碑日期** | `未排期`；且引擎给 `status = unknown-schedule`、`delay_days = null` | 里程碑跟踪表锚定列写 `未排期`，依据列写「无计划日期，无法判定延期」| 无绝对日期且无可锚定工作项的里程碑**不作带日期菱形出图**；若仍需列出则用琥珀 `◇`，**绝不上红** | 不给里程碑编造完成/计划日；**明确说明该里程碑无法判定是否延期**，不用 git 日期等推断基线代替计划日 |
| **工期（duration）** | `未排期` | 任务记录表开始/结束列写 `-`，无工期列 | 甘特条形无 `requires N days` 依据时**不虚构工期**（连带触发第 5 节"甘特是否出图"）| 不说"预计 N 天" |
| **负责人** | `未记录`（见 [people-encoding.md](people-encoding.md)）| 负责人列写 `未记录` | WBS `【未记录】` / 甘特 `▪未记录` / 全量缺失整图不标 + caption | `### 人员与分工` 首句覆盖率声明 + 已检索来源 |
| **任务状态** | `未知（材料无状态信号）` | 状态列写 `未知`（**区别于 `not-started`**：not-started 是"有依据判定未开始"，`未知` 是"无从判定"）| 状态未知的节点/条形**不着四态色**（默认色）+ caption 声明「材料未记录状态信息」| 显式说"N 项状态无材料依据，记为未知" |

**关键区分（防止最隐蔽的臆造）**：

- **推断 vs 臆造**：git 活动区间→项目整体区间是**推断**（有依据、标 `（推断）`）；给某任务编个"60% 完成"是**臆造**（无任何依据）。前者合法，后者禁止。
- **`not-started` vs `未知`**：`not-started` 断言"确实还没开始"（需有依据，如 feature 状态 Draft 且无实现痕迹）；`未知` 承认"无从判定"。**不得**把"没查到状态"默认成 `not-started`——那是把"无知"伪装成"结论"。
- **`unknown-schedule` vs `逾期`（延期维度的同一条边线）**：有计划完成日、未完成、计划日已过 → 引擎判 `delayed`/`at-risk`（红）；**没有计划完成日** → 引擎判 `unknown-schedule`，报告如实写「无计划日期，无法判定延期」，**不上红、不计入逾期数、不用 git 首末提交日等推断基线补一个计划日再判延期**。把"无从判定"画成"逾期"与把它画成"按期"同样是失真。
- **状态映射的诚实边界**：状态列一律按 [consistency-rules.md](consistency-rules.md) §1.1 的映射执行（默认表见该节，**目标项目自身的生命周期定义优先**，差异写进表单 `status_map`）；**但特性状态列本身不含进度信息**——状态回答"处于哪一档"，不回答"推进到几成"，绝不可据一个 in-progress 状态编造完成百分比。

**三处一致校验**：任一禁造物的合法终态一旦采用，落笔检查须确认表格、图、叙述三处该条目**都是同一终态字面量**，无一处被"补"上编造值。

## 4. 无里程碑材料时 `## 项目里程碑` 章节的合法形态

**触发**：表单 `milestones[]` 整组为空（用户未提供任何发布/评审/验收/阶段完成节点），且上下文与用户提供的外部材料里也没有可归集的里程碑事件；若 repo 为 opt-in 且被授权，定向查询（`git tag` / 发布记录 / 验收记录）同样无结果。

**合法形态**（三条同时满足）：

1. **保留章节**：五章骨架是报告契约，`## 项目里程碑` 标题**必留**，不得删章节。
2. **章节体 = 材料声明句 + 已检索来源清单**：不出里程碑视图、不出跟踪表（或跟踪表写一行"（无里程碑条目）"）。声明句模板见第 8 节。
3. **元信息登记**：`### 材料缺口` 记一行；里程碑视图独立成图判定结论记为「不出图（无里程碑材料）」。

**硬禁止——不得把下列事物升格为里程碑**（升格会凭空制造"项目节奏/发布节点"这类根本不存在的信息）：

- ❌ 普通 git 提交（哪怕是 "Initial commit" 或首末提交）；
- ❌ 版本号本身（包/工程清单里的 `version` 字段，**任何生态**）——版本号不等于"已发布里程碑"，除非有对应 git tag / 发布记录；
- ❌ 特性状态到达"已实现"档——"某特性已实现"是特性状态，不是带达成日期与评审记录的里程碑；
- ❌ 文件的 Created/Last-Updated 时间戳。

**唯一合法的里程碑来源**：材料本身把某事件标注为**发布 / 评审 / 验收 / 阶段完成节点**（git tag、release note、verification 通过记录、路线图节点、用户明确口述的节点）。这些都没有 → 就是"无里程碑"，如实声明。

> 实例：表单只填了 `work_items[]`、`milestones[]` 留空，且 repo 未授权里程碑相关字段 → `## 项目里程碑` 走本节完全缺失形态。提交数、版本号、`Implemented` 特性**均不得**升格为里程碑。

## 5. 无任务/工期材料时 `## 任务进展` 甘特图的处置

### 5.1 甘特出图的前置条件

甘特图的本质是**日历排期**：每根条形要能定位到时间轴。因此**出甘特的前置条件**是至少存在下列之一——① 条形的绝对起止日期（`starts/ends yyyy-mm-dd`）；② 工期依据（`requires N days`）；③ 可排期的相对依赖链 **且** 至少一个日期锚点。三者全无 → **不出甘特**（**"只有依赖、没有任何日期锚点"落在这里，属不出图**——见 5.2 判据表第三行）。

**判定取引擎**：`gantt.schedule_material.gantt_recommended`（`false` = 不出甘特）与同结构里的 `reason`（可直接作声明句素材）、`has_planned_dates`、`weak_git_material`。文档不重复判定，只按结果退化。

### 5.2 判据表（材料 → 出不出甘特）

> **判据表与引擎判定一致，不另立标准**：下表每一行的"出不出图"都能由引擎 `gantt.schedule_material` 的字段直接读出（`has_planned_dates` / `gantt_recommended`），执行器**不做第二套判断**。

| 材料情形 | 引擎字段 | 甘特图 | 替代呈现 |
|----------|----------|--------|----------|
| 任务清单 + 日期/工期 | `gantt_recommended=true` | 出完整甘特（走 [task-progress.md](task-progress.md)）| — |
| 任务清单 + 先后依赖 + **至少一个日期锚点** | `gantt_recommended=true`（锚点即计划日期） | 出**相对排期甘特**：除锚点条外其余条以相对依赖定位，`title`/图说明确标注「除锚点外仅表先后次序」 | — |
| 任务清单 + 仅先后依赖、**无任何日期锚点** | `gantt_recommended=false` | **不出甘特**（没有任何可落点的时间基准，画出来的横轴是虚构的）| WBS + 特性/任务状态表 + 状态叙述 |
| 有 `work_items[]`，但**无任何计划/实际日期与工期** | `gantt_recommended=false` | **不出甘特** | WBS + 特性/任务状态表 + 状态叙述 |
| `work_items[]` 只有名称与状态（无日期、无 `checks`）| `gantt_recommended=false` | **不出甘特** | 复用《功能分解》WBS（单层/特性层）+ 特性状态表 |

### 5.3 "只有 git 提交日期"能否作为工期依据？

**判据：不能作为任务级排期依据。** git 提交日期反映的是**代码写入活动**，不是任务的计划工期或起止排期。

- ❌ **禁止**：把某任务/特性的 git 首末提交日期直接当作它的 `starts/ends` 画进甘特条形——这是把"提交活动区间"冒充成"任务排期"。
- ✅ **合法用法**：git 首末提交仅可作为**项目整体活跃区间**的推断锚点，写进 `## 项目概览` 或 `## 元信息` 叙述，且必须标 `（推断）`：
  `项目 git 活跃区间：<yyyy-mm-dd> 至 <yyyy-mm-dd>（推断自 git log 首末提交）`。
- **极弱材料判据（由引擎判定，仅 opt-in repo 情形适用）**：只有在 repo 已 opt-in 且授权了日期类字段时才会有 git 材料；把 `git_window: {commit_count, first_commit, last_commit}` 写进引擎输入，引擎输出 `gantt.schedule_material.weak_git_material` 与 `reason`。**判定阈值（提交数下限、跨度天数下限）是引擎内的可配置常量**，本文档**不写任何具体阈值、也不写算式**——阈值改了文档不用改，执行器一律只读 `weak_git_material` 与 `reason`。命中时 git 日期**不足以支撑任何任务级排期**——甘特一律不出图，`### 材料缺口` 记引擎给出的 `reason`（其文本形如「git 材料过弱（`<提交数>` 提交 / 跨度 `<天数>` 天），不作排期依据」——**括号里的数字来自引擎输出，不是阈值、也不是本文档规定的值**）。

> **形态示例（不是判据）**：一个提交数与跨度都很小的仓命中极弱材料判据 → **甘特不出图**；git 区间仅用于概览一句推断叙述。"什么算小"由引擎阈值决定，**不得**在文档或报告里凭本例的数量级自行比较。未 opt-in 时连这一步都没有——直接因表单无计划日期而不出甘特。

### 5.4 不出甘特时 `## 任务进展` 章节体

= 段首材料声明句（第 8 节模板）+ 复用/引用《功能分解》WBS（或一句"任务分解见《功能分解》"）+ **特性/任务状态表**（来源、状态；无进度%列或该列全 `-`）+ **整体状态叙述**（如"7 个特性中 4 项 Implemented、3 项 Draft；无排期材料，故不呈现甘特图与进度百分比"）。today 参照线随甘特一并省去。

## 6. `## 元信息` 的「材料缺口」清单固定结构

在 `## 元信息` 内新增固定小节 `### 材料缺口`，让读者一眼看到报告边界。结构固定为三列表格：**缺什么 | 已检索来源 | 报告影响（不存在/降级的内容）**。每行的"已检索来源"必须具体到**路径 / 命令 / 文档名**（证明确实找过，不是没找），"报告影响"必须指名到**具体章节/图**。

````markdown
### 材料缺口
| 缺什么 | 已检索来源 | 报告影响（不存在/降级的内容）|
|--------|-----------|------------------------------|
| 工作项的计划日期与工期 | 表单 `work_items[].planned_start/planned_end`（空）、用户提供的进度文档/看板导出（无）| 不呈现《任务进展》甘特图；该节退化为特性状态表 + 状态叙述 |
| 里程碑 | 表单 `milestones[]`（空）、上下文中的发布/评审/验收节点（无）、路线图（未提供）| 不呈现里程碑跟踪表与视图；`## 项目里程碑` 仅保留材料声明 |
| 负责人 | 表单 `people[]` 与条目 `owner_id`（空）、外部文档指派人（无）、repo `people.owner_name` 授权（未声明）| WBS/表整体写 `未记录`；覆盖率取引擎 `people.coverage_formula`，见《人员与分工》|
| 进度百分比 | 表单 `work_items[].checks` 与 `progress_pct`（空）| 无 in-progress 百分比（引擎 `progress_pct=null`）；状态仅按 `status` 字面量映射（见 consistency-rules.md §1.1），状态本身不含进度数字 |
| 里程碑/工作项的计划完成日 | 表单 `planned_end` / `planned_date`（空）、`anchor_item_id`（空）、迭代计划（未提供）| 相关条目引擎判 `unknown-schedule`：报告声明「无计划日期，无法判定延期」，**不判逾期、不上红**，也未用 git 日期代替计划日 |
````

- 每一行都与某个章节内的 `> 材料声明：` 呼应；声明句是局部提示，本表是全局汇总地图。
- 缺口清单**非空**本身是诚实信号，不是缺陷；空表（`| 无 | - | - |`）只在材料确实充足时出现。

## 7. 表单填得少时的最小可交付报告形态

**原则**：表单信息少的项目，报告应当**短而诚实**，不追求"看起来丰满"。占位数字、虚构图表、升格事件都是反模式。报告长度不设下限、不设"完整度"KPI。

**必留（骨架契约）**：五章标题全部保留——`## 项目概览` / `## 需求与特性` / `## 功能分解` / `## 项目里程碑` / `## 任务进展`——缺字段的章节体退化为"材料声明 + 已检索来源"，但标题不删。`## 元信息`（含 `### 材料缺口`）必留。

**必出（有字段就出）**：项目概览叙述（`project_name` 是 R 档、`project_desc` 常有）、工作项或特性状态表（R 档保证 `work_items[]`/`milestones[]` 至少一组非空）——它们是最小报告的"实"骨干。

**可省的图（按材料条件）**：

| 图 | 省的条件 |
|----|----------|
| 特性概览脑图 | 条件出图（判据见 [requirements-features.md](requirements-features.md)「概览图出图判据」）：特性行数 <8 **或** 材料未提供可指认的分组依据 ⇒ 省 |
| WBS | 有 `work_items[]`/`features[]` 就出（可只到单层/特性层）；两者皆空属 R 档阻断 |
| 里程碑视图 | `milestones[]` 为空即省（第 4 节）|
| 任务进展甘特 | 无计划/实际日期与工期字段即省，替代为状态表（第 5 节）|

**最小形态参考清单**（针对表单只填了 `project_name`/`baseline_date` + 一组工作项或特性、无里程碑/负责人/排期的项目）：

1. `## 项目概览` —— **实**：背景/目标/范围（`project_desc` + 上下文摄取所得，逐条注明出处）。
2. `## 需求与特性` —— **实**：特性状态表（表单 `features[]` 各行，含 `status` 与 `source` 列）。
3. `## 功能分解` —— **实但降级**：WBS 以推断出的阶段（或特性）为顶层 + 工作项为叶子，四态着色（按 [consistency-rules.md](consistency-rules.md) §1.1 映射 `status`；无排期字段则引擎不会产出 delayed，故该图无 `.late`），无 `owner_id`（`【未记录】` 或整图 caption）、无 date；`### 人员与分工` 覆盖率声明取引擎 `people.coverage_formula`。
4. `## 项目里程碑` —— **降级为声明**：材料声明「表单未提供里程碑」+ 已检索来源。
5. `## 任务进展` —— **降级为叙述**：材料声明「无排期字段、不出甘特」+ 状态叙述。
6. `## 元信息` —— **实**：含 `### 材料缺口` 表。

**最小交付目录形态**：交付物仍是**一个目录**、契约不变（`summary.md` + `assets/` + `data/`，报告内相对路径引用），只是内容随材料量收缩——稀疏项目可能只有 `summary.md` + `assets/` 里一张 WBS 的三件套（图源 `wbs.puml` + 渲染产物 `wbs.svg`/`wbs.png`）+ `data/` 里的项目数据库与引擎输出（引擎照跑：稀疏输入下它给出的正是 `unknown-schedule`/空值等诚实终态与声明句）。一张图都出不了时 `assets/` 允许为空目录（或省略），但 `summary.md` 与 `data/` 的数据库与引擎输出必须在；**不得**为撑满目录而放入占位图片，也不得引用交付目录外的文件顶替。

**门禁仍走**：概览/里程碑/WBS/甘特四道确认门禁不跳过；但退化章节向用户呈现的是"降级形态 + 材料声明"，用户确认的是"这些内容确实无材料、如实声明"，而非确认一份编造内容。里程碑/甘特门禁在完全缺失时呈现的即"本节不出图 + 声明句"。

## 8. 声明句模板库（可直接复制）

统一前缀 `> 材料声明：`（blockquote，醒目可扫读）。占位符 `<…>` 按实际填写。

- **里程碑完全缺失**：
  `> 材料声明：本项目未记录任何里程碑。已检索：项目输入表单 milestones[]（空）、上下文与用户提供的外部材料（无发布/评审/验收节点）、路线图（未提供）、opt-in repo 定向查询（<未声明 repos[] / 已查 git tag 0 个>）。因此本节不含里程碑跟踪表与里程碑视图；普通提交、版本号与已实现特性均未升格为里程碑。`

- **甘特不出图（无排期材料）**：
  `> 材料声明：表单未提供任何计划/实际日期与工期字段（work_items[].planned_start/planned_end 均为空，也无进度文档可摄取）。<opt-in repo 情形：git 提交仅 <N> 次、跨度 <M> 天，不足以支撑任务级排期——N/M 照抄引擎 reason，不自行判断"够不够"。>因此不呈现甘特图；下方以任务/特性状态表与整体状态叙述替代。`

- **甘特降级为相对排期**（有依赖无日期）：
  `> 材料声明：表单仅提供工作项先后次序（depends_on）、无任何日期锚点。下图为相对排期，仅表先后依赖、非日历排期，未标注绝对日期。`

- **无计划日期、无法判定延期**（引擎 `schedule_status/status = unknown-schedule`）：
  `> 材料声明：<M6 长期演进节点 / T-04 等 N 项> 在材料中没有计划完成日期，因此**无法判定是否延期**——本报告如实标注为"无计划日期"，既不判为逾期（不上红）、也不视作按期；未用 git 提交日期等推断基线代替计划日。`

- **任务状态完全缺失**：
  `> 材料声明：表单未记录任务/特性状态信息（status 与 checks 均为空）。相关条目状态记为「未知」，图内不着四态色；「未知」表示无从判定，非「未开始」。`

- **WBS 分解深度受限**（无 plan/tasks）：
  `> 材料声明：表单未提供阶段划分（phases[] 为空 / 工作项无 phase_id），无 phase→task→subtask 层级材料。下方 WBS 以<推断出的阶段 / 特性>为顶层、工作项为叶子（阶段划分推断自工作项分组），不含任务级工期与负责人。`

- **负责人完全缺失**（另见 [people-encoding.md](people-encoding.md) 2.3；**git 作者的处置按其 2.4 的确定性裁决，不在本模板里二选一**）：
  `> 材料声明：本项目未记录任何负责人信息。已检索：表单 people[] 与条目 owner_id（空）、外部文档指派人（无）、opt-in repo 的 git 作者推断（<未声明 repos[] / 未授权 people.owner_name / 已授权但按 people-encoding 2.4 只得到项目级作者名册，无条目级负责人>）。全图不含人员标注（非「未分配」）。`
  > **括号里三种情形互斥、由事实唯一确定**（未 opt-in / 已 opt-in 未授权该字段 / 已授权但只有项目级作者），执行器按实际情况填其中一种，**不得**在"标注该作者"与"全图未记录"之间自行取舍。

- **git 活跃区间推断**（用于概览/元信息，非任务排期）：
  `项目 git 活跃区间：<yyyy-mm-dd> 至 <yyyy-mm-dd>（推断自 opt-in repo:<repo_id> 的 git log 首末提交，仅表示代码写入活动、非任务排期）。`
