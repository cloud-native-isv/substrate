# 中间数据结构规范（记录层 Schema）—— 单一呈现口径的具体化

本文档定义 `summarize-project` 技能的**四个规范中间数据结构**（记录层）及其**到呈现物的派生映射**。工作流主框架见 [../SKILL.md](../SKILL.md)；跨层公共约定见 [reporting-playbook.md](reporting-playbook.md)；这些结构在图与报告正文中的**具体承载位与图元字面量**见 [people-encoding.md](people-encoding.md)。

**与 [required-info.md](required-info.md) 和 [`../schema/project.sql`](../schema/project.sql) 的分工（去重，避免同一规则两处写）**：

- **字段定义与约束的可执行权威是 [`../schema/project.sql`](../schema/project.sql)（DDL）**：列名、类型、取值域、非空、唯一、外键、条件必填组合由**数据库**强制。本文档**不重复任何 schema 描述**，涉及字段定义时一律引用 DDL。
- **业务含义与三档必填性（R/I/O）的权威是 [required-info.md](required-info.md)**。
- 本文档只管**记录层 → 呈现物**：记录表怎么落成报告里的表格、WBS/甘特/里程碑图元怎么由记录派生、派生前的完整性检查。
- **结构 ↔ 关系模型的表一一对应**（同名字段、同一份数据的两种视图）：

| 记录层结构 | 对应的数据库表 |
|------------|----------------|
| A 项目目标块 | `project`（`project_name` / `project_desc` / `baseline_date`）+ 上下文摄取的背景/范围叙述 |
| B 任务记录表 | `work_items`（+ `phases` 承载层级、`work_item_deps` 承载依赖） |
| C 里程碑记录表 | `milestones` |
| D 人员映射表 | `people`（被 `owner_id` 外键引用） |

- 因此**记录层就是数据库的一个视图**：不再需要"序列化成引擎输入"这一步——引擎直接读 `data/project.db`（`progress-engine.py --db`），取数与聚合都用 SQL。需要一份 JSON 中间产物时用 `project-db.py --export-json`（**只换形态、不换字段名**）。

## 0. 记录与呈现的分离

- **记录（Record）** = 格式化结构表示：采集到的项目信息先按本文档的四个结构归集，再**装载进关系模型**——字段类型、必填性、日期形态、状态取值域**由数据库约束在装载时强制**（规则见 [`../schema/project.sql`](../schema/project.sql)），不靠文档里的格式提醒。
- **呈现（Presentation）** = 可视化表示：报告中的一切表格、图表（WBS、甘特图、里程碑视图、脑图）与叙述**只能从这四个结构派生**，不得绕过结构直接从原始材料落笔。
- 中间结构是**报告生成过程中的口径**，以报告内表格的形态呈现（记录表即报告表格）；它在库里的对应物就是 `work_items` / `milestones` / `people` / `project` 四张表。
- **结构 B/C 同时是进度引擎的输入**：引擎直接读数据库（`scripts/progress-engine.py --db <交付目录>/data/project.db`），用 SQL 取数与聚合，算出状态、进度%、延期天数、聚合与甘特参数；表格里的状态/进度/逾期列一律**回填引擎输出**，不在文档或报告里手算（见 [consistency-rules.md](consistency-rules.md) §0.1）。
- **数据库是派生产物**：落在**交付目录的 `data/` 子目录**（`<交付目录>/data/project.db`，与之并列的 `project-input.yaml` 是用户维护的表单——技能只读它），默认**每次运行由表单重建**（`project-db.py --load`）；用户希望基于历史库按最新信息演进时用 `project-db.py --update`（UPSERT + 变更摘要），并在 `## 元信息` 注明。本技能保持只读呈现定位，除交付目录外**绝不向目标项目写入任何持久化数据**，也**不改写表单内容**。
- 结构在上下文中定稿后进入确认门禁；门禁通过即冻结，所有派生物（图表、叙述）必须与冻结的结构逐字一致。
  > Gate probe: gate-summarize-project-structure-freeze — after the user decision, record firing evidence per confirmation-gates.md §门控观察协议 (non-blocking).

四个结构与全局约定：

| 结构 | 名称 | 回答的问题 | 主要派生物 |
|------|------|------------|------------|
| A | 项目目标块 | 项目目标是什么 | `## 项目概览` 全节文本 |
| B | 任务记录表 | 项目包含哪些任务、什么状态 | WBS 图、进展甘特图、任务记录表格 |
| C | 里程碑记录表 | 里程碑是什么、完成了哪些 | 里程碑视图（条件出图）、里程碑跟踪表、甘特 `happens` 菱形（标签带 `符号 + yyyy-mm-dd`） |
| D | 人员/负责人映射表 | 谁负责什么 | `### 人员与分工` 小节（含覆盖率声明）、WBS 节点第二行 `【姓名】`、甘特条形后缀 ` ▪ 姓名`、里程碑标签后缀 ` ▪姓名` |

**全局字段约定**（适用于所有结构）：

- **来源**：每条记录带来源列（对应 `source` 列，档位 **I**：未填时由 `sources` 表的声明推断并在 `inferred_fields` 留痕），格式 `<文档/系统>#<章节或视图>`、`git:<命令要点>`（仅 opt-in repo）或 `用户描述 / 表单填写`。
- **日期**：报告与图表里的一切日期一律呈现为 `yyyy-mm-dd`（如 `2026-02-14`）；推断出来的日期在呈现值后加 `（推断）`。**日期字面量与日历日的合法性由数据库约束保证**（见 [`../schema/project.sql`](../schema/project.sql) 各日期列的 `CHECK`），本文档不重述格式规则；剩下的归一化职责见第 5 节。
- **状态取值域由数据库约束保证**（见 DDL 中 `status_norm` 列的 `CHECK`）：任务侧四态 `completed / in-progress / delayed / not-started` 加 `deferred`、`unknown` 两个诚实桶；里程碑侧 `achieved / pending / at-risk` 加 **`unknown-schedule`（无计划日期，无法判定延期——不等于 pending、绝不上红）**。取值由引擎产出，不手填。两套取值域独立，`delayed`（工作项）与 `at-risk`（里程碑）只共用红色与 `⚠`，**不得互相混写**（这条是呈现纪律，数据库拦不住）。**降级例外**：当某条目在所有来源中都无任何状态信号时，取诚实降级终态 `未知（材料无状态信号）`——它**不属于**上述取值域、也**不等于** `not-started`（后者断言"确实未开始"、需有依据），须显式声明且图内不着状态色（见 [degradation.md](degradation.md) 第 3 节）。
- **状态与进度值的来源**：`状态` / `进度%` / `延期天数` 三个字段**一律取进度引擎脚本的输出**（`status` / `progress_pct` / `delay_days`）；记录层与呈现层都只做转录，**不在 Markdown 里比较日期、算天数差或算百分比**（字段清单与红线见 [people-encoding.md](people-encoding.md) 第 1.0 节）。
- **缺失值**：材料中没有的可选字段填 `未记录`（人员）或 `-`（其他），**绝不编造**；不得留空白（空白无法区分「未采集」与「确认缺失」）。进度百分比、里程碑日期、工期、负责人、任务状态五类信息无依据时的合法终态（`-（无可计数依据）` / `未排期` / `未记录` / `未知`）及其在表格/图/叙述三处一致呈现的规则，见 [degradation.md](degradation.md) 第 3 节。

## 1. 结构 A：项目目标块（Goal Block）

格式化 Markdown 文本块（非表格），字段规范：

| 字段 | 必填 | 格式 | 说明 |
|------|------|------|------|
| 背景 | 是 | 1–2 段 Markdown 叙述 | 项目为什么启动、解决什么问题；缺失时写「背景：材料未记录」 |
| 目标 | 是 | 条目列表，1–3 条，每条尾注 `（来源：…）` | 业务成果表述；材料未明说时标注「推断自 <出处>」 |
| 范围-做什么 | 是 | 条目列表 | in scope；缺失显式说明 |
| 范围-不做什么 | 是 | 条目列表 | out of scope；材料未界定时写「材料未界定」 |

示例（**虚构样例，只示形态**：目标条数、业务措辞与出处路径随项目而变）：

```markdown
**目标**
1. 让 <目标用户> 能够 <业务成果>（来源：<文档>#<章节>）
2. <第二条业务成果>（来源：<文档>#<章节>）
```

## 2. 结构 B：任务记录表（Task Record）

功能分解树的表格化形态：树（阶段 → 任务 →（有子任务材料时的）子任务）与本表一一对应，`父项` 字段承载层级。

| 字段 | 必填 | 报告表格取值 | 说明 |
|------|------|--------------|------|
| ID | 是（可推断） | 库列 `work_items.item_id`（如 `T-01`），阶段行用 `phases.phase_id`（如 `P-01`） | 缺失时由装载器按出现顺序生成并在 `inferred_fields` 留痕（唯一性由数据库保证） |
| 名称 | 是 | 业务语言动词短语（库列 `item_name`） | 与 WBS/甘特/叙述逐字一致 |
| 父项 | 是（可推断） | 库列 `phase_id` 解析出的阶段；顶层填 `-` | 承载分解树层级；缺失则该项挂顶层（外键可解析性由数据库保证） |
| 状态 | 是 | 引擎 `items[].status`（取值域见 DDL） | **回填引擎输出**；喂给引擎的是库里的 `status` 原文字面量与 `checks_*` 勾选计数（口径见 [task-progress.md](task-progress.md)） |
| 进度% | 条件必填 | 引擎 `progress_pct` | **回填引擎输出**，并同列/邻注照抄 `progress_formula`（自带分子分母）；记录层只登记「进度依据」（可计数事实的出处）供引擎计算，**百分比本身不在记录层或文档中推算**；空值 → 写 `-（无可计数依据）`，**不手算、不臆造、不得填 0 顶替** |
| 排期状态 / 延期天数 | 条件必填 | 引擎 `schedule_status` + `delay_days` | `delayed` 时写「逾期 N 天」（N = `delay_days`，必填）；`unknown-schedule` 时写「无计划日期，无法判定延期」；其余态填 `-` |
| 开始日期 | 否 | 库列 `planned_start` / `actual_start`，或 `-` | 呈现为 `yyyy-mm-dd`；引擎标为推断的日期加 `（推断）`（合法性由数据库保证，见第 5 节） |
| 结束日期 | 否 | 库列 `planned_end` / `actual_end`，或 `-` | 同上 |
| 负责人 | 是（可选来源） | 库列 `owner_id` 解析出的 `owner_name`，或 `未记录` | 呈现名取引擎 `items[].owner_name`；opt-in repo 推断出的须带 `（推断）` |
| 依赖 | 否 | `work_item_deps` 里该项的前置工作项，或 `-` | 无依据不填（不虚构依赖） |
| 来源 | 是 | 见全局约定 | 每行必填 |

示例行：

| ID | 名称 | 父项 | 状态 | 进度% | 开始日期 | 结束日期 | 负责人 | 依赖 | 来源 |
|----|------|------|------|-------|----------|----------|--------|------|------|
| P-01 | 需求定义阶段 | - | completed | 100 | 2026-01-05 | 2026-01-16 | 未记录 | - | specs/001-cli/tasks.md#Phase1 |
| T-03 | 完成镜像构建流水线 | P-02 | in-progress | 60 | 2026-02-02（推断） | - | 张三 | T-02 | specs/001-cli/tasks.md#L42 |

## 3. 结构 C：里程碑记录表（Milestone Record）

| 字段 | 必填 | 报告表格取值 | 说明 |
|------|------|--------------|------|
| 名称 | 是 | 业务语言（如 `M1 需求冻结`，库列 `milestone_name`） | 三处呈现逐字一致；图内标签另加 `符号 + yyyy-mm-dd + ▪负责人`（不计入名称比对） |
| 锚定 | 是（可选来源） | 库列 `planned_date`，或由 `anchor_item_id` 指向的工作项结束点换算 | 锚定日的解析（绝对日期优先、否则取锚定工作项结束点）由 SQL 完成；关联可解析性由数据库保证；两者皆缺 → `未排期` |
| 状态 | 是 | 引擎 `items[].status`（取值域见 DDL） | **回填引擎输出**（判定语义见 [consistency-rules.md](consistency-rules.md) §6.1，编码映射见 [milestones.md](milestones.md)「锚定与状态规则」）；**记录层不自行比较日期**——延期/逾期由引擎判定，记录层只转录；无计划日期的一律 `unknown-schedule`，**不得**补一个推断日期再判逾期 |
| 达成/风险依据 | 条件必填 | 照引引擎 `evidence`（+ 出处） | achieved 与 at-risk 必填；逾期类写 `逾期 N 天`（N 取引擎 `delay_days`，可附引擎给出的基准日与锚定日字面量）；`unknown-schedule` 固定写「无计划日期，无法判定延期」；pending 填 `-` |
| 负责人 | 是 | 结构 D 规范名或 `未记录` | 同结构 B 约定；进入里程碑图元标签的 ` ▪姓名` 后缀 |
| 来源 | 是 | 见全局约定 | 每行必填 |

示例行：

| 名称 | 锚定 | 状态 | 达成/风险依据 | 负责人 | 来源 |
|------|------|------|----------------|--------|------|
| M1 需求冻结 | 2026-01-16 | achieved | git 标签 v0.1（2026-01-16） | 未记录 | git:tag v0.1 |
| M3 联调完成 | 2026-04-03 | at-risk | 逾期 3 天（基准日 2026-04-06 − 锚定日 2026-04-03） | 王五 | specs/001-cli/tasks.md#L58 |
| M5 首版发布 | at T-05's end | pending | - | 李四 | docs/roadmap.md#Q1 |

> **上面三张示例表都是虚构样例**（项目名、人名、日期、路径均为占位），只用于固定**列结构与取值形态**；任何具体值都不构成规则依据（可移植性纪律见 [portability.md](portability.md)）。示例中 M3 依据列的括注是**照抄引擎 `evidence` 的字面量**（引擎生成的解释文本），不是记录层可执行的计算规则——记录层不做日期相减。

## 4. 结构 D：人员/负责人映射表（People Roster）

| 字段 | 必填 | 取值/格式 | 说明 |
|------|------|-----------|------|
| 规范名 | 是 | 一人一个对外呈现名 | 报告各处统一使用此名 |
| 别名/邮箱 | 否 | git 中出现的其他署名与邮箱，逗号分隔 | 用于身份归并；无则 `-` |
| 角色 | 否 | 材料中的角色/职责，或 `未记录` | 不得凭姓名或提交内容臆断角色 |
| 负责条目 | 是 | 结构 B/C 的 ID 列表，或 `-` | 与结构 B/C 的负责人列互为镜像 |
| 来源 | 是 | 见全局约定 | 区分 `工件字段`、`外部文档`、`git:shortlog（推断）` |

示例行：

| 规范名 | 别名/邮箱 | 角色 | 负责条目 | 来源 |
|--------|-----------|------|----------|------|
| 张三 | zhangsan <zs@corp.com>, zs-dev | 未记录 | T-03, T-04 | specs/001-cli/tasks.md#L42 |
| 李四 | - | 发布负责人 | M2 | docs/roadmap.md#Q1 |

**人员采集规则**（按优先级，高优先级来源覆盖低优先级）：

1. **表单/工件显式字段**：表单 `people[]` + 条目 `owner_id`，以及（opt-in 时）工件里明写的负责人/assignee/owner 字段——直接采信。
2. **外部文档**：会议纪要、看板导出、路线图中的负责人/指派人字段——采信并注明文档出处。
3. **git 历史（推断，须标注）**：**仅当 repo 已 opt-in 且该仓 `derive_fields` 声明了 `people.owner_name`** 时使用。
   - 项目级人员盘点：`git shortlog -sne --no-merges`（得到 姓名/邮箱/提交量）；
   - 条目级推断负责人：`git log --format='%an <%ae>' --no-merges -- <相关路径>` 取主要作者；
   - **落盘规则按 [people-encoding.md](people-encoding.md) 2.4 的确定性裁决**（未授权 / 单作者 / 多作者 / 路径级授权四行之一决定"进名册"还是"回填条目"），**不得**在"标注该作者"与"全图未记录"之间自行取舍；
   - git 推断出的负责人一律在值后加 `（推断）`，并在 `## 元信息` 假设区逐条登记。
4. **身份归并**：同一人多个署名/邮箱按邮箱或明显同名归并到一个规范名，别名全部登记；无法确认是否同一人时不归并、并列保留。
5. **诚实降级**：三级来源都没有 → 负责人填 `未记录`；**绝不**根据文件名、代码风格或想象编造人名；`未记录` 是合法且诚实的终态，不算缺陷。

## 5. 日期：呈现形态、合法性把关与推断标注

**呈现形态**：报告与图表里的一切日期（锚定日期、起止日期、生成日期、达成依据中的日期）一律 `yyyy-mm-dd`（零填充，如 `2026-02-05`）。PlantUML 甘特语法本身接受该格式，无需二次转换。

**合法性由数据库把关**：日期列的形态（零填充 `yyyy-mm-dd`）与**真实日历日**（`2026-02-30`、`2026-04-31` 这类会被拒）由 [`../schema/project.sql`](../schema/project.sql) 的 `CHECK` 约束在装载时强制——**非法写法、歧义写法（如 `02/03/2026`）与不存在的日历日根本进不了模型**，装载器报出可读原因、退出码 3。本文档不重述格式规则、也不靠提醒。

**摄取阶段的责任**：把材料原文日期换算成零填充 `yyyy-mm-dd` 再落进表单。材料内写法歧义时，先按该材料内其他无歧义日期确定主导格式；无法确定则**不采信该日期**并在报告说明歧义（宁缺勿猜）。

**提取来源与规范命令**（git 日期在提取时即输出目标格式，避免事后转换出错）：

| 来源 | 命令/方法 | 得到 |
|------|-----------|------|
| 表单/库字段 | 直接读 `planned_start`/`planned_end`/`actual_start`/`actual_end`/`planned_date`/`actual_date` | 计划/实际日期（**主源**） |
| git 标签日期（**仅 opt-in 且已授权**） | `git for-each-ref --format='%(refname:short) %(creatordate:short)' refs/tags` | 发布/里程碑锚点 |
| git 提交日期 | `git log --date=short --format='%ad %s'`（首末提交定项目起止锚点） | 起点、活跃区间 |
| 路径级活动区间 | `git log --date=short --format='%ad' -- <路径> \| sed -n '1p;$p'` | 任务起止推断锚点 |
| 工件内日期 | 解析文本中的日期字面量 | 计划/完成日期 |

**月精度补日仍由引擎处理**：材料只给到年月（`2026-02`）时，引擎补当月首日并置 `date_meta.<字段>.inferred=true`（`precision=month`），呈现时值后加 `（推断）`——**"日"是引擎补出来的，属推断；单纯的格式转写不算推断、不打标记**。

**推断日期标注**：非材料直接给出的日期（git 活动区间推断、估算的计划日、年月补日）一律在记录表值后加 `（推断）`，且在 `## 元信息` 假设区逐条登记「假设：<条目> <字段> 推断为 <日期>（依据：…）」。库里存纯日期，推断标记由引擎的 `date_meta.*.inferred` 与报告表格承担；生成 PlantUML 源码时只留日期。

## 6. 派生映射（结构 → 呈现物）

| 呈现物 | 派生自 | 派生规则 |
|--------|--------|----------|
| `## 项目概览` 全文 | 结构 A | 按字段顺序落笔，出处尾注保留 |
| WBS `@startwbs` | 结构 B（+D） | 按 `父项` 还原树；节点三行 = `标题 + 状态符号[ + ◆Mn]` / `【负责人】`（缺失写 `【未记录】`，全项目无人员则整图不标 + `caption` 声明）/ `NN%[（延期 N 天）]`（进度为 `-` 时该行不写）；状态类 `.done/.doing/.late/.todo` 由 `状态` 列决定 |
| 任务记录表格 | 结构 B | 原样呈现（即记录表本身） |
| 进展甘特 `@startgantt` | 结构 B + C（+D） | 带日期的叶子生成条目，显示名写 `[任务名[ ⚠] ▪ 负责人] as [别名]`（`⚠` 仅 `delayed` 条；缺失负责人写 ` ▪ 未记录`；**不用 `on {}`**）；`状态`→`is colored in`（四态色板）、`进度%`→`is N% complete`；C 的 `happens` 逐条复制，标签带 `符号 + yyyy-mm-dd` |

| **引擎输入 = 数据库 `project.db`** | 结构 A/B/C/D（+ 覆盖清点，opt-in 时 + git 窗口） | `project-db.py --load` 把表单装载进关系模型（**装载即校验**，表结构见 [`../schema/project.sql`](../schema/project.sql)）；落交付目录 `data/` 子目录，引擎经 `--db` 直接读取、用 SQL 查询与聚合。需要 JSON 中间产物做比对时用 `--export-json`（兼容形态，字段名不变） |
| 状态 / 进度% / 延期天数 / today 偏移 / 覆盖闭合等式 | **引擎输出 `engine-out.json`** | 报告与各图**照抄字段**（`status` / `progress_pct` / `progress_formula` / `delay_days` / `gantt.today_offset_days` / `coverage.*`），零手算 |
| `### 整体进度摘要`（项目概览） | 进度数据（项目级汇总） | 完成度句 + 判断句 + 四行概览表，数值逐个取汇总字段（见 [progress-presentation.md](progress-presentation.md) 3.1） |
| `### 工作项进度`（功能分解） | 进度数据（分组聚合 + 条目） | 阶段级聚合表取分组字段、工作项级表取条目字段（3.3） |
| 里程碑进度汇总表 | 进度数据（里程碑汇总） | 达成率 / 已达成·逾期·待达成 / 最大逾期天数（3.4）；无里程碑材料时整表不出 |
| `### 进度叙述`（任务进展） | 进度数据（项目级汇总 + 分组聚合） | 整体句 + 分阶段进度表 + 完成度分布 + 逾期条目数（3.5），与甘特图说同字段同值 |

**派生纪律**：呈现物中的每个条目必须能指回结构中的一行；结构中没有的条目不得出现在任何图表或叙述中（无孤儿条目）；发现呈现需要新条目时，先回记录层补行（含来源），再重新派生。
