# Code Review 最佳实践工作流（方法论全本）

> 本文件是 `code-review` Skill 的方法论参考，承载 `SKILL.md` 各 Phase 步骤引用的细节。
> 工具映射：`git-delta-review.sh diff` → 粒度自检与渲染；`review` → 结构化审查；`note` → 分级反馈落盘；`report --summary` → 收敛判定与合入门禁。

## 一、全景视图

完整的 Code Review 工作流覆盖 **提交前 → 审查中 → 反馈后 → 合入后** 四阶段闭环：

| Phase | 内容 | 目标 |
|-------|------|------|
| 1 提交前准备 | 自检清单、小批量提交、上下文准备 | 让 Reviewer 不需要猜 |
| 2 审查执行 | 结构化审查、多维度检查、优先级排序 | 知道看什么、按什么顺序看 |
| 3 反馈与迭代 | 分级反馈、讨论与共识、修改与复审 | 对事不对人、快速收敛 |
| 4 合入与沉淀 | 合入策略、知识沉淀、度量改进 | Review 不是终点而是起点 |

---

## 二、Phase 1：提交前准备（Author 的责任）

### 2.1 提交粒度控制

| 规则 | 说明 | 反例 |
|------|------|------|
| **单一职责** | 一个 PR 只做一件事 | "修复 bug + 重构 + 加功能"混在一起 |
| **体积上限** | 建议 < 400 行变更（不含生成代码/锁文件） | 一个 PR 改了 3000 行 |
| **可独立合入** | 不依赖其他未合入的 PR | "这个 PR 需要 #123 先合" |
| **原子性** | 每个 commit 都能编译通过、测试通过 | 中间 commit 编译报错 |

经验公式：`Review 质量 ≈ 1 / (变更行数 × 文件数)`。超过 400 行的 PR，Reviewer 的发现率急剧下降（SmartBear 研究数据）。脚本 `diff`/`review` 内置 size guard 自动执行该守门。

### 2.2 PR 描述模板

```markdown
## What（做了什么）
用 1-3 句话描述这个变更的目的。

## Why（为什么做）
- 关联 Issue: #1234
- 背景: 线上支付超时率从 0.1% 升至 2.3%
- 根因: 连接池未设置 idle timeout

## How（怎么做的）
- 为连接池添加 idle_timeout=30s 配置
- 增加连接健康检查定时器
- 补充对应的单元测试

## Testing（如何验证）
- [x] 单元测试: `cargo test payment::pool`
- [x] 集成测试: 本地模拟 1000 并发连接
- [ ] 需要 Reviewer 关注: 超时值 30s 是否合理

## Risk（风险评估）
- 影响范围: 仅 payment-service
- 回滚方案: 配置项关闭即可回退
- 兼容性: 无 breaking change

## Screenshots / Diagrams（可选）
```

### 2.3 Author 自检清单

```markdown
- [ ] 代码能编译，所有测试通过
- [ ] 无调试代码残留 (console.log, println!, TODO-HACK)
- [ ] 无敏感信息 (密钥、密码、内部 IP)
- [ ] 变更与 PR 描述一致（没有"顺手改的"无关代码）
- [ ] 已自行 Review 一遍自己的 diff
- [ ] 复杂逻辑有注释说明 "为什么" 而非 "是什么"
- [ ] 新增公共 API 有文档注释
- [ ] 错误处理路径已覆盖（不是只测 happy path）
```

## 三、Phase 2：审查执行（Reviewer 的责任）

### 3.1 审查维度（P0–P6，按优先级排序）

- **P0 正确性**：逻辑是否正确？边界条件是否覆盖？并发安全/竞态/死锁？错误处理是否完备，失败时会发生什么？
- **P1 安全性**：输入校验/注入风险？权限检查/越权访问？敏感数据处理/日志脱敏？
- **P2 设计**：是否符合系统架构，是否引入不必要的耦合？抽象层次是否合理（过度设计或设计不足）？接口是否向后兼容？
- **P3 可维护性**：命名是否清晰、代码是否自解释？圈复杂度 >10 需警惕？是否有可抽取的重复代码？
- **P4 性能**：N+1 查询/不必要的循环？内存分配是否合理、泄漏风险？热路径上不必要的开销？
- **P5 风格与规范**：是否符合团队编码规范？格式化一致性（应由工具自动处理）？命名约定统一？
- **P6 测试**：是否覆盖变更核心路径？边界与异常路径是否有测试？测试本身是否可读、可维护？

### 3.2 审查顺序（推荐路径）

```
Step 1: 读 PR 描述          → 理解意图（What/Why/How）
Step 2: 看变更文件列表       → 建立全局认知（diff --files）
Step 3: 看测试代码           → 理解预期行为（测试即规格说明）
Step 4: 看核心逻辑变更       → 验证实现是否匹配意图
Step 5: 看接口/配置变更      → 检查兼容性和影响面
Step 6: 看辅助变更           → 日志、文档、重构，快速扫过
```

**为什么先看测试？** 测试代码是 Author 对"正确行为"的形式化描述。先读测试再看实现，能更快发现"实现与预期不符"。脚本 `review` 默认测试文件优先排序，自动落实 Step 3。

### 3.3 时间管理

| PR 规模 | 建议 Review 时间 | 说明 |
|---------|-----------------|------|
| < 100 行 | 15–20 分钟 | 快速审查 |
| 100–400 行 | 30–45 分钟 | 标准审查 |
| 400–800 行 | 60–90 分钟 | 建议拆分；不可拆则分多次看 |
| > 800 行 | 拒绝或要求拆分 | 超过此规模 Review 质量无法保证 |

关键规则：单次 Review 不超过 60 分钟（注意力衰减）；大 PR 分多次、每次聚焦一个模块（`--focus`）；在精力最好的时段做 Review。

## 四、Phase 3：反馈与迭代

### 4.1 反馈分级标注（与脚本 severity 一一对应）

| 级别 | 含义 | Author 的义务 |
|------|------|--------------|
| 🔴 `blocking` | 必须修改，否则不能合入 | 必须解决 |
| 🟠 `important` | 强烈建议修改 | 应解决，若不同意需说明理由 |
| 🟢 `suggestion` | 建议优化，可选 | 可采纳可不采纳 |
| ⚪ `nitpick` | 纯风格偏好 | 完全可选 |
| ❓ `question` | 不理解，需要解释 | 需要回复说明 |
| 👍 `praise` | 写得好，值得肯定 | 无需动作 |

示例：

```
🔴 [BLOCKING] src/payment.rs (Line 45)
gateway 可能为 None，这里直接 unwrap() 会在生产环境 panic。
建议改为 gateway.ok_or(Error::GatewayNotConfigured)?

🟢 [SUGGESTION] src/payment.rs (Line 12)
函数名 do_process 不太能表达意图，考虑 settle_transaction 或 execute_charge？

❓ [QUESTION] src/config.rs (Line 88)
为什么这里选择 30s 作为超时值？有压测数据支撑吗？

👍 [PRAISE] src/pool.rs (Line 23-40)
连接池的健康检查逻辑写得很清晰，定时器 + 懒清理的组合很优雅。
```

### 4.2 反馈的表达原则

| 原则 | ❌ 不好的表达 | ✅ 好的表达 |
|------|-------------|-------------|
| **具体** | "这里写得不好" | "这个循环是 O(n²)，数据量大时会成为瓶颈" |
| **给出理由** | "改成 X" | "建议改成 X，因为 Y 场景下会出现 Z 问题" |
| **给出方案** | "这不对" | "这不对，可考虑 A 方案或 B 方案，A 更简单但 B 更通用" |
| **对事不对人** | "你怎么又忘了处理错误" | "这个路径缺少错误处理，建议补充" |
| **承认不确定性** | "必须用 X" | "我倾向于 X，但如果你有更充分的理由用 Y，我同意" |
| **肯定好的部分** | （只提问题） | "整体设计很清晰，特别是 X 部分。有一个小建议..." |

### 4.3 迭代收敛规则

```
Round 1: Reviewer 提出所有意见
    → Author: 逐条回复（同意 / 不同意+理由 / 已修改）
Round 2: Reviewer 确认修改 或 追问（仅针对未解决的）
收敛条件: 所有 blocking 已解决 + 所有 important 已回应 → Approve
```

防无限循环：同一问题最多讨论 3 轮，超过则线下沟通或升级到 Tech Lead；`nitpick` 分歧不阻塞合入；`important` 设计分歧无法一致时由模块 Owner 最终决策。`report --summary` 将收敛条件固化为合入门禁判定。

## 五、Phase 4：合入与沉淀

### 5.1 合入策略与合入前检查

| 策略 | 适用场景 | 说明 |
|------|---------|------|
| **Squash Merge** | 功能分支 → 主分支 | 多 commit 压缩为一个，主分支历史干净 |
| **Rebase Merge** | 小改动、hotfix | 保留原始 commit，线性历史 |
| **Merge Commit** | 大型 feature 分支 | 保留完整分支历史，可追溯 |

合入前检查：

```markdown
- [ ] CI 全绿（构建 + 测试 + lint）
- [ ] 至少 1 个 Approve（核心模块建议 2 个）
- [ ] report --summary 门禁通过：blocking 清零、important 全部回应
- [ ] 无未解决的讨论线程
- [ ] 分支已 rebase 到最新主分支（无冲突）
```

### 5.2 知识沉淀

| 沉淀形式 | 内容 | 存放位置 |
|---------|------|---------|
| **ADR** | 设计决策及其理由 | `docs/adr/` |
| **编码规范更新** | Review 中反复出现的同类问题 | 团队 Wiki / CONTRIBUTING.md |
| **Checklist 更新** | 新发现的风险模式 | Author 自检清单（§2.3） |
| **Linter 规则** | 可自动化的风格/安全问题 | `.eslintrc` / `clippy.toml` 等 |

判断标准：同一问题在 Review 中被提出超过 2 次 → 变成自动化规则或 Checklist 条目，而非依赖人每次发现。

### 5.3 度量与持续改进

| 指标 | 健康范围 | 异常信号 |
|------|---------|---------|
| **Review 响应时间** | < 4 小时（工作时间） | > 24h 说明流程阻塞 |
| **Review 轮次** | 1–2 轮 | > 3 轮说明 PR 质量或沟通有问题 |
| **PR 体积** | 中位数 < 200 行 | 持续 > 500 行说明拆分意识不足 |
| **Review 覆盖率** | 100% 变更有 Review | 有绕过 Review 直接合入的情况 |
| **缺陷逃逸率** | Review 后仍漏到线上的 bug 数 | 持续上升说明 Review 流于形式 |

## 六、角色与职责矩阵

| 角色 | 职责 |
|------|------|
| **Author** | 写清晰的 PR 描述；控制 PR 体积；提交前自检；及时响应意见（<4h）；对 blocking 必须修改 |
| **Reviewer** | 在承诺时间内完成 Review；按 P0–P6 优先级结构化反馈；区分"必须改"和"建议改"；肯定好的设计；不阻塞于风格偏好 |
| **Module Owner** | 设计类分歧的最终裁决者；维护模块 Review Checklist；确保架构一致性 |
| **Team Lead** | 监控 Review 度量指标；解决跨模块分歧；推动流程改进；确保 Review 文化健康 |

## 七、常见反模式与对策

| 反模式 | 表现 | 对策 |
|--------|------|------|
| **橡皮图章** | 秒 Approve，从不提意见 | 要求至少一条实质性评论；轮换 Reviewer |
| **吹毛求疵** | 全是 nitpick，忽略设计问题 | 强制按 P0–P6 优先级排序反馈 |
| **守门人心态** | "必须按我的方式写" | 区分"客观错误"和"个人偏好"；偏好类标 `nitpick` |
| **拖延症** | PR 挂了 3 天没人看 | SLA 机制（<4h 响应）；自动分配 Reviewer |
| **巨型 PR** | 一次改 2000 行 | 强制拆分；size guard 警告（脚本已内置） |
| **只看不说** | 心里觉得有问题但不写出来 | 鼓励 `question` 类评论；"不确定也可以问" |
| **情绪化反馈** | "这写的什么垃圾" | 团队公约：对事不对人；Code of Conduct |
| **Review 疲劳** | 每天被分配 10 个 PR | 限制每人每天 Review 上限（如 3–5 个） |

## 八、一句话总结

**好的 Code Review 工作流 = 小批量提交 × 结构化审查 × 分级反馈 × 快速收敛 × 持续沉淀。**

目标不是"找 bug"（那是测试的事），而是在代码合入前，通过协作提升代码质量、传播知识、统一架构认知。工具（git-delta、本 Skill、AI 审查）是手段，文化和流程才是核心。
