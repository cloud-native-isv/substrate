# Tool Definitions Reference

Canonical definition of a **Tool**, plus the behavioral-rules format, type semantics, and edge-case handling for `/speckit.tools`. This file is the single source of truth for the Tool concept; other documents link here rather than re-defining it.

## What a Tool Is

A **Tool** is a **named, pre-verified, reusable definition of one concrete capability** — persisted as a record at `.specify/memory/tools/<name>.md` — that an agent invokes *instead of* working out how to perform that action on the fly.

An agent executing a task normally reaches straight for whatever it can call. That default has two failure modes, and a Tool exists to remove both:

- **Environment variance.** The same logical capability is not the same command everywhere. The binary may be named differently, be a different version, need different flags per version, differ by CPU architecture, or differ by OS. An agent reasoning from training knowledge picks *one* plausible invocation and gets it wrong on the machine actually in front of it. A Tool record pins the invocation that is **verified for this environment**, and records the variance explicitly (see Environment Applicability below) so the right form is selected rather than guessed.
- **Throwaway generated scripts.** For anything non-trivial, an LLM otherwise writes ad-hoc script code in the moment. Those scripts vary widely in quality, correctness, and completeness, and — critically — they vary **between runs**, so behavior is not reproducible. A Tool replaces that per-run improvisation with a definition that was verified once and is reused thereafter.

Hence the operating rule: **before generating script code to perform a complex action, look for an existing Tool and reuse it.** Only when no Tool covers the capability should new code be written — and if the capability is worth repeating, it should then be defined as a Tool.

This buys three things:

1. **Stability** — a verified invocation replaces a freshly improvised one, so the same action behaves the same way across runs, sessions, and agents.
2. **Efficiency** — reusing a definition skips the reasoning needed to rediscover, re-derive, and re-validate the invocation, cutting both inference overhead and wall-clock time.
3. **Authority** — a record's `## Behavioral Rules` **override the agent's built-in training knowledge** for that tool. Where the record and the model's beliefs disagree, the record wins.

A Tool is therefore an **abstraction layer between an agent's intent and the environment's reality** — not merely a note about a command.

## Terminology: three different things called "tools"

The word is overloaded in this project. Keep them distinct:

| Term | Meaning | Where it lives |
|------|---------|----------------|
| **Tool** / **Tool record** (this document) | A pre-verified reusable capability definition, owned by `/speckit.tools` | `.specify/memory/tools/<name>.md`; ID form `<TOOL:...>` |
| **AI agent CLI tool** | A supported coding agent — Claude Code, Codex CLI, Qoder CLI, Copilot, opencode, Hermes | `AGENT_CONFIG` in `src/specify_cli/`; `docs/reference/cli/` |
| **Agent tool-call list** | The `tools:` frontmatter key on an agent (`Read`, `Grep`, `Bash`, …) — the LLM's callable surface | `.specify/agents/{templates,instances}/<slug>.agent.md` frontmatter |

Unqualified "Tool" in the tools domain always means the first. The second is best written "AI agent CLI" / "agent tool"; the third, "tool-call list".

Note also: `.specify/memory/tools.md` (singular file) is the **discovery inventory** regenerated by `refresh-tools.sh`; `.specify/memory/tools/` (directory) holds the **definition records**. Only the directory is authoritative.

## Tool Type Standardization

| Type | Scope | Description | Source Identifier |
|------|-------|-------------|-------------------|
| `project-script` | Project-level | Scripts bundled with the current project (e.g., `scripts/bash/*.sh`). Available only within the project workspace. | Path relative to project root |
| `system-binary` | System-level | Executables installed system-wide via package manager or `PATH`. Available to all users/sessions. | Absolute binary path |
| `shell-function` | Shell-session | Functions loaded via `source` from dotfiles or activation scripts. Available only in current shell session. | Function name |
| `webhook` | Network-level | Remote operations triggered by HTTP request to a web endpoint. Available wherever HTTP connectivity and credentials exist. | URL endpoint |

## Environment Applicability

A Tool exists partly to absorb environment variance, so a record can state **where its invocation is known to hold** and **how it differs elsewhere**. Every field below is optional — omit it when the capability does not vary along that axis. Recording nothing means "no known variance", not "verified everywhere".

| Field | Purpose | Example |
|-------|---------|---------|
| **Verified Version** | The exact version the contract was verified against | `jq 1.7.1` |
| **Version Differences** | Invocation/flag differences across versions of the same tool | `--sort-keys only exists in ≥1.6; use -S below that` |
| **Platform** | OS applicability, and per-OS differences | `linux, macOS; macOS ships BSD sed — use gsed` |
| **Architecture** | CPU-architecture applicability or differences | `arm64 requires the -aarch64 build; x86_64 uses the default` |
| **Fallback** | What to use when the primary source is unavailable | `if rg is absent, grep -rn (slower, no --glob)` |
| **Preflight Check** | A cheap command proving the tool is usable before real use | `jq --version` |

Rules:

- A record MUST NOT claim an invocation is valid on a platform, architecture, or version it was not verified on. State what was verified; leave the rest unstated.
- When variance is known but a single invocation cannot cover it, put the branch in **Version Differences** / **Platform** / **Architecture** rather than silently pinning one form.
- When a **Preflight Check** is recorded, run it before the first real invocation in a session; a failed preflight means fall back or stop — never improvise a substitute command.
- Environment fields are **descriptive of the verified environment**, so they are re-verified (not assumed) after a toolchain, OS, or machine change.

## Reuse Before Generating

This is the cross-cutting discipline that makes a Tool worth defining. **Before generating script code to perform a complex or repeatable action**, any skill or command MUST:

1. **Look for an existing Tool** — scan `.specify/memory/tools/` (including aliases) for a record covering the capability.
2. **Reuse it when one exists** — invoke it per its record, treating its `## Behavioral Rules` as authoritative over training knowledge, and honoring its Environment Applicability fields. Do not re-derive an invocation the record already pins, and do not rewrite it as inline script code.
3. **Otherwise proceed normally** — when no Tool covers the capability, write the code needed for the task. This is expected; the gate is a lookup, not a blocker.
4. **Promote what recurs** — if the capability is non-trivial and likely to be needed again, offer to define it as a Tool via `/speckit.tools` so the next run reuses instead of regenerating.

Scope limits, so the gate stays cheap:

- The gate applies to **complex or repeated** actions, not to ordinary one-off file reads, greps, or single obvious commands.
- The gate is a **lookup plus a decision** — it never blocks the task, and a miss is a normal outcome.
- A `Draft` record does **not** satisfy the gate: it is incomplete by definition and cannot be invoked. Treat it as "no Tool yet" and, where useful, complete it via `/speckit.tools` modify.

## Behavioral Rules Format

Each behavioral rule MUST be a markdown bullet prefixed with an RFC 2119 keyword:

- `MUST` — absolute requirement the agent must follow in every invocation
- `MUST NOT` — absolute prohibition the agent must never violate
- `SHOULD` — recommended practice unless a justified exception applies
- `SHOULD NOT` — discouraged practice unless a justified exception applies

Format: `- {KEYWORD} {constraint text}`

These rules are **authoritative**: when a tool has a definition record, the AI agent MUST use the persisted behavioral rules as the source of truth, instead of relying on training knowledge about the tool.

## Edge Cases

- **Name conflict across types**: When same name exists under different types, require explicit user disambiguation. Present all matching records.
- **Non-existent source**: When tool references a source path that doesn't exist, warn user but allow record creation with `Draft` status.
- **Incomplete record invocation**: Block invocation of `Draft` tools. Guide user to complete the definition.
- **Contradictory behavioral rules**: Persist rules as-is with advisory note. User is authoritative source.

## Invocation Preview Format

Before executing any tool, display:

```
## Invocation Preview

**Tool**: <name> (<tool_type>)
**Command**: <resolved command>
**Parameters**: <resolved parameter values>

### Behavioral Rules
- MUST <rule 1>
- MUST NOT <rule 2>
...

**Expected Output**: <output shape>
```

Prompt: `Proceed with execution? (yes/no)`
- Only execute if explicit `yes`
- Do NOT modify parameters beyond what was previewed
- Record invocation session: tool_name, tool_id, resolved_command, result_status

## Output Requirements

- Tool records stored in `.specify/memory/tools/` as `.md` files
- Command output must include `tool_id` and canonical path
- Execution never happens before user confirmation via preview gate
- Existing complete records should be reused (avoid repeated discovery)
- AI agent MUST use persisted records as authoritative source
